## 1. 공통 규칙 (모든 글에 적용)

### 1-1. 우리만 아는 말은 쓰지 않는다

| 쓰지 않는 말 | 대신 쓰는 말 |
| --- | --- |
| 조각 1a, 조각 2 | 회원가입 기능, 프로필 기능 (기능 이름으로) |
| PR #38, 커밋 해시 | 무엇을 만들었는지 한 줄로 |
| pen 노드 번호 (`dIONW` 등), 화면 번호 (06-2a) | 화면 이름 ("이런 사람이 좋아요" 화면) |
| master11, 문서담당, 세션 이름 | 안 씀 |
| Task A9, Part B 같은 계획서 번호 | 안 씀 |
| 키, URL, 프로젝트 ref, 이메일 | 절대 안 씀 |

### 1-2. AI 가 쓴 티가 나지 않게

- 1인칭으로 쓴다. "~를 선택했다", "~로 정했다".
- "사용자가 결정", "지시에 따라", "세션이 처리" 같은 표현은 쓰지 않는다.
- 같은 문장 틀을 반복하지 않는다. 한 문단 안에서 문장 길이를 섞는다.
- 문장 흐름에 맞게 끊는다. 한 문장에 한 가지 내용.
- 과한 격식·번역투("~에 대해 고려하였음")는 피하고 평소 말하듯 쓴다.

### 1-3. 가독성

- 긴 내용은 **토글**로 접는다. 첫 줄만 보고도 요지가 보이게.
- 주제가 커지면 **하위 페이지**로 뺀다. 카드 본문은 요약 + 링크.
- 이모지는 제목·구분 정도로만 **적당히**. 줄마다 붙이지 않는다. (조금 쓰는 건 괜찮다)
- 하이픈은 `-` 만 쓴다. `—`(긴 대시) 는 쓰지 않는다.

### 1-4. 콜아웃과 표는 쓰지 않는다 (2026-09-21 사용자 결정, 되돌림)

한동안 콜아웃 블록과 표로 정리해서 올렸는데 **전부 되돌렸다.** 앞으로도 쓰지 않는다.

- **콜아웃 블록 금지.** 예외 없다.
- **표 금지.** "비교할 때만 표" 도 폐기했다 — 비교도 문단으로 쓴다.

읽는 사람이 면접관이라서 그렇다. 표와 콜아웃으로 각지게 정리된 글은 문서 생성기가 뱉은 것처럼 보이고,
정작 "왜 그렇게 했나" 가 칸 안에서 한 줄로 잘려 나간다. 문단으로 쓰면 판단의 흐름이 남는다.

### 1-5. 심플하게 줄이지 않는다 (2026-09-21 사용자 결정)

짧게 요약하는 쪽으로 기울지 않는다. **고려한 선택지의 장단점을 전부 적는다** — 고르지 않은 쪽의 장점,
고른 쪽의 단점까지. 분량이 늘어도 괜찮다. 한 줄 요약만 남으면 결론만 있고 생각한 흔적이 없는 글이 된다.

## 2. GANTT 보드 - 할 일 관리

| 상태 | 뜻 |
| --- | --- |
| Not started 🧱 | 시작 전. 할 일이 정해지면 바로 카드를 만든다 |
| In progress 🛠 | 하고 있는 중 |
| Done 🏠 | 끝남 |

- 기능 하나를 시작할 때 **Not started 카드를 먼저 만든다.** 제목은 기능 이름.
- 시작하면 In progress, 끝나면 Done 으로 옮긴다. 카드를 지우지 않는다.
- 날짜 속성은 실제 작업 기간으로 채운다 (간트·캘린더가 이 날짜를 쓴다).

**카드 본문은 구체적으로 쓴다** (2026-09-21 사용자 결정). "카드 기능을 만들었다" 같은 한 줄은 안 된다.
무엇을 만들었는지, 그 과정에서 막힌 게 있었으면 무엇이었고 어떻게 풀었는지까지 적는다.
정하기 애매했던 게 있었으면 왜 그쪽으로 정했는지도. 관련 결정이 따로 있으면 기술 결정사항 페이지로 링크한다.

## 2b. "개발 진행 기록" 카드

보드에 있는 **"개발 진행 기록"** 카드(옛 이름 "문서 정리 PR A")에 작업이 하나 머지될 때마다
평문으로 한 줄씩 쌓는다. 기능 카드와 달리 이건 시간순 로그다.

**검토에서 잡은 오류도 여기에 남긴다** (2026-09-21 사용자 결정). 빠뜨리지 않는다 —
"만들었다" 만 쭉 있는 기록보다 "이런 걸 놓쳤고 이렇게 고쳤다" 가 섞여 있는 쪽이 훨씬 믿음이 간다.

- 2~3문장 평문. 토글·목록·표 없이 그냥 문장으로.
- **내가 직접 쓴 것처럼.** "리뷰에서 지적됨" 이 아니라 "다시 보다가 ~를 발견해서 고쳤다".
- 조각·PR 번호·세션 이름은 여기서도 쓰지 않는다(§1-1).
- 예: "알림을 보내다 실패하면 그 뒤 사람들이 카드를 못 받는 구조였다. 알림 한 건이 실패해도 지급은 계속되도록 감싸고, 실패는 로그로만 남기게 바꿨다."

## 3. 캘린더 - 오늘 한 일

- **그날 한 일을 그날 날짜에** 적는다. 보드 카드와 같은 데이터베이스라 날짜만 맞으면 캘린더에 뜬다.
- 한 줄 요약 + 필요하면 토글로 상세.
- 예: "학생증 인증 화면 완성. 얼굴이 없는 사진은 앱에서 먼저 걸러내도록 했다."

## 4. 기술 결정사항 - 지금처럼 유지

틀은 그대로: **상황 → 고려한 선택지(장단점) → 선택 → 이유(비용·운영·지연 등 구체적으로) → 감수한 단점 / 바꿀 조건**

- 선택지마다 왜 안 골랐는지가 보여야 한다. **장단점은 줄이지 말고 전부**(§1-5).
- 이 틀도 표가 아니라 문단으로 쓴다(§1-4).
- 숫자(비용, 지연, 무료 구간)는 근거로 넣되 키·URL 은 안 넣는다.
- 결정이 바뀌면 지우지 말고 "바꾼 이유" 를 아래에 덧붙인다.
