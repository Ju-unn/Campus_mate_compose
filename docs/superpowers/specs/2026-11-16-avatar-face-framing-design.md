# 아바타 얼굴 구도 맞추기 설계 (2026-11-16)

## 1. 왜

2026-11-16 운영 실제 가입자 1명의 아바타에서 얼굴이 안 보였다. 원본이 전신 사진이라 아바타(1024×1536)도 전신으로 나왔고, 얼굴이 그림 위쪽 약 9~17% 높이에 작게 있었다. 앱은 아바타를 모든 자리에서 `BoxFit.cover` **가운데 자르기**로 보인다 — 원(채팅 목록 · 대화 · 수락 줄 · 차단 목록 · 지인 리뷰), 카드 요약 96×96, 상대 프로필 자세히 보기 머리(286×260), 홈 모자이크 112×140, 내 프로필 머리. 그래서 원과 자세히 보기 머리 모두 얼굴이 잘렸다.

사용자 말: 「앱을 고쳐도 앱 안에 가운데 위쪽으로 하면, 아래에 있으면?? 또 고쳐야하잖아」 → 앱의 자르는 기준을 옮기는 것으로는 안 된다. **어떤 사진이 들어와도 아바타 속 얼굴이 늘 같은 자리 · 비슷한 크기**여야 한다.

사용자 말: 「현재 mlkit이나 cloud vision이나 쓰고 있는거에 방법은 없는지 부터 파악하고」 → 아래 2절.

## 2. 이미 쓰는 것으로 되는가 (조사 결과)

| 이미 쓰는 것 | 하는 일 | 이번에 쓸 수 있나 |
| --- | --- | --- |
| 앱 ML Kit (`frontend/lib/auth/media/model/repository/face_detector.dart`) | 기기 안에서 얼굴 유무 · 얼굴 폭 ÷ 사진 폭만 잰다. 1.0.4 부터 15% 미만이면 막는다(#745). 얼굴 위치는 서버로 보내지 않는다 | **아니오.** 앱 업데이트가 있어야 하고, 스토어의 1.0.3 사용자에게는 안 닿는다 |
| 서버 Cloud Vision (`backend/app/core/deps.py` `_vision_client`) | 사진 올릴 때 부적절 · 문서 검사(`profile_onboarding/photos.py` `check_photo` — SAFE_SEARCH · TEXT · LABEL), 졸업증명서 글자 읽기 | **예.** 같은 클라이언트 · 같은 API 에 `FACE_DETECTION` 기능이 있어 얼굴 상자를 준다. 새 의존성 · 새 키 · 새 권한이 없다(아바타 워커도 같은 Cloud Run 서비스 · 같은 서비스 계정에서 돈다) |
| 서버 Pillow (`pillow>=13`, `cards/paid_preview.py` 가 이미 씀) | 그림 자르기 · 줄이기 | **예.** 자르기에 쓴다 |

결론: **새 부품 없이 서버만 고친다.** Vision 으로 원본 사진의 얼굴을 찾고, Pillow 로 원본을 정해진 구도로 자른 뒤, 그 사진으로 지금처럼 아바타를 만든다.

단, 개인정보 처리방침(2026-11-20 시행판)과 어긋난다 — 제2조 바 "사진에 얼굴이 있는지 확인하는 검사(기기 안에서만 처리하고 서버로 보내지 않습니다)", 제6조 Cloud Vision 행의 목적 "유해 이미지·글자·라벨 검사" · 시점 "실사진을 올리거나 바꿀 때마다". 그래서 처리방침을 같이 고친다(8절). 지시문만 바꿔 AI 가 머리·어깨로 그리게 하는 길(방침 변경 없음)도 견줘 봤지만 얼굴 자리를 보장할 수 없어 버렸다 — 사용자 「확실하게 해야해」.

## 3. 목표 · 하지 않을 것

**목표**
- 얼굴이 찾아진 원본은 아바타 속 얼굴이 늘 "머리와 어깨 · 가슴 위" 구도, 비슷한 높이 · 크기로 나온다.
- 앱의 지금 가운데 자르기(원 · 96×96 · 286×260 · 112×140)에서 얼굴이 다 보인다. **앱은 고치지 않는다.**
- 서버 배포만으로 1.0.3 · 1.0.4 사용자 모두에게 적용된다.
- 새로 만드는 아바타를 PNG(운영 평균 1.2MB · 최대 3.6MB) 대신 JPEG 로 저장해 크기를 약 1/7 로 줄인다(4.3절). 사용자 「이번에 같이 하고, 노션에 기술결정사항에 적어줘」.

**하지 않을 것**
- 앱 수정, DB 스키마 변경, 새 설정 값(env) 추가.
- 아바타 지시문(`_STYLE_PROMPT`) 수정 — 7절 "원본 구도를 지켜라"를 그대로 이용한다. 지시문은 시험을 다시 돌려야 바꿀 수 있는 값이다(`avatars.py` 주석).
- 이미 만들어진 아바타 다시 만들기 — 실제 가입자 아바타는 사용자에게 따로 묻고 하나씩 한다.
- 프로필 사진(아바타 원본이 아닌 사진 · 원본 파일 자체) 바꾸기 — 자른 사진은 생성 요청에만 쓰고 저장하지 않는다.

**실패로 볼 것(돌아가도 안 되는 것)**
- 얼굴 찾기가 실패했을 때 아바타 생성이 실패하는 것 → 반드시 원본 그대로 만든다(지금 동작).
- 아바타 실패 횟수(5회 → 기본 아바타 + 하트 10)에 얼굴 찾기 실패가 섞이는 것.

## 4. 동작

아바타 워커(`backend/app/profile_onboarding/tasks_router.py` `generate_avatar_task`)의 (3) 생성 바로 앞에 한 단계를 넣는다. 온보딩 첫 생성과 "다시 만들기"(`me/router.py` → `enqueue_avatar_attempt`)가 모두 이 워커를 지나므로 한 곳만 고치면 된다.

```
원본 다운로드 → [새] 얼굴 기준 구도 맞추기 → AvatarGenerator.generate(맞춘 사진) → 기록
```

### 4.1 구도 맞추기 단계 (`frame_on_face`)

1. 원본을 Pillow 로 연다. EXIF 회전을 픽셀에 반영한다(`ImageOps.exif_transpose`). RGB 로 바꾼다.
2. 그 **회전 반영한 그림**을 JPEG 로 다시 써서 Vision `FACE_DETECTION` 에 보낸다 — Vision 좌표와 자를 그림의 방향이 반드시 같게 하려는 것이다.
3. 얼굴 고르기: 확신도(`detection_confidence`) 0.5 이상인 얼굴 중 상자(`bounding_poly`) 넓이가 가장 큰 것 하나. 없으면 원본 그대로.
4. 자를 상자 계산(5절의 값). 상자가 그림 전체와 같거나 높이가 240 화소보다 작으면(아주 작은 얼굴) 원본 그대로 — 1차 시험에서 본 가장 작은 입력이 160×240(아래 ⑤)이라 그보다 작은 그림은 생성기에 넘기지 않는다.
5. 잘라서(위 빈칸이 있으면 채워서) JPEG(품질 95)로 돌려준다. 키우거나(업스케일) 줄이지 않는다 — 1차 시험에서 160×240 화소까지 작은 입력도 모델이 쓸 만하게 그렸다.

**어떤 예외든**(Vision 오류 · 인증 실패 · 시간 초과 · 그림을 못 여는 형식 · 계산 오류) 잡아서 **원본 바이트를 그대로** 돌려주고 경고 로그 한 줄을 남긴다. 로그에는 수와 참거짓만(얼굴 수 · 얼굴 높이 비율 · 잘랐는지 · 오류 종류 이름) — 이미지 · 경로 · 좌표 · profile_id 는 남기지 않는다(COMMON §3).

Vision 호출에는 시간 제한 10초를 둔다(워커는 큐에서 240초에 끊긴다 — 생성 시간을 빼앗지 않게). 호출의 `timeout=` 은 한 번 시도의 시간일 뿐이고 라이브러리 기본 재시도가 최대 600초까지 다시 부르므로, 호출 전체를 `asyncio.wait_for` 10초로 묶는다(검토에서 찾음 — 닫힌 포트로 재현하면 30초가 지나도 안 돌아왔다).

클라이언트는 `get_vision_client_factory`(만드는 함수)로 받는다 — 졸업생 OCR 과 같은 이유로, 인증 실패(GoogleAuthError)도 이 단계의 try 안에서 잡혀 원본으로 넘어가야 한다.

### 4.2 아바타 저장 형식 (JPEG)

`AvatarGenerator.generate` 가 OpenAI 가 준 PNG 를 저장하기 전에 RGB JPEG(품질 90)로 바꿔 `{profile_id}/{uuid}.jpg` · `image/jpeg` 로 올린다. 11-16 운영 아바타 1장으로 잰 값: PNG 2,293KB → JPEG 90 298KB, 얼굴 부분 2배 확대에서도 차이가 안 보였다.
- 바꾸기가 실패하면(그럴 일은 드물다) PNG 그대로 올린다 — 그림을 잃지 않는 쪽이 낫다. 생성 실패로 세지 않는다.
- 읽는 쪽은 형식을 가리지 않는다: 앱(주소로 받음), 홈 레일 · 유료 카드 미리보기(Pillow 로 연다), 관리자 웹(주소). `avatars` 버킷은 형식 제한이 없다(운영 조회 11-16). 기본 아바타(`defaults/fallback-avatar.png` 복사)는 그대로 PNG 다.
- 이미 만든 아바타(운영 39개)는 바꾸지 않는다.

### 4.3 이 단계가 아닌 것

- 사진 올릴 때 하는 `check_photo` 는 그대로 둔다. 거기서 얼굴 상자를 같이 받아 저장하는 길은 DB 칸이 필요해서 택하지 않았다. 생성은 사람당 몇 번뿐이라 생성 때 한 번 더 부르는 값(Vision 1건, 월 1,000건 무료 뒤 1,000건당 1.5달러)은 작다.

## 5. 구도 값 (시험 생성 2차로 정한 값)

출력 아바타가 1024×1536(가로:세로 2:3)이므로 **자르는 상자도 2:3** 으로 맞춘다. 모델이 지시문 7절대로 구도를 지키면 아바타도 같은 구도가 된다.

| 이름 | 값 | 뜻 |
| --- | --- | --- |
| `FACE_HEIGHT_RATIO` | 0.25 (1차 0.30) | 얼굴 상자 높이 ÷ 자른 상자 높이 |
| `FACE_CENTER_Y` | 0.45 (1차 0.38) | 얼굴 상자 가운데가 자른 상자 위에서 몇 % 아래에 오는가 |
| `MAX_TOP_PAD` | 0.30 (2차에 추가) | 머리 위에 사진이 모자랄 때 위를 빈칸으로 채울 수 있는 최대 비율(자른 높이 대비) |
| `ASPECT` | 2/3 | 자른 상자 가로 ÷ 세로(출력 크기와 같다) |
| `MIN_CONFIDENCE` | 0.5 | 이보다 낮은 얼굴은 무시 |
| `MIN_CROP_HEIGHT` | 240 (검토 뒤 추가) | 자른 높이가 이보다 작으면 원본 그대로 |

계산:
- 바라는 높이 `H = 얼굴높이 ÷ FACE_HEIGHT_RATIO`. 그림 안에 들어가는 2:3 상자의 최대 높이 `Hmax = min(그림 높이, 그림 폭 × 3/2)` 보다 크면 `Hmax` 로 줄인다(얼굴이 이미 큰 셀카 — 더 넓게 볼 화소가 없으니 들어가는 만큼만).
- 폭 `W = H × 2/3`.
- 위치: 위 = 얼굴 가운데 y − `FACE_CENTER_Y` × H, 왼쪽 = 얼굴 가운데 x − W/2. 옆 · 아래로 나가면 안쪽으로 민다(상자 크기는 그대로).
- 위로 나가면 `MAX_TOP_PAD × H` 까지는 그대로 두고 그 칸을 사진 맨 위 띠(자른 상자 폭, 높이는 위 빈칸을 뺀 사진 안쪽 부분 높이의 1/20)의 평균 색으로 채운다 — 생성 모델이 배경으로 그려 넣는다. 더 나가면 민다. **그림 높이를 다 쓰는 상자**(`H = 그림 높이`, 얼굴이 큰 세로 셀카)는 채우지 않는다(아래를 잘라 빈 띠를 붙일 뿐이라). 폭이 모자라 `H = 그림 폭 × 3/2` 로 줄어든 상자(예: 9:16 셀카)는 그림 높이보다 작으니 위를 채울 수 있다 — 얼굴이 45% 자리에 오므로 그쪽이 낫다.
- 자른 높이가 `MIN_CROP_HEIGHT` 보다 작으면 자르지 않는다.
- 좌표는 정수 화소로 반올림한다.

값을 고른 근거(앱 가운데 자르기에서 보이는 세로 띠):
- 상대 프로필 머리 286×260 → 그림 높이의 약 19.7% ~ 80.3%
- 원 · 96×96(정사각) → 16.7% ~ 83.3%
- 모자이크 112×140(4:5) → 8.3% ~ 91.7%

얼굴 상자 가운데 45%, 높이 25% 면 얼굴은 32.5% ~ 57.5% 에 놓이고 머리카락까지 세 띠 안에 든다. 정사각 원 안에서 얼굴 높이는 지름의 약 37% 다.

얼굴이 그림 옆 가장자리에 있으면 상자를 안으로 밀기 때문에 얼굴이 가운데에서 벗어날 수 있다 — 받아들인다.

### 5.1 시험 생성 결과 (2026-11-16, 로컬에서 운영과 같은 Vision · OpenAI 호출)

시험 사진: 실제 가입자 1장(사용자 지시 「이거 실제 사진 다운해서 테스트 진행 사진에 포함시켜서 해줘」 — 로컬 임시 폴더에만, 작업 뒤 지움), 가상 인물 5장(셀카 2 · 허리 위 1 · 벤치에 앉은 전신 1 · 복도에 선 전신 1, 가상 전신 3장은 이번에 생성).

- **1차(0.30 · 0.38, 빈칸 없음)**: 원 · 카드 요약 · 모자이크는 모든 사진에서 얼굴이 보였다. **자세히 보기(286×260)는 실제 사진 · 복도 사진에서 이마와 머리가 잘렸다** — 실제 사진은 머리가 원본 맨 위에 붙어 있어 위로 넓힐 화소가 없었고(얼굴 가운데가 20% 에 머묾), 모델이 머리를 조금 키우고 올려 그리는 경향도 있었다. "최소 자르기 크기"(512px) 변형은 얼굴만 작아져 버렸다.
- **2차(0.25 · 0.45 · 위 빈칸 최대 30%)**: 실제 사진 2번 생성 모두 **네 화면에서 얼굴 전체가 보였다.** 위에 붙인 단색 칸은 모델이 벽 · 배경으로 그려 흔적이 없었다. 가상 전신 2장도 네 화면에서 얼굴이 보였다.
- 얼굴이 이미 큰 사진(셀카 · 허리 위)은 상자가 그림 전체에 가까워 결과가 지금과 같았다.
- **한계**: 얼굴이 사진 폭의 6~7% 인 가상 전신 사진에서 모델이 없는 안경을 그려 넣은 적이 있다(화소 부족). 이런 사진은 앱 1.0.4 의 얼굴 크기 검사(폭 15% 미만 거절, #745)가 막는다. 실제 사진(얼굴 폭 약 28%)에서는 없었다.
- 비용: 이미지 생성 17장(가상 원본 3 · 아바타 14) 약 $1.2, Vision 은 무료 범위.

## 6. 시험

**코드 시험(pytest, 외부 호출 없음)**
- 상자 계산: 작은 얼굴이 가운데 있는 전신 사진 → 2:3 상자, 얼굴 높이 비율 · 가운데가 표의 값. 얼굴이 왼쪽 · 오른쪽 · 아래 가장자리 → 상자가 그 가장자리에 붙고 그림 안에 있다. 머리가 위 끝 → 위 빈칸이 한도 안. 얼굴이 큰 셀카 → `Hmax` 상자, 빈칸 없음. 상자가 그림 전체와 같으면 자르지 않음. 아주 작은 얼굴(자른 높이 240 미만) → 자르지 않음.
- `frame_on_face`: 얼굴 없음 → 원본 바이트 그대로. Vision 이 오류를 냄 · 예외 · 클라이언트 만들기가 실패함 · Vision 이 답하지 않음(시간 제한) → 원본 그대로. 확신도 낮은 얼굴만 있음 → 원본. 얼굴 여러 개 → 가장 큰 얼굴 기준(가장 큰 얼굴을 가운데 두어 "처음" · "마지막" 고르기를 잡는다). EXIF 회전된 JPEG → 회전 반영한 그림을 Vision 에 보냄. 위 빈칸은 맨 위 띠 색. 그림이 아닌 바이트 → Vision 을 부르지 않고 원본.
- 워커: 생성기에 자른 바이트가 넘어간다. 얼굴 찾기가 실패해도 원본으로 생성 · 기록된다.
- 저장: 완성 그림이 JPEG · `.jpg` · `image/jpeg` 로 올라간다. 바꿀 수 없는 바이트면 PNG 그대로.

**시험 생성(실제 Vision + 실제 OpenAI, 비용 발생 — 사용자 허락 11-16 「설계하고 진행해줘」 · 「일단 실험부터 해보자」)** — 결과는 5.1절. 결과 그림은 저장소 밖 로컬 임시 폴더에 두고, 노션 기술 결정에는 가상 인물 그림만 싣는다.

**배포 시험**
- 지금 main 의 서버 코드는 운영 00126-noy(10f6d0d5) 이후 문서만 바뀌었다 — 새 리비전에 들어가는 서버 변경은 이 기능뿐이다.
- 트래픽 0% 시험 주소에 먼저 올린다. 시험 주소는 Cloud Tasks 가 부르지 않으므로(작업 URL 은 운영 주소) 시험 주소의 워커를 직접 부르는 시험은 하지 않는다. 대신 위 시험 생성이 실제 Vision · OpenAI 조합을 확인한다. 0% 단계에서는 서버가 정상 기동하는지(health)와 기존 엔드포인트가 그대로인지 본다.
- 100% 전환 전에 사용자에게 묻는다. 전환 뒤 테스트대학 계정으로 아바타 하나를 만들어 로그에 "구도 맞춤" 줄이 찍히고 결과가 맞는지 본다.

## 7. 되돌리기 · 위험

- 되돌리기는 이전 서버 리비전으로 트래픽을 돌리는 것뿐이다(데이터 변경 없음).
- 위험: 모델이 잘린 사진을 "다시 넓히는" 경우 → 시험 생성에서 확인한다. 잘린 원본이 작으면(전신 사진 속 작은 얼굴) 아바타 얼굴 부분의 원본 화소가 적다 — 아바타 얼굴은 점 · 선이라 영향이 작다고 보지만, 시험에서 머리 · 옷 표현이 뭉개지면 값(`FACE_HEIGHT_RATIO`)을 낮춰 더 넓게 자른다.
- 비용: 생성마다 Vision 1건 추가. 생성 비용(장당 약 $0.07)에 비해 작다.
