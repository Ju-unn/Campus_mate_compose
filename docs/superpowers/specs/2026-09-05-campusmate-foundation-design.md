## 1. 제품 개요

대학생·대학원생 전용 소개팅 애플리케이션.
학교 이메일로 학생임을 인증하고, 성향·관심사·자기소개를 벡터로 변환해
**지급일 아침 가장 잘 맞는 상대 한 명**을 카드로 제공한다(지급 주기는 가변, 2.1절 참조).

### 1.1 왜 스와이프가 아니라 소수 큐레이션 카드인가

**콜드스타트 문제가 제품 구조로 해결된다.**
스와이프는 화면을 채우려면 후보가 수십 명 있어야 하지만, **소수 큐레이션 카드는 후보가 1명만 있어도 성립한다.**
소개팅 앱이 실패하는 가장 흔한 원인인 "들어갔더니 사람이 없다"를 정면으로 피한다.

**지급 주기 자체도 콜드스타트에 맞춰 가변으로 둔다.** 초기에는 후보 풀이 얇으므로 **주 2회(월·목)**로 시작하고, 지역그룹별 활성 사용자 수가 늘어나면 단계적으로 지급 빈도를 늘린다(정확한 임계치는 13장 미결 항목). 매일 지급을 기본값으로 못박지 않는 이유는, 사람이 적은 상태에서 매일 카드를 돌리면 같은 후보가 반복 소진되어 오히려 카드 품질이 떨어지기 때문이다.

부수 효과로, **벡터 매칭의 품질이 곧 제품 품질이 된다.**
상위 20명을 뽑을 때는 순위가 조금 틀려도 티가 안 나지만, **상위 1명만 뽑으면 알고리즘이 전부**다.

### 1.2 남은 최대 위험

**성비 불균형**이다. 출시 전까지 대응 방침을 정해야 한다 (13장 미결 항목).

## 2. 제품 규칙 (핵심 동작)

### 2.1 카드 지급

| 규칙           | 내용                                                                                                                                                           |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 지급 시각      | 지급일**아침 7시** — 초기에는 **주 2회(월·목)**, 지역그룹별 활성 사용자 수 증가에 따라 단계적으로 확대(3회→4회→…, 최종 상한은 13장 미결 항목) |
| 지급량         | **성별 무관 1장**                                                                                                                                        |
| 지급 방식      | 서버 배치(`pg_cron`)가 생성하고 **푸시 알림으로 통지**                                                                                                 |
| 지급 주기 조정 | `region_group_settings`(가칭) 같은 작은 설정 테이블 값만 바꿔 조정 — 코드 배포·관리자 화면 없이 대시보드에서 직접 수정                                     |
| 추가 카드      | **단건 결제로 즉시 1장 더** (50하트, §2.4)                                                                                                       |
| 재등장         | **거절한 상대는 다시 나오지 않는다**                                                                                                                     |

**채팅 개수로 카드 지급을 막는 규칙은 두지 않는다.** 대신 매칭 성사 후에는 2.5절의 "신뢰 확인 게이트"가 방치된 대화를 자연스럽게 정리하므로, 채팅이 쌓인다고 카드 지급까지 막을 이유가 없다.

### 2.2 수락 흐름

```
① A가 오늘의 카드에서 B를 수락
② B에게 알림 — "누군가 당신을 수락했습니다"
③ B가 "받은 수락함"에서 A의 프로필을 확인
④ B도 수락 → 매칭 성립 → 채팅 시작
   B가 거절 → 조용히 종료 (A에게 거절 사실을 알리지 않는다)
```

**한쪽 수락을 상대에게 알리는 이유**: B의 오늘 카드에 A가 없더라도 A를 보게 되므로 **매칭률이 크게 오른다.**
카드를 한 번에 소수만 지급하는 구조에서는 서로의 카드가 겹칠 확률이 낮아 이 경로가 필수적이다.

**거절 사실은 알리지 않는다.** 명시적 거절 통지는 사용자를 앱에서 떠나게 만든다.

### 2.3 카드를 다 쓴 뒤의 화면

- 오늘의 카드가 소진되면 **모자이크 처리된 프로필들이 배너로 보인다**
- "다음 카드는 O월 O일 아침 7시에 도착합니다" 카운트다운 (지급일이 매일이 아니므로 고정 문구가 아니라 다음 지급일을 계산해서 보여준다)
- **추가 카드 구매 버튼**

### 2.4 수익 모델

**현재 수익 모델은 하트(재화) 판매다**(2026-09-08 등록비 폐지, §13-17): 가입비 없음(남녀 동일 무료), **하트 1개 = 60원(2026-09-14, DESIGN.md §13-114·§13-115)**, 추가 카드 50하트(지급 주기당 1장), 아바타 재생성 10하트(최초 1회 무료) — 상세는 DESIGN.md §8.10.

| 단계           | 내용                                 | 금액                              |
| -------------- | ------------------------------------ | --------------------------------- |
| 이용           | 가변 주기 카드, 채팅 무제한          | 무료                              |
| 소모품         | 추가 카드 50하트 · 아바타 재생성 10하트 | 하트 단가 60원 기준(2026-09-14) |
| 구독           | **도입하지 않는다**            | —                                |

**하트(재화)가 이제 유일한 수익원이다.** 매칭·카드 조회·채팅 등 핵심 기능은 여전히 하트 없이 전부 이용 가능하다. 하트 소비처는 **추가 카드와 아바타 재생성 둘뿐**이며, 어느 쪽도 매칭 품질에 영향을 주지 않는다.

#### 하트 가격 정책 (2026-09-14 확정, DESIGN.md §13-114·§13-115)

**기준 단가는 하트 1개 = 60원**이다(종전 40원에서 2026-09-14 개편). 800하트 티어가 신설됐고 할인 상한이 15%→20%로 상향됐다:

| 하트 | 원가(취소선) | 판매가 | 개당 단가 | 할인 |
|---|---|---|---|---|
| 50 | 표기 없음 | 3,000원 | 60.0원 | 표기 없음 |
| 100 | 6,000원 | 5,700원 | 57.0원 | 5% (**추천 배지**) |
| 200 | 12,000원 | 10,800원 | 54.0원 | 10% |
| 400 | 24,000원 | 20,400원 | 51.0원 | 15% |
| 800 | 48,000원 | 38,400원 | 48.0원 | 20% (신설 티어) |

- **최소 번들이 정확히 카드 1장치다.** 경쟁사는 전부 최소 번들을 여러 번치로 묶어 잔액을 남기는데, 이걸 하지 않는 것이 DESIGN.md §8.10 정직함 원칙과 맞고 차별점이 된다
- **할인 상한이 20%로 상향됐다(2026-09-14).** 800 신설로 추가 카드 16장치를 한 번에 팔게 되며 미사용 잔액 위험이 있음을 결정 전 사용자에게 고지했다
- "추천" 배지는 가장 큰 번들이 아니라 **100하트(2장치)** 에 붙인다
- **원가 취소선 병기가 허용됐다(2026-09-14, 종전 "취소선 할인가 금지" 원칙을 절반 개정).** 실시간 카운트다운 배너는 계속 금지
- 경쟁사 대비 위치: 썸타임 좋아요 1회가 약 2,976원, 캠퍼스팅 하트 1개가 약 220원이다. CampusMate 추가 카드(50하트=3,000원)는 **행동 단가 기준으로 경쟁사보다 명확히 싸다**

#### 사는 것과 쓰는 것을 분리한다 (2026-09-08 확정)

**결제는 막지 않고, 여는 횟수만 제한한다.** 원래는 "카드 지급일 당일에만 추가 카드를 살 수 있다"였는데, 이건 리듬을 지키는 대신 결제 자체를 막는 규칙이었다. 사고 싶은 순간(카드를 다 보고 아쉬운 순간)과 살 수 있는 순간이 어긋나면 리듬은 그대로인데 매출만 사라진다.

| 항목 | 규칙 |
|---|---|
| 하트 구매 | 제한 없음. 언제든, 원하는 만큼 |
| 추가 카드 구매·열기 | **지급 주기당 1장.** 다음 카드가 오기 전까지 언제든 |
| 구매한 카드의 수명 | **만료 없음.** 수락·거절을 누를 때까지 유지 |
| 무상 카드의 수명 | 다음 지급 때 만료. **무응답으로 만료된 경우에만 상대가 재노출 대상으로 복귀한다. 수락·거절한 상대, 매칭 이력이 있는 상대는 영구 제외**(2026-09-13 확정, ERD.md §11-4 · §6.7 하드 필터 정의) |

- **상한 총량은 이전과 같다.** 주 2회 지급이면 월 8~9장으로, 지급일 당일 제한이 있던 때와 동일하다. 무료 하트로 얻는 월 4~5장을 빼면 결제 여지는 3~4장으로 유지된다 — **창구만 넓혔고 천장은 그대로다**
- **갱신 직전 구매가 증발하면 안 된다.** 갱신 한 시간 전에 산 카드가 한 시간 만에 사라지면 그건 기능이 아니라 결제 사고다. 구매한 카드는 **결정 대기 큐**(DESIGN.md §8.9)에 남는다. **오늘의 카드 화면 노출 순서(2026-09-14 사용자 결정, DESIGN.md §13-96 — 종전 "구매 카드 먼저"를 뒤집음)**: 위에서부터 [이번 주기 무료 카드 → 이번 주기 잠금 카드 → 이전 주기에 산 카드(결정 전까지 쌓임)] 순서로 노출한다. 결정 대기 중에도 추가 구매를 계속 허용하며, 이번 주기에 새로 산 카드는 잠금 카드 자리에 열리고 그 주기엔 잠금 카드가 다시 노출되지 않는다
- **결제 전에 고지한다.** 하트 스토어와 결제 확인 시트 양쪽에 "다음 카드가 올 때까지 한 장만 열 수 있어요 / 산 카드는 결정할 때까지 사라지지 않아요" 두 문장을 고정 노출하고, 옆에 FAQ 진입점을 둔다. 상한이 있는 재화를 팔면서 결제 후에 알리는 것은 환불 분쟁과 스토어 심사 양쪽에서 지는 방식이다

**구독제를 넣지 않는 이유**: 구독은 매달 새로운 가치를 제공해야 성립한다.
초기에는 사용자가 적어 그 가치를 줄 수 없고, "구독했는데 만날 사람이 없다"는 환불 요구로 이어진다.
사용자 규모가 확보된 뒤 재검토한다.

**채팅 횟수 제한은 두지 않는다.** 대화가 중간에 끊기면 돈을 내지 않은 쪽뿐 아니라
**상대방의 경험까지 망가진다.** 대신 매칭 앞단(카드 지급)도 채팅 개수로 막지 않고, 매칭 뒤에는 2.5절의 신뢰 확인 게이트가 방치된 대화를 정리하는 역할을 대신한다.

#### 가입비 폐지 결정 기록 (2026-09-08)

원래는 등록비(남 9,900원 / 여 0원, 가입 1회 결제)를 받는 모델이었다. 성별 차등 자체가
민원·논란 소지가 있고, 인앱결제 상품·가격이 스토어에 공개 등록되는 이상 숨길 수도 없어
**성별 차별 문제를 원천적으로 없애기로 하고 가입비를 완전히 폐지했다.** 대신 수익은
이미 확정돼 있던 하트 이코노미(DESIGN.md §8.9·§8.10, 주기당 1장 초과 카드 = 50하트)로 단일화한다 —
새로운 과금 시점(예: 매칭 성사 시 재화 차감)은 만들지 않는다. 가입 플로우 자체가 더는
결제를 포함하지 않으므로, DESIGN.md 화면 9 "등록비 결제"(`purchase-sheet`)는 폐기한다.

**프로모션 코드는 별도 목적으로 유지한다.** 성별 차등을 우회하기 위한 용도가 아니라
(가입비 자체가 없으므로 그 목적은 소멸했다), 이벤트·마케팅용 범용 코드(예: 코드 입력 시
무료 하트 지급)로 남긴다. 발급 규칙(1코드=1계정, 발행량 상한 등)은 실제 이벤트 설계 시점에 정한다.

### 2.5 매칭 후 신뢰 확인 게이트 (경쟁사 조사 반영, 신규)

매칭 성사만으로는 "진지하게 대화할 의사"가 검증되지 않는다. 그래서 채팅 시작 후 일정 시점에 한 번, 서로 계속 대화할 의사가 있는지 확인하는 절차를 둔다.

**48시간 응답 기한은 매칭 성립 시점(`matches.created_at`)부터 계산한다**(24시간 뒤 추가로 시작되는 별도 기한이 아니다, 2026-09-13 확정 — ERD.md §11-6).

```
매칭 성립(채팅 시작, 48시간 기한 시작) → 24시간 경과, 아직 응답 안 한 상태로 채팅방 진입 시마다 다이얼로그 노출
                        (+ 24시간 시점에 푸시 알림 발송)
→ 매칭 성립 후 48시간 응답 기한 안에 양쪽 모두 수락
    → 카카오톡 아이디 자동 공유 + 실사진 공개, 앱 내 채팅은 계속 병행 유지
→ 48시간 안에 한쪽이라도 거절(또는 무응답)
    → 48시간 후 채팅 삭제. 매칭 기록은 남기고 채팅만 닫는다(재노출 악용 방지).
      거절 사실은 상대에게 알리지 않는다(2.2절 원칙과 동일)
```

**48시간은 이 다이얼로그의 응답 기한일 뿐, 대화 전체를 상시 감시하는 규칙이 아니다.** 게이트를 통과한 뒤의 채팅은 자동 만료 없이 계속 열려 있으며, 필요하면 사용자가 직접 "채팅방 나가기"로 조용히 종료할 수 있다(상대에게 알리지 않음, 2.2절과 동일 톤).

**카카오톡 아이디는 가입 온보딩(`04-1b`)에서 필수로 받는다**(2026-09-14 사용자 결정, DESIGN.md §13-91 — 종전 "이 다이얼로그 시점에 입력" 안을 뒤집음). `profile_private.kakao_id`(ERD.md)에 저장해두고, 이 다이얼로그(신뢰 확인 게이트)는 **저장된 아이디를 보여주고 "변경" 진입점만 제공**한다 — 매칭 전 카드/수락함 응답에 이 값을 포함하지 않는다는 원칙(7.1절)은 그대로 유지한다.

**이 게이트는 기존의 "채팅 5개 동시 상한"을 대체한다.** 상한을 없애 채팅을 무제한으로 열어주는 대신, 이 게이트가 서로 대화 의사가 없는 매칭을 자연스럽게 걸러내는 역할을 한다.

**상대가 탈퇴하면 게이트를 통과시키지 않는다.** 이미 게이트를 통과한 매칭에서도 탈퇴자의 카카오톡 아이디·실사진은 더 주지 않는다(§2.6, ERD.md §11-15). **"매칭 기록은 남긴다(재노출 악용 방지)"는 재가입한 계정에는 적용되지 않는다** — 새 계정에는 이 기록에 따른 재노출 방지가 걸리지 않는다(알려진 한계, ERD.md §11-17).

### 2.6 계정 상태 관리 — 일시중지 · 탈퇴 · 재가입 (2026-09-08 신규, 경쟁사 비교 그릴링)

**매칭 일시중지 토글.** 나의정보(설정) 화면에 온/오프 토글을 둔다. 꺼두면 새 카드 배치 대상에서 제외되고(조각 4 카드 배치 쿼리에서 제외), 기존 매칭·채팅은 그대로 유지된다. 탈퇴와 달리 데이터는 삭제되지 않는다. 휴학·시험기간처럼 카드만 잠시 멈추고 싶은 사용자를 위함(연픽 "매칭 활성화" 토글, 클럽트웬티 "일시중지" 벤치마킹).

**탈퇴 절차.** 클럽트웬티 패턴을 따른다: 설정 → "탈퇴하기" → 확인 화면(삭제되는 항목을 구체적으로 안내 — 프로필·매칭 기록·채팅·쓴/받은 지인 리뷰·투표 글과 표·남은 하트 전부, "30일 뒤 완전 삭제"와 "결제 내역은 법에 따라 보관"을 명시, **탈퇴는 되돌릴 수 없음을 함께 안내**) → "영구 삭제" 버튼(위험 액션이므로 이중 확인) → **즉시 숨김·로그인 차단, 30일 뒤 계정 전체를 완전 삭제**(ERD.md §11-15). 보관 목적은 신고·분쟁 대응이다.

- **예외.** 검증이 끝나지 않은 학생증 사진(`student-id-temp`)은 탈퇴 즉시 삭제한다. 실명·전화번호·카카오톡 아이디(`profile_private`)는 30일 보관한다. 결제 내역(`purchases`)은 구매자 식별 없이 5년 보관한다(§2.6 FK 규칙 문단, ERD.md §11-14·§11-19).
- **30일 동안.** 게이트를 통과한 매칭만 남은 상대가 채팅을 읽고 신고할 수 있다(메시지는 보낼 수 없다). 게이트를 통과하지 않은 매칭은 기존 규칙대로 48시간 기한에 게이트 실패로 닫힌다. 푸시 토큰(`push_tokens`)은 탈퇴 즉시 삭제한다.
- **되돌리기.** 탈퇴는 되돌릴 수 없다(ERD.md §11-21 확정). 30일 보관은 계정을 되살리기 위한 유예가 아니라 신고·분쟁 대응 목적이다.

화면은 DESIGN.md §9에 신규 추가한다.

**FK 규칙(ERD.md §2·§11-11), 30일 뒤 계정 삭제 때 적용.** `profiles`를 가리키는 FK와, 탈퇴로 지워지는 행을 가리키는 하위 FK 5개(`card_decisions.card_id`·`acceptance_responses.card_id`·`match_participants.match_id`·`messages.match_id`·`poll_votes.poll_id`)는 `on delete cascade` — 탈퇴하면 그 사람이 쓴 지인 리뷰·투표 글도 지워지고, 투표 글이 지워지면 달린 표도 함께 지워진다. 받은 사람의 지인 리뷰도 작성자가 탈퇴하면 사라진다. 예외는 `reports.reporter_id`(신고 근거 보존), `profile_avatars.source_photo_id`(set null), `purchases.profile_id`(set null, 구매자 식별만 지우고 5년 보관 — ERD.md §11-14). `heart_transactions`는 예외 없이 함께 삭제된다.

**재가입 제한 검사.** `signup_blocks`는 FastAPI HTTP Auth Hook이 학교 메일 도메인 화이트리스트와 함께 검사한다(§7.3).

**재가입 제한 — 탈퇴 후 2개월(확정, 2026-09-08).** 같은 대학 이메일로 2개월간 재가입을 막는다(클럽트웬티 사례와 동일). 탈퇴-재가입 반복으로 신고 이력을 세탁하거나 매칭 큐를 도는 악용을 막기 위함. 2개월로 정한 근거는 악용 차단에 충분하면서 정당한 복귀를 과도하게 막지 않는 선이라는 것이다. **2개월은 탈퇴 요청 시각부터 센다**(계정이 실제로 지워지는 30일 뒤 시점이 아니다, ERD.md §11-17). **정지(suspended) 중 탈퇴는 다르다 — 같은 학교 메일로는 기간 없이(무기한) 재가입을 막는다**(ERD.md §11-22). 다른 학교 메일로 우회 가입하는 경우까지는 막지 못하며, 이는 알려진 한계다. **잠시 쉬고 싶은 사용자에게는 탈퇴 대신 매칭 일시중지 토글을 안내한다** — 탈퇴 확인 화면에서 일시중지를 먼저 제시한다.

### 2.7 추천인 프로그램 (2026-09-08 신규, 경쟁사 비교 그릴링)

연픽의 "추천 코드 즉시 보상 + 월간 랭킹 시상"을 벤치마킹해 정식 추천인 프로그램을 도입한다.
가입비가 없어졌으므로 현금성 보상은 하지 않고 전부 하트(재화)로 지급한다.

- 가입 시 개인 추천 코드 1개를 자동 발급한다
- 신규 가입자가 가입 시 코드를 입력하면 **추천인 + 피추천인 양쪽에게 각각 50하트(카드 1장치)를 즉시 지급**한다 (2026-09-08 확정)
- 월간 랭킹(추천 성사 건수 기준) 상위 N명에게 추가 하트를 보상한다 — 상위 인원수와 보상량은 첫 코호트 운영 데이터를 보고 정한다. **집계는 `referrals` 기준이고, 탈퇴 계정의 cascade 삭제로 지난달 행이 줄어들 수 있어 월말에 순위를 확정해 지급한다**(2026-09-13, ERD.md 읽는 법·§3)
- **양쪽 50하트로 정한 근거**: 신규 가입자 1명 확보에 4,000원어치를 쓰는 셈인데, 소개팅 앱 실제 사용자 확보비가 보통 1만 원을 넘으므로 여전히 싸다. 보상이 정확히 카드 1장이라 체감도 명확하다
- 어뷰징 방지(자기추천·대포 계정)는 조각 7에서 구현한다 — 동일 기기·동일 전화번호 차단, 피추천인이 학생증 인증을 통과해야 보상 지급
- **추천인이 탈퇴하면 추천인 몫은 없음.** 피추천인 보상은 추천인이 탈퇴해도 30일 안에 학생증을 통과하면 그대로 지급되지만, 탈퇴한 추천인 몫 50하트는 주지 않는다. 탈퇴자의 추천 코드는 받지 않는다(없는 코드로 처리). 월간 랭킹 보상에서도 제외한다(알려진 한계, ERD.md §11-16).

### 2.8 지인 리뷰 (2026-09-08 신규, 핵심 차별점)

**소개팅 앱의 근본 문제는 자기소개를 본인이 쓴다는 것이다.** 아무리 잘 써도 신뢰의 근거가 되지 못한다. 지인 리뷰는 **대학 인증을 통과한 실제 지인이 남긴 평가**를 카드에 함께 노출해 이 문제를 구조적으로 해결한다. 경쟁사 5곳 어디에도 없는 기능이며, 이미 확정된 추천인 프로그램과 결합해 초대 동기를 하트 보상 이상으로 끌어올린다.

**작동 방식.** 추천 코드로 연결된 지인끼리 **양방향으로** 리뷰를 주고받는다.

- 신규 가입자는 온보딩에서 추천 코드를 입력한 **그 자리에서 추천인에게 리뷰를 작성**한다
- 추천인에게는 "○○님이 가입했어요, 리뷰를 남겨주세요" 푸시가 가고 거기서 작성한다
- 서로 써주는 구조라 품앗이처럼 보이지만 **실제로 아는 사이라 정직한 품앗이**다. 변별 신호는 평가의 높낮이가 아니라 "리뷰가 존재한다 = 실명 인증된 지인이 보증했다"는 사실 자체다
- **신규 가입자가 영원히 리뷰 0개로 남는 문제**를 양방향 구조가 해결한다

**가입하지 않은 사람은 리뷰를 쓸 수 없다.** 링크로 외부인이 쓰게 하면 부계정 자작이 쉬워져 신뢰의 근거가 무너진다. 대학 인증된 가입자만 쓸 수 있다는 점이 이 기능의 핵심 자산이다.

**형식.** 장점 태그(고정 목록에서 선택) + 자유 텍스트 한 줄.

**게시·삭제 정책 (심사 요건 연동).**

| 주체 | 권한 | 근거 |
|---|---|---|
| 리뷰를 받은 사람 | **삭제 불가** | 마음에 안 든다고 지우면 평판의 진정성이 사라진다 |
| 리뷰를 쓴 사람 | 삭제 가능 | 자기 글이고 오타·실수 정정 문의가 운영으로 몰리는 것도 막는다 |
| 운영자 | 신고 시 블라인드 | **애플 심사 지침 1.2는 UGC에 신고 수단과 24시간 내 조치 능력을 요구한다.** 조치 수단이 없으면 리젝된다. 국내법상 명예훼손 신고 시 임시조치 의무도 있다 |

**노출.** 카드에 전부 노출하되 가로 스크롤 또는 "더보기"로 접는다. 리뷰어는 **대학 로고 + 만화 아바타 + 닉네임 + 태그 + 자유 텍스트 한 줄**로 표시한다(2026-09-10 개정 — 실명 마스킹(김○○) 방식은 폐기, 전 화면에서 닉네임으로만 표시하는 규칙과 동일, CLAUDE.md §7).

> **출시 전 리스크 — 대학 로고 상표권.** 대부분의 대학이 UI(University Identity) 사용 지침을 두고 무단 사용을 금지한다. 사용자가 실제 로고 사용을 선택했으므로, **출시 전 대상 대학의 UI 사용 지침을 확인**하고 거절당하면 자체 디자인 배지(대학 상징색 + 학교명 텍스트)로 폴백한다.

**남은 한계.** 지인을 많이 데려온 사람이 리뷰도 많아 유리해진다. 내성적인 사용자가 구조적으로 불리해지는 문제는 남아 있으며, 첫 코호트에서 리뷰 개수 분포를 보고 노출 방식을 재검토한다.

### 2.9 코호트 오픈 — 성비 불균형 대응 (2026-09-08 신규)

**성비 붕괴는 소개팅 앱이 실패하는 가장 흔한 원인이고, 한 번 무너지면 복구가 거의 불가능하다.** 그래서 전국 동시 오픈을 하지 않고 **학교별로 순차 오픈**한다.

```
학교 오픈 공지 → 14일 모집 기간(가입은 되지만 카드는 안 옴)
              → 예고한 날짜에 카드 지급 시작
```

- 모집 기간에는 **"N월 N일에 첫 카드가 열려요"를 명시**하고 남은 시간을 카운트다운으로 보여준다. 기존 `{type.countdown}` 48px 토큰을 그대로 재사용한다
- **재화 차등이 없다.** 소수 성별에게 하트를 더 주는 방식은 등록비 폐지로 해결한 성차별 문제를 재화 쪽에서 다시 만든다. 코호트 오픈은 그 논란 없이 첫 경험 품질을 확보한다
- **14일이 끝나면 성비와 무관하게 예고한 날짜에 연다.** 공지한 날짜를 미루면 대기자가 그대로 이탈하고 재유입이 안 된다
- 다만 **성비가 최소선에 못 미치면 지급 주기를 주 1회로 낮춰 시작**한다. 날짜 약속은 지키되 얇은 후보 풀에서 카드를 남발하지 않는다. 이후 §2.1 사다리에 따라 정상 주기로 올린다
- **지급 주기·성비 판단은 학교 단위가 아니라 지역그룹 단위다**(2026-09-13 확정, ERD.md §11-7). 지역그룹이 곧 매칭 풀이므로 `region_group_settings` 값도 지역그룹당 하나뿐이고 학교별 주기 컬럼은 두지 않는다. **새로 오픈하는 학교는 14일 모집 기간이 끝나면 자체 성비를 새로 판단하지 않고, 그 시점 소속 지역그룹의 현재 지급 주기에 합류**한다 — 위 "성비 미달이면 주 1회로 시작"은 지역그룹이 처음 열릴 때만 적용되는 기준이다

**초기 사용자 확보 채널** (전부 병행):

| 채널 | 비용 | 코호트와의 궁합 |
|---|---|---|

## 3. 개발 전략 — 얇게 끝까지 관통시키기

기능을 하나씩 완성하는 대신, **가입부터 채팅까지 최소 구현으로 먼저 이어붙인다.**

1. 소개팅 앱은 루프가 한 군데라도 끊기면 가치가 0이다. 부분 완성은 검증되지 않는다.
2. **매칭 품질은 실제 프로필이 있어야만 판단할 수 있다.** 상상으로 벡터를 튜닝하면 안 된다.

푸시는 이 제품에서 부가 기능이 아니라 **핵심 동작의 일부**다.

### 3.2 만들지 않을 것 (명시적 제외)

1개월 MVP를 지키기 위해 아래는 의도적으로 만들지 않는다.

- 관리자 웹 화면 → **Supabase 대시보드로 대체**
- 임베딩 모델 자체 서빙 → **OpenAI API 호출**
- 추천 알고리즘 사전 튜닝 → **데이터가 쌓인 뒤에**
- 무한 스크롤 카드덱(스와이프 UI) → **제품 형태상 불필요**
- 정교한 디자인 → 조각 8로 이월
- 구독제·광고
- **오프라인 이벤트 제휴 채널** (경쟁사 연픽의 "일일호프"류) → 매칭 제품 핵심 가치와 결이 다른 별도 사업이라 도입하지 않는다 (경쟁사 조사 반영, 최종 결론)
- **매칭 외 체류 콘텐츠 전면 도입은 하지 않는다.** 최소 스코프의 커뮤니티 탭(5번째 탭, `polls`·`poll_votes`)만 둔다(2026-09-13 도입 확정, §13 미결14 · DESIGN.md §8.11)

### 3.3 iOS 빌드 (Mac 없음)

macOS 없이는 iOS 빌드와 앱스토어 제출이 불가능하다.
**클라우드 CI(Codemagic 등)로 iOS 빌드·서명·제출을 처리한다.**
따라서 다음을 지킨다.

- 코드에 플랫폼 분기를 최소화하고 Flutter 표준 API를 우선 사용한다
- iOS 전용 설정(권한 문구, 번들 ID, 서명)을 조각 0에서 미리 잡아둔다
- Apple Developer Program(연 약 13만원) 가입이 필요하다

### 6.2 성향 설문 — 9축

**각 축을 자기 자신에 대해서만 1회 묻는다("나는 어떤가", 2026-09-13 확정 — 사용자 최종 결론 "나 1회만").** DESIGN.md §8.5 `trait-slider` 서술이 맞았고, 이 절이 예전에 적어뒀던 "나/이상형 2회" 서술이 틀렸다(§13 미결25 해결). 이상형에 대한 조건은 설문으로 재질문하지 않고 **06-1 이상형 조건 화면**(선호 나이·키 범위 슬라이더, 선호 MBTI·얼굴상·인상, "상관없어요" 체크박스)으로만 받는다. **5점 슬라이더(−1 −0.5 0 0.5 1)로 고른다(2026-09-13 사용자 결정 — ERD.md §11-3).**

| #  | 축                       | 왼쪽 ← → 오른쪽                       |
| -- | ------------------------ | --------------------------------------- |
| 1  | 활동성                   | 집에서 쉬는 게 좋다 ↔ 밖에 나가야 산다 |
| 2  | 낯가림·친밀도 형성 속도 | 낯을 많이 가린다 ↔ 금방 친해진다       |
| 3  | 계획성                   | 즉흥적으로 ↔ 계획을 세워서             |
| 4  | 연락 빈도                | 필요할 때만 ↔ 하루 종일                |
| 5  | 감정 표현                | 담백한 편 ↔ 표현이 풍부                |
| 6  | 음주                     | 거의 안 마신다 ↔ 자주 즐긴다           |
| 7  | 운동                     | 관심 없다 ↔ 꾸준히 한다                |
| 8  | 관계 속도                | 천천히 알아가기 ↔ 확신하면 빠르게      |
| 9  | 새로움                   | 익숙한 게 편하다 ↔ 늘 새로운 걸        |

**"학업·진로" 축은 2026-09-12 폐지**(사용자 요청, DESIGN.md §13 미결48). 슬라이더 9세트(9축 × 1회)는 **1분 이내**가 걸릴 것으로 예상한다(베타에서 재측정). 실제 축별 문구(총 9세트)는 DESIGN.md §8.5에 정리했다.

**벡터화**: 5점 슬라이더(−1, −0.5, 0, 0.5, 1)로 9개 값을 얻는다(2026-09-13 확정, 사용자 결정 — ERD.md §11-3). 이 중 **8축(낯가림 제외)에 축별 가중치를 사전 곱셈**해 pgvector 컬럼 `self_survey`에 저장하고, **낯가림 값은 별도 컬럼 `shyness_score`**에 그대로 둔다(2026-09-13 확정, 사용자 결정 — §13 미결32 해결). 가중치를 쿼리 시점이 아니라 저장 전에 곱하는 이유는 pgvector가 축별 가중치를 곱한 거리 연산을 지원하지 않기 때문이다. `ideal_survey`는 폐지됐다(2026-09-13, §13 미결25 해결).

**점수 — 확정(2026-09-13, 사용자 결정 — §13 미결32 해결): 벡터 유사도 채택, 단 코사인이 아니라 L2 거리(`<->`).** 코사인 유사도는 Likert 축에서 `[3,3,3]`과 `[5,5,5]`의 유사도를 1.0으로 판정해 "중립인 사람"과 "극단인 사람"을 같다고 본다 — 오답이다. 두 사람의 `self_survey`(8축, 가중치 사전 곱셈)를 pgvector L2 거리로 직접 비교한다 — 앞서 적어뒀던 두 후보 중 (a) 채택, (b) "06-1에 방향성 재질문 추가" 안은 기각.

**낯가림 축은 이 벡터에서 제외한다.** 사용자 지시: "낯가림 빼고는 다 가까울수록 좋다야" — 나머지 8축은 가까울수록(유유상종) 좋지만, 낯가림은 서로 다를수록 좋은 축이다. 같은 L2 거리 함수에 넣으면 부호가 반대로 작동하므로, `shyness_score`는 별도로 `abs(A.shyness_score − B.shyness_score)`를 보너스 점수로 가산한다(§6.7).

```
최대가능거리 = 2 × √8 = 5.66     (8개 축이 단위 가중치로 정반대인 경우 기준값 — 실제 축별 가중치가 정해지면 최대가능거리도 다시 산출해야 한다, 조각 3·4)
```

### 6.3 벡터 3종(2026-09-19 — "나는"/"원해" 문장 임베딩 신설로 2종에서 확대, §13 미결8 해결 전제)

| 벡터           | 의미                                                    | 차원 |
| -------------- | ------------------------------------------------------- | ---- |
| `self_survey`  | 성향 설문 8축(낯가림 제외), 축별 가중치 사전 곱셈       | 8    |
| **"나는" 임베딩**(2026-09-19 신규, 구 `self_text` 대체) | 학과·계열 한 문장 + MBTI 한 문장 + 본인 얼굴상·인상 한 문장 + 자기소개를 서버 템플릿(LLM 아님)으로 이어붙인 문장의 임베딩(`text-embedding-3-small`) | 512 |
| **"원해" 임베딩**(2026-09-19 신규, 구 `ideal_text` 폐기분의 사실상 부활) | 선호 얼굴상·인상 한 문장 + "이런 사람이 좋아요" 자유 글(AI 초안 없음)을 서버 템플릿으로 이어붙인 문장의 임베딩 | 512 |

`shyness_score`(낯가림 원값, **5점(−1 −0.5 0 0.5 1), 2026-09-13 확정 — ERD.md §11-3**)는 벡터가 아니라 단일 컬럼으로 별도 저장한다(§6.2·§6.7). **낯가림 보너스는 2026-09-19 폐지됐다 — `shyness_score`는 저장만 하고 점수에는 가산하지 않는다.**

설문(`self_survey`)은 **L2 거리**, "나는"/"원해" 임베딩은 **코사인 유사도**를 쓴다(§6.7).

**문장에서 제외하는 항목**: 성향 설문(벡터로만, §6.2)·태그(자카드로만, §6.6b)·나이·키·흡연·종교(감점 계수로만, §6.5·§6.6a)·닉네임·사진·학교·성별(표시/필터로만). **MBTI는 예외다** — 문장에도 넣고 감점 계수(§6.4)도 유지한다. 선호 MBTI는 ok/no 토글이라 계수 쪽이 정확하고, 문장 쪽은 보조 신호일 뿐이라 중복 계산 문제가 생기지 않는다.

자기소개·태그·얼굴상·"원해" 글을 수정하면 문장과 임베딩을 **즉시 재생성**한다(2026-09-19 확정, §13 미결8 해결).

**`ideal_survey`는 계속 폐지 상태다.** 이번에 되살아난 것은 옛 `ideal_text`(자유 서술 재질문) 그 자체가 아니라 새 벡터 "원해" 임베딩이다 — 옛 구조는 이상형 조건 재질문과 자유 서술을 분리하지 않았지만, 새 구조는 06-1(구조화 조건: 나이·키·MBTI·얼굴상)과 "이런 사람이 좋아요"(신규 자유 글)를 계속 분리해서 받는다. "원하는 사람" 자유 서술 필드가 삭제됐던 2026-09-10 시점(DESIGN.md §9 화면8/구 `06-3`)의 결정은 폐기하지 않고, 새 화면(DESIGN.md §9 화면7b-2)으로 다시 들여온 것으로 본다.

### 6.4 MBTI — 8개 극 토글, 감점 방식

**입력**: 8개 토글, 기본값은 전부 ok.

```
E ok/no    I ok/no    N ok/no    S ok/no
T ok/no    F ok/no    J ok/no    P ok/no
```

**한 축에서 양쪽을 모두 끈 경우는 "상관없음"으로 해석한다.**
한 축에서 켜진 극이 1개면 그 극을 선호하고, 0개거나 2개면 그 축을 보지 않는다.
이 규칙 덕분에 실수로 양쪽을 다 꺼도 "아무도 보이지 않는" 상태가 되지 않는다.

**상대의 MBTI가 "모름"이면 그 상대의 MBTI계수는 1.00으로 둔다.**
정보가 없다는 이유로 불이익을 주지 않는다.

**판정 예시** — 내 설정이 `E ok, I ok, N ok, S no, T ok, F no, J ok, P ok` 일 때

| 상대          | 판정                     | 적합도 | 계수 |
| ------------- | ------------------------ | ------ | ---- |
| ENTJ          | E✓ N✓ T✓ J✓          | 4/4    | 1.00 |
| ESTJ          | E✓**S✗** T✓ J✓ | 3/4    | 0.90 |
| ESFJ          | E✓ S✗ F✗ J✓          | 2/4    | 0.80 |
| (전부 불일치) | —                       | 0/4    | 0.60 |

```
적합도(A→B)  = B의 4글자 중 A가 ok로 둔 글자 수 ÷ 4
양방향적합도 = √( 적합도(A→B) × 적합도(B→A) )
MBTI계수     = 0.6 + 0.4 × 양방향적합도        →  0.60 ~ 1.00
```

**아무도 배제하지 않는다.** 하드 필터로 만들면 후보가 6.25%까지 줄어 카드를 만들지 못하는 날이 생긴다.

**MBTI를 성향 벡터에 섞지 않는 이유**: E/I는 설문의 낯가림·친밀도 형성 속도 축과, J/P는 계획성 축과 겹친다.
같은 정보를 두 번 세면 그 항목만 과대평가된다.

### 6.5 키 — MBTI와 동일한 감점 방식

```
키적합도(A→B) = 1.00   B의 키가 A가 지정한 범위 안
              = 0.85   범위에서 5cm 이내로 벗어남
              = 0.70   그 이상 벗어남
              = 1.00   A가 선호 범위를 지정하지 않음

키계수 = √( 키적합도(A→B) × 키적합도(B→A) )      → 0.70 ~ 1.00
```

**키는 필수 입력이고 프로필에 공개된다.** 소개팅에서 실제로 중요하게 여겨지는 정보이고,
숨길 수 있게 두면 미입력이 오히려 부정적 신호로 읽힌다.

**선호 키 범위는 선택이다.** 지정하지 않으면 이 항목이 점수에 관여하지 않는다.

### 6.6 학과 — 매칭에 관여하지 않는 표시값

**학과는 매칭에 쓰지 않는다 — 같은 학과 하드 필터는 폐기했다(2026-09-13, §13 미결27).** 같은 과 지인에게 들킬 우려는 여전히 유효하지만, UI 를 어디에 둘지 정하는 대신 필터 기능을 없앴다 — 학과는 카드·프로필에 표시만 되는 값으로 남는다.

### 6.6a 흡연·종교 — 벡터 미포함, 감점 계수

흡연 여부(`smoke-toggle`)와 종교(`religion-select`)는 성향 설문 벡터(`self_survey` 8축 + `shyness_score`, §6.2·§6.3)에 포함되지 않는다. MBTI(§6.4)·키(§6.5)와 같은 방식으로, 최종 점수(§6.7)에 곱해지는 **감점 계수**로만 반영한다.

**벡터화하지 않는 이유**: 두 항목 모두 "상대는 어땠으면 하는가"를 묻는 이상형 재질문이 없다 — 본인 응답만 1회 받고, 상대에 대한 선호는 별도로 묻지 않는다. MBTI(선호 8개 극 토글, §6.4)와 달리 "내가 원하는 상대의 흡연 여부·종교"를 입력받을 방법이 없어서, 방향성 적합도 계산 자체가 성립하지 않는다. 감점 계수 방식은 상대 선호 입력 없이도 최종 점수에 곱셈으로 반영할 수 있어 이 문제를 우회한다. (참고로 성향 설문도 2026-09-13부로 나 1회만 묻는 방식이 됐지만, 그쪽은 9축 자체가 이미 벡터로 확정돼 있어 §6.2의 별도 미결로 다룬다.)

**흡연계수·종교계수는 §6.7 최종점수 공식에 곱해진다**(활동성계수와 같은 자리). **수치 확정(2026-09-19, 사용자 결정)**:

- **흡연계수 = 0.5** — 내가 비흡연이고 상대가 흡연이면 적용. 그 외(둘 다 흡연·둘 다 비흡연·내가 흡연자인 경우)는 1.0.
- **종교계수 = 0.8** — 나와 상대의 종교 응답이 다르면 적용. 같으면 1.0.

2026-09-12 그릴링 세션에서는 "벡터에 넣지 않고 감점 계수로만 반영한다"는 방식만 확정됐었고, 이번에 실제 수치까지 확정했다(사용자가 종교계수를 0.7이라 답했다가 0.8로 번복, DESIGN.md §13-49).

### 6.6b 나의 특징 · 이상형 특징 — 자카드 상호 매칭(2026-09-19 확정, 태그점수 20%에 통합)

`04-6 나의 특징`(**46개** 태그 풀 중 최소 3·최대 5개, 2026-09-19 개정 — 48개 풀에서 "높은 연봉"·"뛰어난 커리어" 삭제)과 `06-2 이상형 특징`(**44개** 태그 풀 중 최소 3·최대 5개, 2026-09-19 개정 — 45개 풀에서 "안정적인 직업" 삭제)은 관심사 태그(§6.1)와 별개의 입력이다(2026-09-13 확정, DESIGN.md §13-53).

**구조는 상호(reciprocal) 매칭이고, 계산은 자카드 유사도다(2026-09-19 확정, 사용자 결정 — "유사도 검증으로 해보고 싶다").** 내 "나의 특징" ↔ 상대의 "이상형 특징"을 자카드로 비교하고, 동시에 상대의 "나의 특징" ↔ 내 "이상형 특징"을 자카드로 비교해 두 값의 평균을 낸다 — 예전 방향점수(A→B/B→A, §6.7)가 `ideal_survey`/`self_survey`를 양방향으로 보던 것과 같은 발상이다. **다만 성향 점수 쪽은 2026-09-13 개정으로 대칭 비교(§6.2)로 바뀌어 방향성이 없어졌다 — 비대칭 구조가 남아있는 건 이 항목뿐이다.**

**태그점수(§6.7, 가중치 20%) = 평균[ 관심사↔관심사 자카드(대칭), 나의특징↔이상형특징 자카드(양방향 평균) ]**(2026-09-19 확정).

**얼굴상·인상은 이 절에서 빠졌다(2026-09-19 변경).** 상호 벡터 비교 방식은 폐기되고, "나는"/"원해" 문장의 재료로 편입됐다(§6.1·§6.3) — 본인 얼굴상·인상은 "나는" 문장에, 선호 얼굴상·인상은 "원해" 문장에 각각 들어가 문장유사도(§6.7, 50%)로 반영된다. 라벨을 자기가 고르는 방식이라 인기 얼굴상으로 응답이 쏠릴 수 있다는 점검 사항(DESIGN.md §13-49)은 여전히 유효하다 — 문장 임베딩으로 바뀌어도 라벨 선택 자체의 쏠림 위험은 남는다.

### 6.7 최종 점수

**2026-09-19 갱신 — 유사도 검증 방식으로 3차 확정(§6.6b·이 절의 "가중치 미정" 전부 해소, 사용자 의도 "유사도 검증으로 해보고 싶다").** "나는"/"원해" 문장 임베딩(§6.3)이 신설되면서 성향점수·태그점수·문장유사도 3항 가중합 구조로 바뀌었다. (2026-09-13 갱신 당시의 `ideal_survey`·`ideal_text` 폐지·방향점수 폐기 결정(§13 미결32·33)은 유지된다 — 이번 갱신은 그 위에 문장유사도 항을 새로 얹은 것이다.)

```
성향점수   = 1 − ( L2거리(A.self_survey, B.self_survey) ÷ 최대가능거리 )   (0~1, pgvector `<->`, §6.2)

태그점수   = 평균[ 자카드(A.관심사, B.관심사), 평균( 자카드(A.나의특징, B.이상형특징), 자카드(B.나의특징, A.이상형특징) ) ]   (§6.6b)

문장유사도 = 평균[ cos(A.원해, B.나는), cos(B.원해, A.나는) ]   ("나는"/"원해" 임베딩, §6.3)

최종점수 = (0.3 × 성향점수 + 0.2 × 태그점수 + 0.5 × 문장유사도)
           × MBTI계수(0.60 ~ 1.00)
           × 키계수(0.70 ~ 1.00)
           × 나이계수(0.70 ~ 1.00)
           × 흡연계수(1.0 또는 0.5, §6.6a)
           × 종교계수(1.0 또는 0.8, §6.6a)
           × 활동성계수(§13 미결9)
```

**낯가림 보너스는 폐지했다(2026-09-19)** — `shyness_score`는 저장만 하고 점수에는 더 이상 가산하지 않는다(§6.2·§6.3).

**"나는"/"원해" 문장 — 서버 템플릿(LLM 아님)으로 조립한다(§6.3).**

- **"나는"** = 학과·계열 한 문장 + MBTI 한 문장 + 본인 얼굴상·인상 한 문장 + 자기소개(직접 작성 또는 06-2b AI 초안 수정본).
- **"원해"** = 선호 얼굴상·인상 한 문장 + "이런 사람이 좋아요" 자유 글(§6.1 신규, AI 초안 없음).
- 문장에서 제외: 성향 설문(벡터로만)·태그(자카드로만)·나이·키·흡연·종교(계수로만)·닉네임·사진·학교·성별(표시/필터로만). **MBTI는 예외** — 문장에도 넣고 계수도 유지한다(선호 MBTI가 ok/no 토글이라 계수가 정확하고, 문장은 보조 신호일 뿐이라 중복 계산 문제가 없다).
- 자기소개·태그·얼굴상·"원해" 글을 수정하면 문장과 임베딩을 **즉시 재생성**한다(§13 미결8 해결).

**문장 예시(김철수, 사용자 제공 — DESIGN.md §9에도 동일 예시 반영)**

> **[나는]** "나는 컴퓨터공학과, 공대 계열 학생이다. MBTI는 ENFP다. 얼굴은 강아지상이고 부드러운 인상이다. 주말마다 산 타고 내려와서 맛집 찾아다니는 게 낙이에요. 등산은 혼자보다 같이 가는 걸 좋아해서 같이 갈 사람 있으면 초보 코스부터 천천히 알려드릴 수 있어요. 계획 짜는 걸 좋아해서 여행 가면 제가 일정 다 짭니다. 카페 가서 보드게임 하는 거 좋아하고, 영화는 장르 안 가리고 다 봐요. 술은 거의 안 마시고, 술자리보다는 낮에 만나서 뭐 하는 걸 더 좋아해요."
>
> **[원해]** "고양이상이나 여우상, 시크한 인상이 좋다. 말이 잘 통하는 사람이 제일 좋아요. 자기 일 열심히 하고 하고 싶은 게 확실한 사람한테 끌려요. 같이 새로운 데 다니는 거 좋아하면 더 좋고, 술 안 마셔도 괜찮은 사람이었으면 해요. 솔직하게 말하는 편이면 좋아요."

앞의 학과·MBTI·얼굴상(또는 선호 얼굴상) 문장은 템플릿이 고정 생성하고, 그 뒤는 사용자가 쓴 자기소개/자유 글 원문을 그대로 이어붙인다.

**나이계수 — 확정(2026-09-13, 사용자 결정, 미결28 해결): 키와 같은 감점 계수 방식.**

```
나이적합도(A→B) = 1.00   B의 나이가 A가 지정한 범위 안
                = 0.85   범위에서 2살 이내로 벗어남
                = 0.70   그 이상 벗어남
                = 1.00   A가 "나이는 상관없어요"를 선택(선호 범위 미지정)

나이계수 = √( 나이적합도(A→B) × 나이적합도(B→A) )      → 0.70 ~ 1.00
```

키(§6.5)와 동일한 근거 — 초기 코호트는 인원이 적어 하드 필터로 두면 카드를 못 받는 사람이 생긴다.

**최종점수는 산술 가중합에 계수를 곱하는 구조다**(2026-09-19, 3차 확정). 방향 A→B/B→A와 기하평균(궁합점수) 구조는 문장유사도 항의 평균으로 흡수됐다. LLM 재정렬·수락/거절 학습은 하지 않는다(2026-09-19 확정, §6.9).

**비중 요약**

| 항목                          | 최종 점수 기여                                                   |
| ----------------------------- | ----------------------------------------------------------------- |
| 성향 설문(`self_survey` 8축) | **30%**(2026-09-19 축소, 구 70% — 문장유사도 신설로 재배분) |
| 관심사 태그 + 나의 특징·이상형 특징 | **20%**(자카드, §6.6b, 2026-09-19 확정 — 구 관심사 단독 30%에서 재배분) |
| "나는"/"원해" 문장유사도 | **50%**(2026-09-19 신설, §6.3) |
| 낯가림                        | 폐지(가산 없음, `shyness_score` 저장만, §6.2·§6.3) |
| MBTI            | 위 합계를 0.60~1.00배 |
| 키              | 위 합계를 0.70~1.00배 |
| 나이            | 위 합계를 0.70~1.00배(2026-09-13 확정, 미결28 해결) |
| 흡연            | 위 합계를 0.5배(비흡연자↔흡연자 조합만, §6.6a) |
| 종교            | 위 합계를 0.8배(응답 불일치 시, §6.6a) |
| 활동성          | 위 합계를 계수만큼 감점(§13 미결9 — 0~3일 1.0 / 4~7일 0.7 / 8~14일 0.4) |

**하드 필터**: 성별(반대 성별만, DESIGN.md §13-113) · 지역그룹 · 활성 상태 · 차단 · **15일 이상 미접속**(2026-09-19, §13 미결9 해결 — 활동성계수가 아니라 하드 필터로 후보에서 제외) · **이미 카드로 받은 사람**. 같은 학과 필터는 폐기했다(§6.6).

**"이미 카드로 받은 사람"의 정의 — 확정(2026-09-13, 사용자 결정, ERD.md §11-4·§4 주석)**: 내가 결정한 카드의 상대(`card_decisions`) + 받은 수락함에서 응답한 상대(`acceptance_responses`) + 매칭 이력이 있는 상대(`matches`, 게이트 실패 포함) + 아직 만료되지 않은 카드의 상대. **무응답으로 만료된 무상 카드의 상대만 다시 나올 수 있다.**

**활동성 계수는 소수 큐레이션 구조에서 특히 중요하다.**
유령 계정에게 그 지급일의 유일한 카드를 낭비하면 사용자는 다음 지급일까지 통째로 잃는다.

### 6.8 카드 생성 쿼리

pgvector를 택한 핵심 이유가 여기에 있다. **필터와 벡터 연산이 하나의 SQL 안에서 끝난다.**

```sql
-- pick_daily_card(owner uuid) — 상위 1명을 반환
-- profiles.looking_for 컬럼은 조각 2 마이그레이션에서 삭제한다(ERD.md §12-36)
where 상대_성별 <> 나의_성별  -- 반대 성별 자동 매칭(DESIGN.md §13-113)
  and 지역그룹 일치  and 상태 = 'active'
  and 아직 카드로 받은 적 없음  and 서로 차단하지 않음
order by 최종점수 desc limit 1
```

**성능**: 수천 명 규모에서는 인덱스 없이 전체 스캔해도 수십 밀리초다.
벡터가 수만 개를 넘을 때 HNSW 인덱스를 추가한다. 지금 붙이면 정확도만 손해다.

**교체 가능성**: 카드 생성은 `MatchingRepository` 인터페이스 뒤에 둔다.
나중에 전용 벡터 DB로 옮길 때 구현체 하나만 교체하면 되고, ViewModel과 화면은 손대지 않는다.

### 6.9 알려진 기술적 불확실성

없음. "원하는 사람 서술" 임베딩과 자기소개 임베딩을 대조할 때의 불확실성은 `ideal_text` 폐기로 사라졌다(2026-09-13, §13 미결33).

## 7. 보안과 권한

소개팅 앱은 데이터가 유출되면 서비스가 끝난다. 가장 중요한 장이다.

**개인정보 최소수집 원칙**: 주민등록번호 등 민감정보는 수집하지 않는다. 학생증 검증(7.3절)의 자동 OCR은 **학교명만** 추출해 대조하고, **실명은 OCR로 추출하지 않는다** — `3b`에서 사용자가 직접 입력한 이름을 학생증 이미지와 대조하고, 그 값은 `profile_private.real_name`(민감, 본인만 조회, 서버 응답에 담기지 않음)에만 저장한다(2026-09-13 사용자 결정, ERD.md §11-2). 향후 본인인증을 강화하는 논의가 나오더라도 최소수집 원칙은 유지한다(경쟁사 연픽이 통신사 본인인증에서 주민번호 앞 7자리를 수집하는 것과의 의도적 차별점).

### 7.1 원칙 — 클라이언트는 본인 데이터만 읽고, 쓰기는 전부 FastAPI를 거친다

RLS는 행 단위라 "이 사람의 이 컬럼만"을 표현하지 못한다. 그래서 경로를 나눈다.

**확정(2026-09-13, 사용자 결정 — ERD.md §11-8): FastAPI 경유.** Supabase RPC(DB 함수) 대신, 남의 데이터가 섞이는 조회·쓰기는 전부 FastAPI 엔드포인트가 처리하고 `service_role`로 접근한다. `security definer` 함수는 쓰지 않는다(frontend/CLAUDE.md §10.1).

| 접근 대상   | 방식                                                        |
| ----------- | ----------------------------------------------------------- |
| 내 프로필   | `profiles` 직접 조회 — RLS가 `(select auth.uid()) = id` 만 허용 |
| 오늘의 카드 | **FastAPI 경유** — 필요한 컬럼만 골라 반환    |
| 받은 수락함 | **FastAPI 경유**                                      |

이 구조에서는 앱 코드에 버그가 있어도 **남의 이메일·연락처가 나갈 경로 자체가 없다.**

**모자이크 배너**는 실제 사진을 내려주고 앱에서 흐리게 처리하는 방식이 아니라,
**서버가 처음부터 흐린 이미지만 내려준다.** 앱에서 처리하면 원본이 이미 기기에 도착해 있어 우회 가능하다.

### 7.2 테이블별 RLS 정책

**이 절의 표는 폐기(2026-09-13, 사용자 결정 — ERD.md §11-8).** `daily_cards`·`card_decisions`는 카드 화면에 상대 정보가 섞여 클라이언트 조회 정책 자체를 두지 않고(FastAPI 전용), `reports`의 "신고자 쓰기"도 §2 원칙대로 클라이언트 쓰기 정책 없이 FastAPI가 대신 쓴다. 실제 접근 표는 **ERD.md §2 "접근 경로와 RLS"**를 기준으로 삼는다.

### 7.3 학생인증 강제 지점

Supabase Auth는 기본적으로 아무 이메일이나 받는다.
**Auth Hook**(DB 함수가 아니라 **FastAPI HTTP Auth Hook**, 2026-09-13 사용자 결정 — ERD.md §11-12)을 걸어 가입 시점에 **`university_email_domains`(학교당 도메인 여러 개, ERD.md §3)** 화이트리스트와 **`signup_blocks`(탈퇴 후 재가입 제한, §2.6)를 함께 검사**하고,
목록에 없는 도메인이거나 재가입 제한에 걸리면 거부한다. **도메인 1개는 학교 1개에만 속하고, 캠퍼스 분리는 두지 않는다**(첫 출시는 서울권뿐, ERD.md §11-10).

**가입 흐름 전체(조각 1a, 2026-09-18 결정)**: 이메일 OTP 요청(6자리 코드, 유효 10분, 재전송 60초 경과 후, 시간당 최대 5회) → Before User Created HTTP Auth Hook(FastAPI, Google Cloud Run 서울)이 위 화이트리스트·재가입 제한을 검사 → 통과하면 Supabase Auth가 `auth.users` 계정을 생성 → **`profiles` pending 행은 앱도 FastAPI도 아니라, `auth.users` INSERT 직후에 도는 Postgres 트리거(`handle_new_user_profile`, `AFTER INSERT ON auth.users`)가 만든다.** Before User Created 훅은 `auth.users` 행이 커밋되기 전에 불려서 그 안에서 `profiles.id → auth.users.id` FK를 참조하는 insert를 하면 위반이 나기 때문에, 승인/거부만 결정하고 행을 쓰지 않는다(2026-09-18 리뷰로 정정 — ERD.md §11-26, ERD_DECISIONS.md §11-26).

**OTP 정책(조각 1a, 2026-09-18 사용자 결정).** 인증코드 유효 시간 10분, 재전송은 60초 경과 후에만 가능, 시간당 최대 5회로 제한한다. Supabase Auth 설정값을 그대로 맞춘다(OTP expiry 600초, rate limit).

**졸업 여부는 따지지 않는다(2026-09-18 사용자 결정, §13 미결1).** 학교 이메일로 가입만 되면 졸업생도 그대로 이용할 수 있고, 정기 재인증 주기는 두지 않는다. 부적절한 이용은 신고와 학생증 재인증(조각 1b)으로 보완한다.

앱 화면에서만 막으면 API를 직접 호출해 우회할 수 있다.

**학생증 사진 검증도 함께 강제한다(경쟁사 조사 반영, 신규. 2026-09-18: 조각 1a 이메일 인증 뒤 조각 1b 로 이동 — §3.1).** 이메일 인증만으로는 클럽트웬티처럼 "미인증 배지가 붙은 채로 진행"되는 신뢰성 리스크가 있다고 판단해, 학생증/학생카드 사진 검증을 추가한다.

- 자동 1차: OCR로 학생증에서 **학교명만** 추출해 이메일 도메인으로 이미 확인된 학교와 대조한다. **실명은 OCR로 추출하지 않는다** — `3b`에서 사용자가 직접 입력한 이름을 학생증 이미지와 대조하고 `profile_private.real_name`에 저장한다(2026-09-13 사용자 결정, ERD.md §11-2)
- **OCR 도구는 Google Cloud Vision(조각 1b, 2026-09-19 결정).** 같은 GCP 프로젝트에 걸려 있어 계정을 새로 만들 필요가 없고, 월 1,000장까지 무료 구간이라 초기 규모에서는 사실상 비용이 들지 않는다. 네이버 클로바 OCR은 별도 계정·결제가 필요해 탈락, 온디바이스 ML Kit는 클라이언트가 낸 결과를 서버가 그대로 신뢰할 수 없어(우회 가능) 탈락했다. **자동 통과 기준은 OCR 텍스트 안에 학교명과 `3b` 실명이 둘 다 보일 때**다.
- 애매하거나 자동 대조에 실패하면 사람이 **Supabase 대시보드에서 학생증 이미지를 직접 열어** "진짜 학생증처럼 보이는가"만 육안으로 재검토한다(학교명 대조 기준. 실명은 위 OCR과 무관하게 `3b` 입력값이 그대로 쓰인다). 전용 관리자 페이지는 만들지 않고 추후 필요해지면 고려한다(조각 1b, 2026-09-19 결정). 재검토가 발생하면 담당자에게 **디스코드 웹훅으로 텍스트 알림만** 보낸다 — 학생증 사진 자체는 디스코드로 보내지 않는다(조각 1b, 2026-09-19 결정)
- 검증 결과는 boolean이 아니라 상태값(`none`/`pending`/`verified`/`rejected`, ERD.md `profiles.student_verification`)으로 남긴다 — 자동 대조 실패 시 사람이 재검토하는 대기 상태를 표현해야 하기 때문이다(§13 미결3, 2026-09-13 결정 — ERD.md §11-2, 값 4개는 2026-09-14 확정 — ERD.md §11-24). 학생증 원본 이미지는 `student-id-temp` 비공개 버킷에 검증이 끝날 때까지만 두고, 끝나면 즉시 삭제한다(ERD.md §9)
- **학생증을 제출할 때마다 시도 기록 `student_verification_attempts` 에 한 행을 남긴다**(2026-09-14 사용자 결정, ERD.md §11-24). 반려 사유와 재검토 시각도 이 행에 남고, 재시도 횟수는 행 수로 FastAPI 가 센다. 클라이언트는 이 테이블을 읽지 않고 본인 반려 사유는 FastAPI 응답으로 받는다. **재제출 횟수 상한은 두지 않는다(2026-09-19 결정, §13 미결3 해결)** — `pending` 중에는 재제출이 막혀 한 번에 한 건만 쌓이고, 악용이 확인되면 그때 상한을 추가한다. 고객 지원 경로는 미정으로 남긴다
- **`verified` 확정 후에는 재제출 자체를 막는다(2026-09-20 결정)** — 이미 통과한 사람이 다시 제출하면 FastAPI 가 거부한다(409). `rejected` 는 위 상한 없음 규칙대로 계속 재제출할 수 있다. 확정(`verified`/`rejected`) 순간 Postgres 트리거가 `student-id-temp` 의 최근 제출 파일을 지운다 — 보관 기간을 두지 않고 즉시 삭제한다(ERD.md §9, `student_verification_finalized` 트리거)
- 검증이 끝나기 전까지 사용자는 온보딩 화면에 머무르며 다른 기능에 접근할 수 없다
- 업로드된 실사진 자체는 `google_mlkit_face_detection`(Flutter, 온디바이스)으로 얼굴 존재 여부를 기기 안에서 검증한다. 얼굴이 없으면 업로드를 막고 재촬영을 요구한다. **구현 후 실기기 테스트로 검증을 마쳐야 한다**(frontend/CLAUDE.md §8 테스트)
- **학과·학번은 학생증 검증 대상이 아니다(2026-09-13, DESIGN.md `3c` 신설).** 위 대조는 학교명(+3b의 실명)까지만 하고, 학과·학번은 `3c`에서 사용자가 직접 입력한 값을 그대로 저장한다 — 학생증에 학과가 인쇄돼 있어도 대조하지 않는다. 허위 입력 가능성에 대비할지는 미결(§13 미결35, DESIGN.md §13-66)
- **`profiles.department` 컬럼은 새로 만들지 않는다(2026-09-20 결정)** — 학과는 기존 `profiles.major` 를 그대로 재사용한다. FastAPI 응답의 `department` 는 PostgREST 별칭(`department:major`)일 뿐 DB 컬럼은 하나다. 학번은 `profiles.student_number` 컬럼을 새로 추가해 저장한다(ERD.md §3)

### 7.4 사진

Storage 버킷은 **비공개**로 두고 서명 URL로만 내려준다.
공개 버킷이면 URL을 아는 누구나 볼 수 있고, 크롤링 시 전체 사진이 통째로 유출된다.

**사진 버킷(`profile-photos` · `student-id-temp`)은 파일 10MB · `image/jpeg` `image/png` 로 제한한다**(2026-09-14 사용자 결정, ERD.md §11-25). 앱은 업로드 전에 사진을 압축하고 JPEG 로 다시 인코딩한다. 버킷 제한은 업로드 쪽이 신고한 content type 과 크기만 보므로(413 · 400), 파일 내용(매직 바이트)은 FastAPI 가 검사한다.

### 7.5 비밀키

**OpenAI API 키를 Flutter 앱에 넣지 않는다.** 앱은 디컴파일되면 키가 그대로 노출된다.
임베딩 생성은 **FastAPI**(2026-09-12 확정, §1) 에서만 수행하고, 키는 서버 환경변수에 둔다.

Supabase URL과 anon key는 `--dart-define` 으로 주입하고, `.env` 파일은 커밋하지 않는다.

### 7.6 결제 검증 (조각 7)

**구매 여부를 앱이 판단하지 않는다.** 영수증은 반드시 **FastAPI**(2026-09-12 확정, §1) 에서 검증하고,
`entitlements` 갱신과 아이템 지급도 서버에서 수행한다. 앱이 판단하면 우회 결제가 가능하다.

### 7.6b 지인 차단 연락처 데이터 보관 — 확정 (2026-09-13, 사용자 결정, DESIGN.md §13-62)

**본인 전화번호(04-1 온보딩)와 지인 연락처(`8d` 차단 대상)는 저장 방식이 다르다.**

- **회원 본인 전화번호** — **원본(평문) 저장.** 저장 시 컬럼 암호화(at-rest) + 접근 통제(운영자 조회 최소화, 감사 로그)를 둔다. **감사 로그는 테이블 없이 FastAPI 구조화 로그로 남긴다**(2026-09-13 사용자 결정 — ERD.md §11-13). **운영자는 `profile_private`를 FastAPI 관리 기능으로만 조회한다 — Supabase 대시보드·SQL 직접 조회는 금지**(2026-09-13 확정, ERD.md §11-18). 접속 기록 보관 기간은 개인정보 안전성 확보조치 기준을 확인해 조각 2 전에 정한다.
- **지인 연락처 차단 목록(`8d`/`contact_blocks`)** — **원본을 저장하지 않는다.** 서버 비밀키 기반 **HMAC 해시**로만 저장한다. 번호는 해시 전에 **E.164(국가번호 포함) 형식으로 정규화**한 뒤 HMAC을 적용한다.
  - **단순 해시(SHA 등)가 아니라 HMAC인 이유**: 전화번호는 경우의 수가 적어 키 없는 단방향 해시는 전수 대입으로 쉽게 역산된다. 비밀키(DB 밖, FastAPI 환경변수)를 섞은 HMAC이어야 원본이 보호된다.
  - **나중에 가입한 지인 소급 차단(§13-21 해결)**: 신규 가입자의 본인 번호를 같은 키로 HMAC 처리해 기존 차단 해시와 대조한다. 원본 없이도 상호 차단이 동일하게 동작한다.
  - **`8a` 고지문 "전화번호는 암호화해 대조에만 쓰고 원본은 저장하지 않아요"는 그대로 참**이라 문구를 바꿀 필요가 없다.
  - **비밀키 교체 시 기존 해시가 전부 무효화**된다 — 키 교체 절차는 조각 6 구현 시점에 정한다(신규 미결, 아래 §13 미결36 참조).

**미결34(법무 검토) 범위**: 비회원(가입하지 않은 지인) 번호는 원본을 보관하지 않으므로 그 부분의 법무 리스크는 사라졌다. 해시(HMAC) 보관 자체가 개인정보 처리에 해당하는지 여부만 검토 대상으로 남긴다.
