## 1. 제품 개요

대학생·대학원생 전용 소개팅 애플리케이션.
학교 이메일로 학생임을 인증하고, 성향·관심사·자기소개를 벡터로 변환해
**지급일 아침 가장 잘 맞는 상대 한 명**을 카드로 제공한다(지급 주기는 가변, 2.1절 참조).

| 항목 | 결정 |

| 앱 이름 | CampusMate |
| 패키지명 | `io.github.juunn.campusmate` |
| 플랫폼 | Android + iOS |

### 1.1 왜 스와이프가 아니라 소수 큐레이션 카드인가

**콜드스타트 문제가 제품 구조로 해결된다.**
스와이프는 화면을 채우려면 후보가 수십 명 있어야 하지만, **소수 큐레이션 카드는 후보가 1명만 있어도 성립한다.**
소개팅 앱이 실패하는 가장 흔한 원인인 "들어갔더니 사람이 없다"를 정면으로 피한다.

**지급 주기 자체도 콜드스타트에 맞춰 가변으로 둔다.** 초기에는 후보 풀이 얇으므로 **주 2회(월·목)**로 시작하고, 지역그룹별 활성 사용자 수가 늘어나면 단계적으로 지급 빈도를 늘린다(정확한 임계치는 13장 미결 항목). 매일 지급을 기본값으로 못박지 않는 이유는, 사람이 적은 상태에서 매일 카드를 돌리면 같은 후보가 반복 소진되어 오히려 카드 품질이 떨어지기 때문이다.

부수 효과로, **벡터 매칭의 품질이 곧 제품 품질이 된다.**
상위 20명을 뽑을 때는 순위가 조금 틀려도 티가 안 나지만, **상위 1명만 뽑으면 알고리즘이 전부**다.

### 1.2 남은 최대 위험

**성비 불균형**이다. 출시 전까지 대응 방침을 정해야 한다 (12장 미결 항목).

## 2. 제품 규칙 (핵심 동작)

### 2.1 카드 지급

| 규칙 | 내용 |
|---|---|
| 지급 시각 | 지급일 **아침 7시** — 초기에는 **주 2회(월·목)**, 지역그룹별 활성 사용자 수 증가에 따라 단계적으로 확대(3회→4회→…, 최종 상한은 13장 미결 항목) |
| 지급량 | **성별 무관 1장** |
| 지급 방식 | 서버 배치(`pg_cron`)가 생성하고 **푸시 알림으로 통지** |
| 지급 주기 조정 | `region_group_settings`(가칭) 같은 작은 설정 테이블 값만 바꿔 조정 — 코드 배포·관리자 화면 없이 대시보드에서 직접 수정 |
| 추가 카드 | **단건 결제로 즉시 1장 더** (가격 미정, 12장 참조) |
| 재등장 | **거절한 상대는 다시 나오지 않는다** |

**채팅 개수로 카드 지급을 막는 규칙은 두지 않는다.** 대신 매칭 성사 후에는 2.5절의 "신뢰 확인 게이트"가 방치된 대화를 자연스럽게 정리하므로, 채팅이 쌓인다고 카드 지급까지 막을 이유가 없다.

### 2.2 수락 흐름

```
① A가 오늘의 카드에서 B를 수락
② B에게 알림 — "누군가 당신을 수락했습니다"
③ B가 "받은 수락함"에서 A의 프로필을 확인
④ B도 수락 → 매칭 성립 → 채팅 시작
   B가 거절 → 조용히 종료 (A에게 거절 사실을 알리지 않는다)
```

**한쪽 수락을 상대에게 알리는 이유**: B의 오늘 카드에 A가 없더라도 A를 보게 되므로 **매칭률이 크게 오른다.**
카드를 한 번에 소수만 지급하는 구조에서는 서로의 카드가 겹칠 확률이 낮아 이 경로가 필수적이다.

**거절 사실은 알리지 않는다.** 명시적 거절 통지는 사용자를 앱에서 떠나게 만든다.

### 2.3 카드를 다 쓴 뒤의 화면

- 오늘의 카드가 소진되면 **모자이크 처리된 프로필들이 배너로 보인다**
- "다음 카드는 O월 O일 아침 7시에 도착합니다" 카운트다운 (지급일이 매일이 아니므로 고정 문구가 아니라 다음 지급일을 계산해서 보여준다)
- **추가 카드 구매 버튼**

### 2.4 수익 모델

**2026-09-08 수정 — 등록비 게이트를 폐지했다.** 아래는 현재 확정 모델이다. 배경은 절 끝의 "가입비 폐지 결정 기록" 참조.

| 단계 | 내용 | 금액 |
|---|---|---|
| **가입** | 앱 이용 자격 | **무료 — 남녀 동일 0원, 결제 없음** |
| 이용 | 가변 주기 카드, 채팅 무제한 | 무료 |
| 소모품 | 추가 카드 | **하트 50개(2,000원 상당).** 구매는 **다음 카드가 오기 전까지 언제든**, 열 수 있는 건 **지급 주기당 1장**(2026-09-08 수정). 산 카드는 갱신돼도 만료되지 않는다 |
| 소모품 | 아바타 재생성 | **최초 1회 무료, 이후 하트 10개(400원 상당).** OpenAI 이미지 생성 비용이 실제로 발생하는 유일한 지점 |
| 소모품 | ~~부스트 · 거절 되돌리기~~ | **폐기(2026-09-08 확정).** 부스트는 "돈 낸 사람이 더 노출된다"가 되어 큐레이션 공정성과 충돌하고, 거절 되돌리기는 이미 지나간 카드에 돈을 쓰는 것이라 환불 분쟁 소지가 크다 |
| 구독 | **도입하지 않는다** | — |

**하트(재화)가 이제 유일한 수익원이다.** 매칭·카드 조회·채팅 등 핵심 기능은 여전히 하트 없이 전부 이용 가능하다. 하트 소비처는 **추가 카드와 아바타 재생성 둘뿐**이며, 어느 쪽도 매칭 품질에 영향을 주지 않는다.

#### 하트 가격 정책 (2026-09-08 확정)

**기준 단가는 하트 1개 = 40원**이다. 추가 카드 1장(50하트 = 2,000원)을 기준점으로 삼아 역산했다.

| 하트 | 가격 | 개당 단가 | 할인 |
|---|---|---|---|
| 50 | 2,000원 | 40.0원 | 기준 |
| 100 | 3,800원 | 38.0원 | 5% (**추천 배지**) |
| 200 | 7,200원 | 36.0원 | 10% |
| 400 | 13,600원 | 34.0원 | 15% |

- **최소 번들이 정확히 카드 1장치다.** 경쟁사는 전부 최소 번들을 여러 번치로 묶어 잔액을 남기는데, 이걸 하지 않는 것이 §8.10 정직함 원칙과 맞고 차별점이 된다
- **할인을 얕게 건다.** 추가 카드는 지급 주기당 1장이라 소비량에 하드 상한이 있다. 대량 할인을 세게 걸면 다 못 쓰는 잔액이 쌓이고 환불 분쟁으로 돌아온다
- "추천" 배지는 가장 큰 번들이 아니라 **100하트(2장치)** 에 붙인다
- 경쟁사 대비 위치: 썸타임 좋아요 1회가 약 2,976원, 캠퍼스팅 하트 1개가 약 220원이다. CampusMate 추가 카드 2,000원은 **행동 단가 기준으로 경쟁사보다 명확히 싸다**

#### 사는 것과 쓰는 것을 분리한다 (2026-09-08 확정)

**결제는 막지 않고, 여는 횟수만 제한한다.** 원래는 "카드 지급일 당일에만 추가 카드를 살 수 있다"였는데, 이건 리듬을 지키는 대신 결제 자체를 막는 규칙이었다. 사고 싶은 순간(카드를 다 보고 아쉬운 순간)과 살 수 있는 순간이 어긋나면 리듬은 그대로인데 매출만 사라진다.

| 항목 | 규칙 |
|---|---|
| 하트 구매 | 제한 없음. 언제든, 원하는 만큼 |
| 추가 카드 구매·열기 | **지급 주기당 1장.** 다음 카드가 오기 전까지 언제든 |
| 구매한 카드의 수명 | **만료 없음.** 수락·거절을 누를 때까지 유지 |
| 무상 카드의 수명 | 다음 지급 때 만료, 상대는 재노출 대상으로 복귀(§13 미결31) |

- **상한 총량은 이전과 같다.** 주 2회 지급이면 월 8~9장으로, 지급일 당일 제한이 있던 때와 동일하다. 무료 하트로 얻는 월 4~5장을 빼면 결제 여지는 3~4장으로 유지된다 — **창구만 넓혔고 천장은 그대로다**
- **갱신 직전 구매가 증발하면 안 된다.** 갱신 한 시간 전에 산 카드가 한 시간 만에 사라지면 그건 기능이 아니라 결제 사고다. 구매한 카드는 **결정 대기 큐**(DESIGN.md §8.9)에 남아 오늘의 카드 화면에서 먼저 노출된다
- **결제 전에 고지한다.** 하트 스토어와 결제 확인 시트 양쪽에 "다음 카드가 올 때까지 한 장만 열 수 있어요 / 산 카드는 결정할 때까지 사라지지 않아요" 두 문장을 고정 노출하고, 옆에 FAQ 진입점을 둔다. 상한이 있는 재화를 팔면서 결제 후에 알리는 것은 환불 분쟁과 스토어 심사 양쪽에서 지는 방식이다

**구독제를 넣지 않는 이유**: 구독은 매달 새로운 가치를 제공해야 성립한다.
초기에는 사용자가 적어 그 가치를 줄 수 없고, "구독했는데 만날 사람이 없다"는 환불 요구로 이어진다.
사용자 규모가 확보된 뒤 재검토한다.

**채팅 횟수 제한은 두지 않는다.** 대화가 중간에 끊기면 돈을 내지 않은 쪽뿐 아니라
**상대방의 경험까지 망가진다.** 대신 매칭 앞단(카드 지급)도 채팅 개수로 막지 않고, 매칭 뒤에는 2.5절의 신뢰 확인 게이트가 방치된 대화를 정리하는 역할을 대신한다.

#### 가입비 폐지 결정 기록 (2026-09-08)

원래는 등록비(남 9,900원 / 여 0원, 가입 1회 결제)를 받는 모델이었다. 성별 차등 자체가
민원·논란 소지가 있고, 인앱결제 상품·가격이 스토어에 공개 등록되는 이상 숨길 수도 없어
**성별 차별 문제를 원천적으로 없애기로 하고 가입비를 완전히 폐지했다.** 대신 수익은
이미 확정돼 있던 하트 이코노미(§8.9·§8.10, 주기당 1장 초과 카드 = 50하트)로 단일화한다 —
새로운 과금 시점(예: 매칭 성사 시 재화 차감)은 만들지 않는다. 가입 플로우 자체가 더는
결제를 포함하지 않으므로, DESIGN.md 화면 9 "등록비 결제"(`purchase-sheet`)는 폐기한다.

**프로모션 코드는 별도 목적으로 유지한다.** 성별 차등을 우회하기 위한 용도가 아니라
(가입비 자체가 없으므로 그 목적은 소멸했다), 이벤트·마케팅용 범용 코드(예: 코드 입력 시
무료 하트 지급)로 남긴다. 발급 규칙(1코드=1계정, 발행량 상한 등)은 실제 이벤트 설계 시점에 정한다.

### 2.5 매칭 후 신뢰 확인 게이트 (경쟁사 조사 반영, 신규)

매칭 성사만으로는 "진지하게 대화할 의사"가 검증되지 않는다. 그래서 채팅 시작 후 일정 시점에 한 번, 서로 계속 대화할 의사가 있는지 확인하는 절차를 둔다.

```
매칭 성립(채팅 시작) → 24시간 경과, 아직 응답 안 한 상태로 채팅방 진입 시마다 다이얼로그 노출
                        (+ 24시간 시점에 푸시 알림 발송)
→ 48시간 응답 기한 안에 양쪽 모두 수락
    → 카카오톡 아이디 자동 공유 + 실사진 공개, 앱 내 채팅은 계속 병행 유지
→ 48시간 안에 한쪽이라도 거절(또는 무응답)
    → 48시간 후 채팅 삭제. 매칭 기록은 남기고 채팅만 닫는다(재노출 악용 방지).
      거절 사실은 상대에게 알리지 않는다(2.2절 원칙과 동일)
```

**48시간은 이 다이얼로그의 응답 기한일 뿐, 대화 전체를 상시 감시하는 규칙이 아니다.** 게이트를 통과한 뒤의 채팅은 자동 만료 없이 계속 열려 있으며, 필요하면 사용자가 직접 "채팅방 나가기"로 조용히 종료할 수 있다(상대에게 알리지 않음, 2.2절과 동일 톤).

**카카오톡 아이디는 온보딩이 아니라 이 다이얼로그 시점에 입력받는다.** 미리 받아두면 카톡을 안 쓰는 사용자도 강제 입력해야 해 이탈 요인이 되고, 매칭 전 어떤 카드/수락함 RPC 응답에도 이 값이 포함되면 안 된다(7.1절 원칙과 동일).

**이 게이트는 기존의 "채팅 5개 동시 상한"을 대체한다.** 상한을 없애 채팅을 무제한으로 열어주는 대신, 이 게이트가 서로 대화 의사가 없는 매칭을 자연스럽게 걸러내는 역할을 한다.

### 2.6 계정 상태 관리 — 일시중지 · 탈퇴 · 재가입 (2026-09-08 신규, 경쟁사 비교 그릴링)

**매칭 일시중지 토글.** 나의정보(설정) 화면에 온/오프 토글을 둔다. 꺼두면 새 카드 배치 대상에서 제외되고(조각 4 카드 배치 쿼리에서 제외), 기존 매칭·채팅은 그대로 유지된다. 탈퇴와 달리 데이터는 삭제되지 않는다. 휴학·시험기간처럼 카드만 잠시 멈추고 싶은 사용자를 위함(연픽 "매칭 활성화" 토글, 클럽트웬티 "일시중지" 벤치마킹).

**탈퇴 절차.** 클럽트웬티 패턴을 따른다: 설정 → "탈퇴하기" → 확인 화면(삭제되는 항목을 구체적으로 안내 — 프로필·매칭 기록·채팅 전부 영구 삭제, 되돌릴 수 없음을 명시) → "영구 삭제" 버튼(위험 액션이므로 이중 확인) → 즉시 처리. `phone_number`를 포함한 개인정보는 즉시 파기한다(§13 미결27과 연결). 화면은 DESIGN.md §9에 신규 추가한다.

**재가입 제한 — 탈퇴 후 2개월(확정, 2026-09-08).** 같은 대학 이메일로 2개월간 재가입을 막는다(클럽트웬티 사례와 동일). 탈퇴-재가입 반복으로 신고 이력을 세탁하거나 매칭 큐를 도는 악용을 막기 위함. 2개월로 정한 근거는 악용 차단에 충분하면서 정당한 복귀를 과도하게 막지 않는 선이라는 것이다. **잠시 쉬고 싶은 사용자에게는 탈퇴 대신 매칭 일시중지 토글을 안내한다** — 탈퇴 확인 화면에서 일시중지를 먼저 제시한다.

### 2.7 추천인 프로그램 (2026-09-08 신규, 경쟁사 비교 그릴링)

연픽의 "추천 코드 즉시 보상 + 월간 랭킹 시상"을 벤치마킹해 정식 추천인 프로그램을 도입한다.
가입비가 없어졌으므로 현금성 보상은 하지 않고 전부 하트(재화)로 지급한다.

- 가입 시 개인 추천 코드 1개를 자동 발급한다
- 신규 가입자가 가입 시 코드를 입력하면 **추천인 + 피추천인 양쪽에게 각각 50하트(카드 1장치)를 즉시 지급**한다 (2026-09-08 확정)
- 월간 랭킹(추천 성사 건수 기준) 상위 N명에게 추가 하트를 보상한다 — 상위 인원수와 보상량은 첫 코호트 운영 데이터를 보고 정한다
- **양쪽 50하트로 정한 근거**: 신규 가입자 1명 확보에 4,000원어치를 쓰는 셈인데, 소개팅 앱 실제 사용자 확보비가 보통 1만 원을 넘으므로 여전히 싸다. 보상이 정확히 카드 1장이라 체감도 명확하다
- 어뷰징 방지(자기추천·대포 계정)는 조각 7에서 구현한다 — 동일 기기·동일 전화번호 차단, 피추천인이 학생증 인증을 통과해야 보상 지급

### 2.8 지인 리뷰 (2026-09-08 신규, 핵심 차별점)

**소개팅 앱의 근본 문제는 자기소개를 본인이 쓴다는 것이다.** 아무리 잘 써도 신뢰의 근거가 되지 못한다. 지인 리뷰는 **대학 인증을 통과한 실제 지인이 남긴 평가**를 카드에 함께 노출해 이 문제를 구조적으로 해결한다. 경쟁사 5곳 어디에도 없는 기능이며, 이미 확정된 추천인 프로그램과 결합해 초대 동기를 하트 보상 이상으로 끌어올린다.

**작동 방식.** 추천 코드로 연결된 지인끼리 **양방향으로** 리뷰를 주고받는다.

- 신규 가입자는 온보딩에서 추천 코드를 입력한 **그 자리에서 추천인에게 리뷰를 작성**한다
- 추천인에게는 "○○님이 가입했어요, 리뷰를 남겨주세요" 푸시가 가고 거기서 작성한다
- 서로 써주는 구조라 품앗이처럼 보이지만 **실제로 아는 사이라 정직한 품앗이**다. 변별 신호는 평가의 높낮이가 아니라 "리뷰가 존재한다 = 실명 인증된 지인이 보증했다"는 사실 자체다
- **신규 가입자가 영원히 리뷰 0개로 남는 문제**를 양방향 구조가 해결한다

**가입하지 않은 사람은 리뷰를 쓸 수 없다.** 링크로 외부인이 쓰게 하면 부계정 자작이 쉬워져 신뢰의 근거가 무너진다. 대학 인증된 가입자만 쓸 수 있다는 점이 이 기능의 핵심 자산이다.

**형식.** 장점 태그(고정 목록에서 선택) + 자유 텍스트 한 줄.

**게시·삭제 정책 (심사 요건 연동).**

| 주체 | 권한 | 근거 |
|---|---|---|
| 리뷰를 받은 사람 | **삭제 불가** | 마음에 안 든다고 지우면 평판의 진정성이 사라진다 |
| 리뷰를 쓴 사람 | 삭제 가능 | 자기 글이고 오타·실수 정정 문의가 운영으로 몰리는 것도 막는다 |
| 운영자 | 신고 시 블라인드 | **애플 심사 지침 1.2는 UGC에 신고 수단과 24시간 내 조치 능력을 요구한다.** 조치 수단이 없으면 리젝된다. 국내법상 명예훼손 신고 시 임시조치 의무도 있다 |

**노출.** 카드에 전부 노출하되 가로 스크롤 또는 "더보기"로 접는다. 리뷰어는 **대학 로고 + 만화 아바타 + 마스킹된 이름(김○○) + 태그 + 자유 텍스트 한 줄**로 표시한다. 이름 마스킹은 매칭 전 이름을 서버 응답 단계에서부터 가린다는 기존 규칙을 그대로 따른다.

> **출시 전 리스크 — 대학 로고 상표권.** 대부분의 대학이 UI(University Identity) 사용 지침을 두고 무단 사용을 금지한다. 사용자가 실제 로고 사용을 선택했으므로, **출시 전 대상 대학의 UI 사용 지침을 확인**하고 거절당하면 자체 디자인 배지(대학 상징색 + 학교명 텍스트)로 폴백한다.

**남은 한계.** 지인을 많이 데려온 사람이 리뷰도 많아 유리해진다. 내성적인 사용자가 구조적으로 불리해지는 문제는 남아 있으며, 첫 코호트에서 리뷰 개수 분포를 보고 노출 방식을 재검토한다.

### 2.9 코호트 오픈 — 성비 불균형 대응 (2026-09-08 신규)

**성비 붕괴는 소개팅 앱이 실패하는 가장 흔한 원인이고, 한 번 무너지면 복구가 거의 불가능하다.** 그래서 전국 동시 오픈을 하지 않고 **학교별로 순차 오픈**한다.

```
학교 오픈 공지 → 14일 모집 기간(가입은 되지만 카드는 안 옴)
              → 예고한 날짜에 카드 지급 시작
```

- 모집 기간에는 **"N월 N일에 첫 카드가 열려요"를 명시**하고 남은 시간을 카운트다운으로 보여준다. 기존 `{type.countdown}` 48px 토큰을 그대로 재사용한다
- **재화 차등이 없다.** 소수 성별에게 하트를 더 주는 방식은 등록비 폐지로 해결한 성차별 문제를 재화 쪽에서 다시 만든다. 코호트 오픈은 그 논란 없이 첫 경험 품질을 확보한다
- **14일이 끝나면 성비와 무관하게 예고한 날짜에 연다.** 공지한 날짜를 미루면 대기자가 그대로 이탈하고 재유입이 안 된다
- 다만 **성비가 최소선에 못 미치면 지급 주기를 주 1회로 낮춰 시작**한다. 날짜 약속은 지키되 얇은 후보 풀에서 카드를 남발하지 않는다. 이후 §2.1 사다리에 따라 정상 주기로 올린다

**초기 사용자 확보 채널** (전부 병행):

| 채널 | 비용 | 코호트와의 궁합 |
|---|---|---|
| 에브리타임 학교별 홍보글 | 0원 | 학교 단위 타겟이라 가장 정확 |
| 추천인 프로그램 + 지인 리뷰 | 하트 | 리뷰를 받으려면 지인을 데려와야 해 동기가 강함 |
| 학과·동아리 단톡방 시드 | 0원 | 단톡방 하나가 수십 명을 한번에 데려옴 |
| 학교 방문 전단지 배포 | 인쇄비 | 한 학교 집중 공략 구조와 정확히 맞음 |
| 인스타그램 유료 광고 | 예산 | 확장은 빠르나 학교별 타겟이 부정확 |

## 3. 개발 전략 — 얇게 끝까지 관통시키기

기능을 하나씩 완성하는 대신, **가입부터 채팅까지 최소 구현으로 먼저 이어붙인다.**

1. 소개팅 앱은 루프가 한 군데라도 끊기면 가치가 0이다. 부분 완성은 검증되지 않는다.
2. **매칭 품질은 실제 프로필이 있어야만 판단할 수 있다.** 상상으로 벡터를 튜닝하면 안 된다.

### 3.1 작업 조각과 순서

| # | 조각 | 내용 |
|---|---|---|
| 0 | **기반 공사** | Flutter 프로젝트, Supabase 스키마, 라우팅, 규칙 문서 ← **이 문서** |
| 1 | 계정 · 학생인증 | ac.kr 이메일 가입, 인증코드, 허용 도메인, 지역 그룹 |
| 2 | 프로필 · 온보딩 | 사진, 자기소개, 설문, 태그, MBTI, 키, 학과 입력 |
| 3 | 벡터화 | 설문·텍스트를 벡터로 변환해 저장 |
| 4 | **큐레이션 카드 · 수락** | 배치 생성, 카드 화면, 수락/거절, 받은 수락함, 매칭 성립, **푸시 알림** |
| 5 | 채팅 | 매칭된 상대와 1:1 실시간 대화 |
| 6 | **안전** | 신고, 차단, 지인 차단(연락처 기반, 신규), 계정 삭제 — **애플·구글 심사 필수 요건** |
| 7 | **수익화 · 성장** | 인앱결제(하트 구매), 추가 카드, 아바타 재생성, 추천인 프로그램, **지인 리뷰(2.8절)**, **FAQ(DESIGN.md §8.13 — 결제 고지와 한 몸이라 여기서 함께 만든다)** — 유일한 수익원이라 **출시 필수** |
| 8 | 다듬기 | 디자인 시안 반영, 성능 |

**조각 7이 출시 필수인 이유**: 가입비가 없어져 가입 플로우 자체엔 결제가 없지만,
하트 이코노미(추가 카드 구매)가 **유일한 수익원**이라 이것 없이는 매출이 0이다.
개발 중에는 하트 구매를 막아두고 진행하되, 출시 전에 반드시 붙여야 한다.

각 조각은 **자기만의 설계 → 계획 → 구현 → 검토** 사이클을 갖는다.

**조각 4에 푸시 알림이 포함되는 이유**: 아침 7시 지급은 알림이 없으면 사용자가 카드가 온 줄 모른다.
푸시는 이 제품에서 부가 기능이 아니라 **핵심 동작의 일부**다.

### 3.2 만들지 않을 것 (명시적 제외)

1개월 MVP를 지키기 위해 아래는 의도적으로 만들지 않는다.

- 관리자 웹 화면 → **Supabase 대시보드로 대체**
- 임베딩 모델 자체 서빙 → **OpenAI API 호출**
- 추천 알고리즘 사전 튜닝 → **데이터가 쌓인 뒤에**
- 무한 스크롤 카드덱(스와이프 UI) → **제품 형태상 불필요**
- 정교한 디자인 → 조각 8로 이월
- 구독제·광고
- **오프라인 이벤트 제휴 채널** (경쟁사 연픽의 "일일호프"류) → 매칭 제품 핵심 가치와 결이 다른 별도 사업이라 도입하지 않는다 (경쟁사 조사 반영, 최종 결론)
- **매칭 외 체류 콘텐츠** → 익명 투표 커뮤니티(§13 미결14, DESIGN.md §8.11)만 조각 8에서 만든다. 미니게임/진단 콘텐츠(경쟁사 썸타임의 타로·페르소나진단류), 스토리형/블로그 콘텐츠는 **지금은 만들지 않는다** — 사용자가 어느 정도 모인 뒤 재검토 (2026-09-08 경쟁사 비교 그릴링에서 확정)
- **그룹/대면 미팅 기능** (경쟁사 썸타임 2:2, 연픽 미팅탭, 클럽트웬티 3:3) → 1:1 큐레이션이 핵심 차별점이라 이번 스코프에 넣지 않는다. 정산·인원매칭·노쇼처리 등 완전히 다른 서브시스템이 필요해 별도 스코프가 될 것 — 조각 0~7 완료 후 별도 브레인스토밍으로 재검토 (2026-09-08 경쟁사 비교 그릴링에서 확정)

### 3.3 iOS 빌드 (Mac 없음)

macOS 없이는 iOS 빌드와 앱스토어 제출이 불가능하다.

## 4. 아키텍처

### 4.1 계층

MVVM을 기본 골격으로 하고 Clean Architecture의 계층 분리를 결합한다. 과도한 추상화는 피한다.

| 계층 | 위치 | 역할 |
|---|---|---|
| View | `<기능>/view/` | 화면과 위젯. 표시와 이벤트 전달만 담당 |
| ViewModel | `<기능>/viewmodel/` | 흐름 제어. UiState 생성, View 이벤트 처리 |
| Model | `<기능>/model/` | 비즈니스 로직, 엔티티, Repository |

**의존성 방향은 항상 안쪽(Model)을 향한다.** Model은 View를 모른다.
ViewModel은 Flutter 위젯 타입(`BuildContext`, `Widget`)을 참조하지 않는다.

### 4.2 패키지 구조

```
lib/
├── auth/                  조각 1 — 학생인증
│   ├── model/             UniversityEmail, VerificationCode, AuthRepository
│   ├── view/              SignUpScreen, VerifyCodeScreen
│   └── viewmodel/         SignUpViewModel, SignUpUiState
├── profile/               조각 2
├── matching/              조각 3·4 — 벡터, 큐레이션 카드, 수락
├── chat/                  조각 5
├── safety/                조각 6 — 신고·차단
├── billing/               조각 7 — 추가 카드 결제
├── common/                값 객체, 확장, 에러 타입, Result
└── core/
    ├── supabase/          클라이언트 초기화, 테이블 상수
    ├── router/            go_router 라우팅
    ├── push/              FCM 초기화·토큰 관리
    └── theme/             디자인 토큰
```

### 4.3 상태 관리 — Riverpod

Riverpod의 `Notifier`는 **Flutter 위젯을 전혀 모르는 순수 Dart 클래스**로 작성할 수 있다.
"ViewModel이 UI 타입을 몰라야 한다"는 규칙이 자연스럽게 지켜지고, 위젯 없이 단위 테스트가 된다.

Provider는 `BuildContext`에 묶이고, BLoC은 이 규모에 비해 보일러플레이트가 과하다.

### 4.4 데이터 흐름

```
View --이벤트--> ViewModel --호출--> Model(Repository)
View <--UiState-- ViewModel
```

- 상태는 `UiState` 클래스 하나로 모아 노출한다 (필드별 상태 남발 금지)
- 일회성 이벤트(스낵바, 화면 이동)는 상태가 아니라 별도 이벤트로 처리한다
- 위젯은 상태를 직접 만들지 않고 받는다 (stateless 우선)

### 4.5 UseCase 사용 기준

항상 만들지 않는다. 아래일 때만 도입한다.

- 로직이 ViewModel에 두기엔 복잡하거나 여러 화면에서 재사용될 때
- 여러 도메인 객체를 조합해야 할 때

단순한 흐름이면 ViewModel이 Repository를 직접 호출한다.

## 6. 매칭 설계 (핵심)

| 자기 동물상 / 이목구비·인상 | **각 1종 선택, 필수** (동물상 8종·인상 5종) | 벡터 제외 — 상대 "선호"와 대조 (6.6a) |

| MBTI | 16종 선택 (모름 허용) | 표시 + 감점 계수 |

| **전화번호** | **필수, 평문(7절 예외)** | 점수 미반영 — 지인 차단(6.7) 대조 전용 |

**사진을 점수에 넣지 않는 것은 의도적이다.** 외모를 수치화하면 소수에게 쏠림이 극심해지고,
그 순간 벡터 매칭은 의미를 잃는다.

**동물상·인상은 사진 매력도 점수가 아니다.** 본인이 고른 "유형 태그"(강아지상/고양이상…,
선한상/시크상…)이고, 상대가 고른 "선호 유형"과 일치하는지만 본다 — MBTI 선호 토글과 같은
성격의 취향 대조다. 매력도 순위를 매기는 게 아니므로 위의 쏠림 문제가 생기지 않는다.
유저에게 점수·순위로 노출하지 않고 카드 배치 계수로만 쓴다. 반면 체형·몸무게처럼 매력도
서열로 직결되는 항목은 이 원칙에 걸리므로 입력받지 않는다.

### 6.2 성향 설문 — 10축 5점 슬라이더 (2026-09-10 개정)

**"나는 어떤가"만 한 번 묻는다.** 이전 설계는 축마다 "나 / 이상형"을 두 번 물어 `ideal_survey`를
만들었으나, 이 재질문(10화면)과 이상형 자유서술을 함께 폐지했다 — 근거는 6.3절. 성향 궁합은
이제 **두 사람의 실제 성향(`self_survey`)이 얼마나 가까운지**로만 잰다(대칭).

**입력 형식**: 문장형 버튼 3개 → **5점 슬라이더**로 교체(경쟁사 조사 반영 — 3단계는 중간값 근처
응답이 뭉개진다). 축당 1화면, 눈금 5개, 양 끝에 짧은 라벨. 눈금을 고르기 전까지 "다음으로" 비활성.

| # | 축 | 왼끝 ← → 오른끝 |
|---|---|---|
| 1 | 활동성 | 집콕 ↔ 밖으로 |
| 2 | 낯가림 | 낯가림 ↔ 금방 친해짐 |
| 3 | 계획성 | 즉흥적 ↔ 계획적 |
| 4 | 연락 빈도 | 필요할 때만 ↔ 자주 |
| 5 | 감정 표현 | 담백한 편 ↔ 표현이 풍부 |
| 6 | 음주 | 거의 안 마셔요 ↔ 자주 즐겨요 |
| 7 | 운동 | 거의 안 해요 ↔ 꾸준히 해요 |
| 8 | 관계 속도 | 천천히 알아가요 ↔ 확신하면 빠르게 |
| 9 | 새로움 | 익숙한 게 좋아요 ↔ 새로운 게 좋아요 |
| 10 | 학업·진로 | 여유로운 편 ↔ 몰입 중 |

헤드라인(질문) 전문과 슬라이더 스펙은 DESIGN.md §8.5 `trait-slider`에 있다. 슬라이더 10개는
탭·드래그로 빠르게 끝나 **1분 내외**를 예상한다(베타에서 재측정).

**벡터화**: 왼→오 5단계를 `−1, −0.5, 0, 0.5, 1` 로 매핑해 10차원 벡터 `self_survey` **한 개**를
만든다. 궁합 점수 공식(6.7절)은 연속값 기준이라 그대로 쓴다.

**점수 (대칭)**:
```
설문적합도 = 1 − (L2거리(A.self_survey, B.self_survey) ÷ 최대가능거리)
최대가능거리 = 2 × √10 ≈ 6.325     (10개 축이 각각 −1과 +1로 정반대인 경우)
```
두 사람 성향이 완전히 같으면 1, 전 축이 정반대면 0. 결과는 항상 0~1 범위다.
A→B와 B→A가 같은 값이므로 방향 구분이 없다(상보성 신호 없음 — 6.7절 참조).

**흡연**은 슬라이더에 넣지 않는다. "한다/안 한다" 2버튼으로 따로 받아 벡터 밖 감점 계수로만
쓴다(6.6a절). 5점 척도로 표현할 값이 아니고, 벡터에 섞으면 이분 변수가 연속 축을 왜곡한다.

### 6.3 벡터 2종 (2026-09-10 개정 — 4종에서 축소)

| 벡터 | 의미 | 차원 | 비교 방식 |
|---|---|---|---|
| `self_survey` | 내가 실제로 이런 사람이다 | 10 | **L2 거리** (대칭) |
| `self_text` | 내 자기소개 임베딩 | 512 | **코사인 유사도** (대칭) |

**폐지: `ideal_survey`(10), `ideal_text`(512).** 두 "이상형 벡터"를 모두 없앴다.

- `ideal_survey`: 성향 축을 이상형으로 재질문하던 10화면을 없앴다. 온보딩이 20문항 → 10문항으로
  줄고, 사용자가 "나"와 "이상형"에 사실상 같은 답을 넣는 경우가 많아 신호 대비 비용이 낮았다.
- `ideal_text`: "원하는 사람 서술" 자유 텍스트 입력 자체를 폐지했다. 6.9절에 적어둔 대로 "원함 ↔
  해당됨" 임베딩 유사도가 작동한다는 보장이 없었고, 온보딩의 유일한 자유 텍스트를 자기소개
  하나로 모으는 편이 낫다고 판단했다.
- **대신 이상형은 축소판으로 받는다**: 선호 동물상·선호 인상(각 최대 3) + 선호 MBTI(8극 토글,
  기존) + 선호 키 범위(기존). 전부 벡터가 아니라 감점 계수다(6.6a절).

**트레이드오프(사용자 확정)**: 성향·자기소개 둘 다 대칭 유사도라 **"비슷한 사람끼리"만
매칭된다.** 상보성(opposites attract) 신호가 어디에도 없다. 이상형 축소판 계수는 "특정 유형
선호"만 반영할 뿐, "나와 반대인 사람을 원한다"는 표현하지 못한다.

### 6.4 MBTI — 8개 극 토글, 감점 방식

**입력**: 8개 토글, 기본값은 전부 ok.

```
E ok/no    I ok/no    N ok/no    S ok/no
T ok/no    F ok/no    J ok/no    P ok/no
```

**한 축에서 양쪽을 모두 끈 경우는 "상관없음"으로 해석한다.**
한 축에서 켜진 극이 1개면 그 극을 선호하고, 0개거나 2개면 그 축을 보지 않는다.
이 규칙 덕분에 실수로 양쪽을 다 꺼도 "아무도 보이지 않는" 상태가 되지 않는다.

**상대의 MBTI가 "모름"이면 그 상대의 MBTI계수는 1.00으로 둔다.**
정보가 없다는 이유로 불이익을 주지 않는다.

**판정 예시** — 내 설정이 `E ok, I ok, N ok, S no, T ok, F no, J ok, P ok` 일 때

| 상대 | 판정 | 적합도 | 계수 |
|---|---|---|---|
| ENTJ | E✓ N✓ T✓ J✓ | 4/4 | 1.00 |
| ESTJ | E✓ **S✗** T✓ J✓ | 3/4 | 0.90 |
| ESFJ | E✓ S✗ F✗ J✓ | 2/4 | 0.80 |
| (전부 불일치) | — | 0/4 | 0.60 |

```
적합도(A→B)  = B의 4글자 중 A가 ok로 둔 글자 수 ÷ 4
양방향적합도 = √( 적합도(A→B) × 적합도(B→A) )
MBTI계수     = 0.6 + 0.4 × 양방향적합도        →  0.60 ~ 1.00
```

**아무도 배제하지 않는다.** 하드 필터로 만들면 후보가 6.25%까지 줄어 카드를 만들지 못하는 날이 생긴다.

**MBTI를 성향 벡터에 섞지 않는 이유**: E/I는 설문의 낯가림·친밀도 형성 속도 축과, J/P는 계획성 축과 겹친다.
같은 정보를 두 번 세면 그 항목만 과대평가된다.

### 6.5 키 — MBTI와 동일한 감점 방식

```
키적합도(A→B) = 1.00   B의 키가 A가 지정한 범위 안
              = 0.85   범위에서 5cm 이내로 벗어남
              = 0.70   그 이상 벗어남
              = 1.00   A가 선호 범위를 지정하지 않음

키계수 = √( 키적합도(A→B) × 키적합도(B→A) )      → 0.70 ~ 1.00
```

**키는 필수 입력이고 프로필에 공개된다.** 소개팅에서 실제로 중요하게 여겨지는 정보이고,
숨길 수 있게 두면 미입력이 오히려 부정적 신호로 읽힌다.

**선호 키 범위는 선택이다.** 지정하지 않으면 이 항목이 점수에 관여하지 않는다.

### 6.6 학과 — 점수가 아닌 회피 필터

학과를 "비슷하면 가점"으로 다루지 않는다.
**같은 과 사람은 이미 아는 사이일 가능성이 높고, 교내 소개팅 앱에서 가장 피하고 싶은 것이
아는 사람에게 들키는 일**이기 때문이다.

`hide_same_major` 를 켠 사용자에게는 같은 학과를 하드 필터로 제외한다. 기본값은 꺼짐이다.

### 6.6a 흡연 · 동물상 · 인상 계수 (2026-09-10 신규)

세 항목 모두 벡터가 아니라 **MBTI·키와 같은 감점 계수**다. 하드 필터가 아니므로 아무도 배제하지
않는다(6.5·6.4 원칙). 기본 하한을 둬서 곱해도 0이 되지 않는다.

**흡연 계수** — 두 사람의 흡연 여부(각자 "한다/안 한다")를 비교한다.

```
흡연계수 = 1.00   두 사람의 흡연 여부가 같음
         = 0.85   다름 (비흡연 ↔ 흡연)
```

별도 "상대 흡연 선호" 문항은 두지 않는다. 흡연 여부는 본인 값만 받고, 서로 다르면 대칭으로
감점한다. 0.85는 베타에서 재측정한다.

**동물상·인상 계수** — 내가 고른 "선호 유형"에 상대의 "본인 유형"이 들어있는지 본다(방향성).
MBTI·키와 같은 양방향 기하평균으로 짝사랑을 막는다.

```
유형적합도(A→B) = 1.00   A가 선호 유형을 하나도 안 고름 (= 상관없음)
               = 1.00   B의 본인 유형이 A의 선호 목록에 있음
               = k      없음                    (동물상 k=0.85, 인상 k=0.90)

동물상계수 = √( 동물상적합도(A→B) × 동물상적합도(B→A) )      → 0.85 ~ 1.00
인상계수   = √( 인상적합도(A→B)  × 인상적합도(B→A)  )      → 0.90 ~ 1.00
```

- 선호는 각 **최대 3종**까지 다중 선택, 미선택은 "상관없음"으로 1.00 처리 — 실수로 다 비워도
  카드가 사라지지 않는다(MBTI 토글과 같은 안전장치).
- 인상(이목구비) 계수의 하한을 동물상보다 높게(0.90) 둔 이유: 5종이라 자기 분류의 신뢰도가
  낮고, 8종인 동물상보다 약한 신호로 취급한다. 두 k 값 모두 베타에서 재측정한다.
- 동물상·인상은 **아바타 아트와 무관하다**(아바타는 §5.2 사진→만화 변환 그대로). 매칭 태그로만 쓴다.

### 6.7 최종 점수

**2026-09-10 개정** — 성향·자기소개가 대칭 유사도가 되면서 방향점수 개념이 사라졌다.
계수는 3종(흡연·동물상·인상)이 늘었다.

```
설문적합도  = 1 − ( L2거리(A.self_survey, B.self_survey) ÷ 2√10 )     (대칭, 0~1)
텍스트유사도 = ( 코사인유사도(A.self_text, B.self_text) + 1 ) ÷ 2       (대칭, 0~1)
              (자기소개 20자 미만이면 텍스트 항 제외, 설문 가중치 1.0)

궁합점수 = 0.6 × 설문적합도 + 0.4 × 텍스트유사도
           (A→B와 B→A가 같으므로 기하평균 불필요)

태그유사도 = |겹치는 태그| ÷ |둘의 전체 태그|        (자카드 유사도, 대칭)

최종점수 = (0.7 × 궁합점수 + 0.3 × 태그유사도)
           × MBTI계수 (0.60 ~ 1.00)
           × 키계수   (0.70 ~ 1.00)
           × 흡연계수 (0.85 ~ 1.00)      ┐
           × 동물상계수(0.85 ~ 1.00)      ├ 6.6a
           × 인상계수 (0.90 ~ 1.00)      ┘
           × 활동성계수
```

**대칭 모델이 짝사랑 매칭을 구조적으로 없앤다.** 예전엔 `ideal↔self` 방향이 A→B와 B→A로
갈려 한쪽만 좋아하는 카드가 나왔고, 그래서 기하평균으로 깎았다. 이제 성향·자기소개는 두 사람의
실제값을 직접 비교하므로 방향이 하나뿐이다. 선호 기반 계수(MBTI·키·동물상·인상)는 여전히
방향성이 있어 **각 계수 내부에서만 양방향 기하평균**을 유지한다.

**계수가 6개로 늘어난 데 대한 주의**: 최악의 경우 곱이 `0.6×0.7×0.85×0.85×0.9 ≈ 0.27`까지
떨어진다(활동성 제외). 각 항의 하한이 0보다 커서 완전 배제는 아니지만(6.5 원칙), 실제로 모든
계수가 동시에 바닥을 치는 후보는 드물다. 첫 코호트에서 최종점수 분포를 보고 계수 하한이나
가중을 조정한다.

**비중 요약**

**지인 차단 판정**: `contact_blocks`에 별도 대칭 기록을 만들지 않는다. "내가 상대의 번호를 차단 목록에 올렸는가" 또는 "상대가 내 번호를 차단 목록에 올렸는가" 둘 중 하나만 성립해도 양쪽 다 서로의 카드 후보에서 빠진다 — 쿼리 시점에 양방향으로 대조한다(7.2 참조). 어느 쪽에도 제외 사실을 알리지 않는다(완전 침묵, 기존 `blocks` 원칙과 동일).

**활동성 계수는 소수 큐레이션 구조에서 특히 중요하다.**
유령 계정에게 그 지급일의 유일한 카드를 낭비하면 사용자는 다음 지급일까지 통째로 잃는다.

### 6.8 카드 생성 쿼리

pgvector를 택한 핵심 이유가 여기에 있다. **필터와 벡터 연산이 하나의 SQL 안에서 끝난다.**

```sql
-- pick_daily_card(owner uuid) — 상위 1명을 반환
where 상대_성별 = 나의_찾는성별
  and 상대_찾는성별 = 나의_성별
  and 지역그룹 일치  and 상태 = 'active'
  and 아직 카드로 받은 적 없음  and 서로 차단하지 않음
  and 서로 지인 차단하지 않음(phone_number 양방향 대조)
  and (hide_same_major 가 켜져 있으면) 학과가 다름
order by 최종점수 desc limit 1
```

**성능**: 수천 명 규모에서는 인덱스 없이 전체 스캔해도 수십 밀리초다.
벡터가 수만 개를 넘을 때 HNSW 인덱스를 추가한다. 지금 붙이면 정확도만 손해다.

**교체 가능성**: 카드 생성은 `MatchingRepository` 인터페이스 뒤에 둔다.
나중에 전용 벡터 DB로 옮길 때 구현체 하나만 교체하면 되고, ViewModel과 화면은 손대지 않는다.

### 6.9 알려진 기술적 불확실성

**2026-09-10 — "원함 ↔ 해당됨" 문제는 설계로 해소했다.** 예전 우려는 *"원하는 사람 서술"*
임베딩과 *"상대 자기소개"* 임베딩의 코사인 유사도였다. 임베딩은 "같은 주제인가"는 잘 잡지만
"원함 ↔ 해당됨" 관계를 학습한 게 아니라서, *"운동 좋아하는 사람이면 좋겠어요"* 와 *"저는 헬스를
3년째 하고 있어요"* 의 거리가 예상보다 멀 수 있었다. 이 절에 적어둔 대비책이 "자기소개 ↔
자기소개 비교로 전환"이었고, `ideal_text` 폐지로 그 전환을 실행했다.

**남은 불확실성**: 자기소개가 서로 비슷하다고 해서 잘 맞는 사이인지는 여전히 미검증이다.

- **대비책**: 텍스트 비중은 28%뿐이고 설문(42%)과 태그(30%)가 뼈대를 이룬다
- **검증 시점**: 조각 3에서 실제 데이터로 확인한다. 결과가 나쁘면 `self_text` 비중을 낮춘다
- 상보성 신호가 전혀 없다는 점(6.3절 트레이드오프)도 첫 코호트 매칭 만족도로 재검토한다
- 지금 더 파고들지 않는다. 진짜 프로필이 쌓여야만 답이 나온다

## 7. 보안과 권한

소개팅 앱은 데이터가 유출되면 서비스가 끝난다. 가장 중요한 장이다.

**개인정보 최소수집 원칙**: 주민등록번호 등 민감정보는 수집하지 않는다. 통신사 본인인증(경쟁사 연픽이 주민번호 앞 7자리를 수집)도 도입하지 않는다. 아래 두 가지만 명시적 예외로 두고, 그 밖에는 이 원칙을 유지한다.

**예외 1 — 지인 차단용 전화번호(신규, 필수 수집으로 수정)**: 지인 차단 기능(6.7·5.3 참조)은 상대의 등록된 전화번호와 대조해야만 동작하므로, `profiles.phone_number`를 평문으로 신규 수집한다. 이 필드는 (1) 로그인·인증에 전혀 관여하지 않고, (2) **회원가입 시 전 사용자에게서 필수로 수집한다** — 지인 차단 기능 자체(연락처 목록에서 차단할 사람을 고르는 것, `contact_blocks`)는 여전히 선택이지만, 번호 등록만큼은 미참여자도 걸러질 수 있어야 하므로 필수로 둔다(사용자 결정, §13 결정 26), (3) 타 사용자에게 API로 노출되는 경로가 없다(7.1 RPC 원칙 적용). 이제 전체 가입자를 대상으로 하는 평문 PII 컬럼이므로 출시 전 법무 검토가 더 시급하다(§13 미결 27).

**예외 2 — 실명 `real_name`(2026-09-10 신규, 필수 수집)**: 이전에는 "학생증에서 학교명만 대조하고 실명은 추출·저장하지 않는다"였으나, **같은 학교 타인의 학생증을 도용하는 경로**를 막기 위해 방침을 바꿨다. `profiles.real_name`을 회원가입 시 전 사용자에게서 평문으로 받는다. 이 필드는 (1) 로그인·인증에 관여하지 않고, (2) 학생증 OCR 이름 대조(7.3절)·검증 수동 재검토·신고 분쟁 시 운영자 조회에만 쓰이며, (3) **카드·프로필·매칭 등 사용자에게 보이는 어떤 경로에도 실리지 않는다** — 타 사용자 대상 RPC 응답에서 서버가 제거하고, 본인만 설정 > 계정 정보에서 조회한다. OCR로 학생증에서 읽어낸 이름은 대조 직후 폐기하며, 시스템이 보관하는 실명은 사용자가 입력한 `real_name` 하나뿐이다. 전체 가입자 평문 PII 컬럼이 하나 더 늘어난 것이므로 출시 전 법무 검토 범위에 포함한다(§13 미결 27).

### 7.1 원칙 — 앱은 `profiles` 를 직접 조회하지 않는다

RLS는 행 단위라 "이 사람의 이 컬럼만"을 표현하지 못한다. 그래서 경로를 나눈다.

**2026-09-12 확정 — 백엔드를 FastAPI(비즈니스 로직) + Supabase(Auth·DB·RLS·Storage)로 나눈다.** 이전엔 "필요한 컬럼만 반환"을 Postgres RPC 함수로 구현했으나, 이제 그 역할을 FastAPI 엔드포인트가 맡는다. FastAPI는 요청에 실린 Supabase JWT를 검증한 뒤에만 동작하므로, RLS·Auth라는 신뢰 축은 그대로 유지된다(Supabase Auth+RLS는 폐기하지 않는다).

| 접근 대상 | 방식 |
|---|---|
| 내 프로필 | `profiles` 직접 조회 — RLS가 `id = auth.uid()` 만 허용 (Flutter → Supabase 직접) |
| 오늘의 카드 | **FastAPI 엔드포인트로만** — JWT 검증 후 필요한 컬럼만 골라 반환 |
| 받은 수락함 | **FastAPI 엔드포인트로만** |

이 구조에서는 앱 코드에 버그가 있어도 **남의 이메일·연락처가 나갈 경로 자체가 없다.**

**모자이크 배너**는 실제 사진을 내려주고 앱에서 흐리게 처리하는 방식이 아니라,
**서버가 처음부터 흐린 이미지만 내려준다.** 앱에서 처리하면 원본이 이미 기기에 도착해 있어 우회 가능하다.

### 7.2 테이블별 RLS 정책

| 테이블 | 정책 |
|---|---|
| `daily_cards` | **본인에게 발급된 카드만 조회** |
| `card_decisions` | **본인이 내린 결정만 조회.** 상대의 거절 여부를 알 수 있으면 안 된다 |
| `matches` | 당사자 2명만 |
| `messages` | 해당 match에 속한 2명만. 매칭이 해제되면 접근도 끊긴다 |
| `blocks` | 차단한 사람만 조회. **차단당한 쪽은 자신이 차단됐음을 알 수 없어야 한다** |
| `reports` | 신고자는 쓰기만, 읽기는 관리자만 |

### 7.3 학생인증 강제 지점

Supabase Auth는 기본적으로 아무 이메일이나 받는다.
**Auth Hook**을 걸어 가입 시점에 `universities.email_domain` 화이트리스트를 검사하고,
목록에 없는 도메인은 거부한다.

앱 화면에서만 막으면 API를 직접 호출해 우회할 수 있다.

**학생증 사진 검증도 함께 강제한다(경쟁사 조사 반영, 신규).** 이메일 인증만으로는 클럽트웬티처럼 "미인증 배지가 붙은 채로 진행"되는 신뢰성 리스크가 있다고 판단해, 학생증/학생카드 사진 검증을 추가한다.

**실명(`real_name`)은 이 화면에서 학생증 업로드와 함께 입력받는다**(2026-09-10, DESIGN.md 화면 3b). "학생증에 적힌 이름과 같게 입력하세요" 안내를 두고, 업로드 즉시 아래 OCR 대조가 실행되도록 온보딩 1(화면 4)보다 앞에 배치한다. 온보딩 1에는 닉네임·생년·키·전화번호·성별·MBTI만 남는다.

- 자동 1차: OCR로 학생증에서 **학교명 + 이름**을 추출한다(2026-09-10 개정 — 이전엔 학교명만).
  - **학교명**을 이메일 도메인으로 이미 확인된 학교와 대조한다. 불일치면 **자동 반려**(기존과 동일)
  - **이름**을 사용자가 입력한 `real_name`과 대조한다. 불일치면 반려하지 않고 **수동 검토 큐로 회부한다** — 이름 OCR은 가림·글꼴·조명으로 오탐이 잦아 자동 반려하면 정상 사용자를 막는다
  - **OCR로 읽어낸 학교명·이름 문자열은 대조 직후 폐기한다.** 시스템이 보관하는 실명은 사용자가 입력한 `real_name` 하나뿐이다(§7 예외 2)
- 애매하거나 자동 대조에 실패하면(이름 불일치 포함) 사람이 "진짜 학생증처럼 보이는가 + 이름이 입력값과 같은가"를 육안으로 재검토한다
- 검증 결과(boolean)만 `profiles.student_id_verified`에 남기고 원본 이미지는 검증 직후 즉시 삭제한다
- 검증이 끝나기 전까지 사용자는 온보딩 화면에 머무르며 다른 기능에 접근할 수 없다
- 업로드된 실사진 자체는 `google_mlkit_face_detection`(Flutter, 온디바이스)으로 얼굴 존재 여부를 기기 안에서 검증한다. 얼굴이 없으면 업로드를 막고 재촬영을 요구한다. **구현 후 실기기 테스트로 검증을 마쳐야 한다**(8.5절 테스트 전략)

### 7.4 사진

Storage 버킷은 **비공개**로 두고 서명 URL로만 내려준다.
공개 버킷이면 URL을 아는 누구나 볼 수 있고, 크롤링 시 전체 사진이 통째로 유출된다.

### 7.5 비밀키

**OpenAI API 키를 Flutter 앱에 넣지 않는다.** 앱은 디컴파일되면 키가 그대로 노출된다.
OpenAI를 호출하는 모든 경로는 **FastAPI 서버에서만** 수행하고, 키는 서버 환경변수에 둔다(2026-09-12: Supabase Edge Function에서 FastAPI로 이전).

| FastAPI 엔드포인트 | 용도 | 비고 |
|---|---|---|
| 임베딩 생성 | `bio` → `self_text`(512) 벡터 | **2026-09-10: `ideal_text` 임베딩 제거** — 이제 자기소개 한 종류만 임베딩한다(6.3) |
| 아바타 변환 | 실사진 → 만화 아바타 이미지 | §5.2, 모델 미정(§13 미결7) |
| 자기소개 다듬기 (구 `polish-text`) | **자기소개 AI 다듬기** (2026-09-10 신규) | 소형 모델. 라이트 터치(오타·비문·말투만, 길이 ±20%, 1인칭 유지, 없는 사실 추가 금지). moderation + 프롬프트 인젝션 방어 + 연락처·URL 포함 시 거부. 온보딩 1회 + 프로필 수정 1회로 호출 제한 |

Supabase URL과 anon key는 `--dart-define` 으로 주입하고, `.env` 파일은 커밋하지 않는다. FastAPI 쪽 비밀키(OpenAI 키, 결제 검증 키, DB 서비스 롤 키)도 동일하게 서버 환경변수로만 주입하고 저장소에 넣지 않는다.

### 7.6 결제 검증 (조각 7)

**구매 여부를 앱이 판단하지 않는다.** 영수증은 반드시 서버(FastAPI, 2026-09-12: Edge Function에서 이전)에서 검증하고,
`entitlements` 갱신과 아이템 지급도 서버에서 수행한다. 앱이 판단하면 우회 결제가 가능하다.

**하트 차감도 서버에서 강제한다.** 앱 화면에서만 막으면 API를 직접 호출해 우회할 수 있다.
추가 카드 발급 API(FastAPI)는 `entitlements` 의 하트 잔액을 서버에서 확인·차감한 뒤에만 동작한다.
가입 자체엔 결제 게이트가 없으므로(2.4절, 2026-09-08 수정) 카드 조회·수락 API는 결제 상태를 확인하지 않는다.

푸시(`firebase_messaging`), 결제 패키지, **FastAPI 를 호출할 HTTP 클라이언트(`core/api/`)** 는 해당 조각에서 추가한다 — 조각 0은 여전히 Flutter+Supabase 스키마만 다루고, FastAPI 서버·클라이언트는 그 로직이 처음 필요해지는 조각(매칭·결제)에서 붙인다.
새 의존성 추가는 사전에 사용자에게 확인한다.

### 8.4 코딩 규칙 (Kotlin 프로젝트 규칙의 Dart 이식)

| 원칙 | Dart에서의 형태 |
|---|---|
| 원시값 포장 | `extension type` 또는 불변 클래스 (`UniversityEmail`, `Nickname`) |
| 일급 컬렉션 | 컬렉션 하나만 필드로 갖는 클래스 (`InterestTags`) |
| getter 노출 금지 | 필드는 `_private`, 행위 메서드만 공개 (UiState는 예외) |
| 인스턴스 변수 2개 이하 | Model 계층에 엄격 적용, UiState는 예외 |
| 들여쓰기 1단계 | early return, 컬렉션 함수 활용 |
| `else` 금지 | early return / `switch` 표현식 |
| 메서드 10줄 이하 | 위젯도 길어지면 하위 위젯으로 분리 |
| 축약 금지 | 완전한 단어 사용 (`id`, `url`, `ui` 등 통용 약어는 예외) |
| 한 줄에 점 하나 | 컬렉션 체이닝과 위젯 빌더 체이닝은 예외 |
| 명시적 파라미터 | Dart는 기본적으로 충족 |
| SOLID | 전 계층 적용 |

- 코드와 네이밍은 영어, 주석과 문서는 한국어
- 문자열과 색상은 상수/토큰을 통해서만 참조한다

### 8.5 테스트 전략

**모든 비공개(private)가 아닌 클래스는 테스트를 갖는다.**

| 대상 | 위치 | 방식 |
|---|---|---|
| 값 객체 · Model | `test/` | `package:test` 단위 테스트 |
| Repository | `test/` | 인터페이스 뒤 **Fake 구현**으로 검증 |
| ViewModel | `test/` | Riverpod 컨테이너 + Fake repository |
| 화면 · 위젯 | `test/` | `testWidgets` 위젯 테스트 |
| **RLS 정책** | `supabase/tests/` | **다른 사용자로 조회 시 0행이 나오는지 SQL로 검증** |

마지막 항목을 별도로 두는 이유: **RLS는 틀려도 앱이 정상 동작한다.**
테스트가 없으면 유출을 출시 후에야 알게 된다.

## 9. Git 전략

git flow를 따른다.

| 브랜치 | 역할 | 분기 원본 | 병합 대상 |
|---|---|---|---|
| `main` | 배포된 릴리스만. 직접 커밋 금지 | — | — |
| `develop` | 개발 통합 브랜치 | `main` | — |
| `feature/*` | 기능 단위 개발 | `develop` | `develop` |
| `release/*` | 릴리스 준비 | `develop` | `main` + `develop` |
| `hotfix/*` | 긴급 수정 | `main` | `main` + `develop` |

브랜치명은 kebab-case. 조각 0은 `feature/foundation-setup`.

커밋 메시지는 Conventional Commits 형식, 타입은 영문 소문자, 설명은 한국어.
범위(scope)는 기능 패키지명(`auth`, `profile`, `matching`, `chat`, `safety`, `billing`, `core`)을 쓴다.

**커밋과 푸시는 사용자가 직접 수행한다.** 작업 완료 시 커밋 메시지 초안만 제안한다.

## 12. 디자인

디자인 시안은 아직 없다. **문서 작업 완료 후 Pencil로 시안을 작성하고 `DESIGN.md` 를 별도로 만든다.**

따라서 조각 0~7에서는 다음을 지킨다.

- 색상·간격·타이포는 `core/theme/` 의 **디자인 토큰을 통해서만 참조**한다
- 위젯 안에 색상 리터럴이나 하드코딩된 수치를 쓰지 않는다
- 크기는 화면 비율에 대응시킨다 (아이콘 크기·코너 반경 등 고정이 맞는 값은 예외)

시안이 확정되면 **토큰 값만 교체**하면 되도록 만든다.
