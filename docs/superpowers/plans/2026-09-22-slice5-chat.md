**Goal:** 매칭된 두 사람이 **1:1 로 글을 주고받고**, 매칭 성립 24시간 뒤에 **신뢰 확인 게이트**(카카오톡 아이디
공유 여부)를 묻고, **48시간 안에 양쪽이 수락하면 카카오톡 아이디와 실사진을 공개**하고, 아니면 **대화를 닫는**
데까지 만든다. 신고·차단은 조각 6, 하트 소비는 조각 7 이다.

**Architecture:** **보내는 건 FastAPI, 받는 건 Supabase Realtime** 이다. 쓰기는 전부 FastAPI 가
`service_role` 로 한다는 원칙(설계 §7.1)은 그대로 두고, 앱은 `messages` 테이블의 INSERT 이벤트만 구독한다 —
ERD §2 가 이미 `messages` 에 "참여 중인 매칭의 메시지" 읽기를 열어 뒀기 때문에 구독에도 같은 RLS 가 그대로
걸린다. 구독은 **채팅방을 열고 있는 동안만** 하고, 대화 목록(13)은 푸시와 당겨서 새로고침으로 갱신한다.
게이트의 시계는 `matches.created_at + 48시간` 하나뿐이고(설계 §2.5), **매시 정각에 도는 배치**가 ①
24시간을 막 넘긴 미응답자에게 리마인드 푸시를 보내고 ② 48시간을 넘긴 매칭에 `chat_closed_at` 을 찍는다.
조각 4 와 같은 방식으로 **상태 컬럼도 정리 배치도 두지 않는다** — 닫힘은 `chat_closed_at` 한 칸, 게이트
통과는 `trust_passed_at` 한 칸이고 나머지는 조회 시점에 판정한다. 다만 **수락은 24시간을 기다리지 않는다**
(결정 10 "미리 수락") — 매칭 순간부터 수락할 수 있고 양쪽이 수락한 순간 바로 공개된다. 24시간은 이제
**"아직 아무도 수락 안 한 방에 리마인드를 보내는 시점"** 일 뿐이다.

**채팅에는 사람이 쓰지 않은 줄도 섞인다**(결정 7 나가기 · 결정 10 미리 수락). 그래서 `messages` 에
`kind` 한 칸을 둔다 — `text` 는 말풍선, 나머지는 시스템 줄(pen `CbXi6` SystemMessage)로 그린다.
**별도 테이블도, 별도 API 도 만들지 않는다**: 시스템 줄도 그냥 메시지라서 목록의 마지막 줄 · 안 읽은 수 ·
푸시 · Realtime 구독이 전부 공짜로 따라온다.

### 결정 7 "나가기가 상대에게 보인다" 가 정확히 무엇인가

| 누가 | 무엇을 본다 |
| --- | --- |
| 나간 사람 | 대화 목록에서 **즉시 사라진다.** 그 방의 메시지도 더는 못 읽는다(RLS `left_at is null`) |
| 남은 사람 | 채팅창에 시스템 줄 **"{닉네임}님이 채팅방을 나갔어요"**, 입력창이 잠긴다. 목록에는 **그대로 남아** 지난 대화를 계속 볼 수 있고, 본인이 나가야 사라진다 |
| 게이트 | 한쪽이 나간 방은 **24시간 리마인드 · 48시간 마감에서 빠진다.** 닫을 사람이 없는데 닫아 봐야 남은 사람의 기록만 감춰진다 |

### 결정 10 "미리 수락" 이 정확히 무엇인가

| 시점 | 화면 | 동작 |
| --- | --- | --- |
| 매칭 직후 ~ 24시간 | 채팅방 위 **안내 배너**(pen `teNRJ` Notice 재사용)에 수락 버튼 하나. **거절 버튼은 두지 않는다** — 첫날 홧김에 누른 거절을 48시간 동안 되돌릴 수 없게 되는 게 더 나쁘다 | 누르면 확인 다이얼로그 → 수락 |
| 24시간 이후 | 기존 14f 시트가 방에 들어올 때마다 뜬다("수락" / "거절하고 나가기" — 결정 11) | 그대로 |
| 한쪽 수락 | 상대 채팅창에 **"{닉네임}님이 카카오톡 아이디·실사진 공개를 수락했어요"** 시스템 줄 + 푸시 1건 | `kind = 'trust_accept'` |
| 양쪽 수락 | **그 순간 공개**(48시간을 기다리지 않는다). `trust_passed_at` 기록 → 14b 시스템 카드 | 기존 B3 Step 2 그대로 |
| 거절 | **나가기와 같다**(결정 11) — `kind='left'` 시스템 줄 · 내 목록에서 방이 사라진다 | `POST /leave` |

**확인 다이얼로그 문구**(pen 없음 — 나가기 확인과 같은 기존 다이얼로그 스타일로):
"수락하면 채팅창에 수락했다는 문구가 상대에게 전송됩니다." / 취소 · 수락.

### 결정 11 "거절 = 나가기" 가 코드에서 무엇을 지우는가

| 사라지는 것 | 대신 |
| --- | --- |
| `POST /trust` 의 `{"decision": "reject"}` 경로 | `POST /leave` 하나. `/trust` 는 **수락 전용**이 되고 바디가 없어진다 |
| `trust_response` 에 `'reject'` 를 쓰는 코드 | 아무 것도 쓰지 않는다. **거절한 사람은 `left_at` 으로만 남는다** |
| "거절 뒤 14h 배너" 상태 | 거절하면 방에서 나가므로 그 화면을 볼 사람이 없다(14h 는 아래처럼 조건이 바뀐다) |
| "거절은 상대에게 안 보인다" 규칙 | **수락 · 거절 · 나가기 전부 보인다.** 예외가 없어진다 |

`match_participants.trust_response` **컬럼과 `card_decision` enum 은 그대로 둔다.** enum 은 조각 4 의
`card_decisions` 가 같이 쓰고 있어 없앨 수 없고, 컬럼을 지우려면 마이그레이션이 하나 더 드는데 얻는 게
없다. **이제 이 칸에 들어가는 값은 `'accept'` 아니면 null 둘뿐이다** — ERD 설명만 그렇게 고치면 된다
(마이그레이션 불필요).

## Global Constraints

- **새 테이블은 RLS 를 켜고, `revoke all ... from anon, authenticated, service_role` 뒤 필요한 것만 grant**
  한다(`docs/SUPABASE.md` §5). `messages` 에 여는 것은 `authenticated` 의 `select` 하나뿐이다(ERD §2).
- **RLS 정책의 `auth.uid()` 는 `(select auth.uid())` 형태로 쓴다**(기존 정책과 같은 모양, initplan 최적화).
  새 함수를 만들면 `security definer` 없이 `set search_path = ''` 를 걸고 식별자를 `public.` 으로 수식한다.
- **마이그레이션 파일명은 `supabase migration new <name>` 으로만 만든다. 이미 클라우드에 적용된 파일은
  절대 수정하지 않는다** — 새 파일만 추가한다.
- **클라우드 적용 금지.** Part C 는 파일 작성 + 로컬 스택(`supabase db reset`, `supabase test db`)까지다.
- **키 · URL · project ref · `service_role` 키를 저장소에 쓰지 않는다.** 배포 문서에는 시크릿 **이름만** 적는다.
- **커밋 · PR 에 AI/도구 표식을 넣지 않는다**(`[[feedback-no-tool-attribution]]`). 커밋 형식은
  `<이모지> <타입>(<scope>): <한국어 요약>`, **`git add -A` 금지**(파일 이름으로만 스테이징).

```sql
create table public.messages (
  id uuid primary key default gen_random_uuid(),
  match_id uuid not null references public.matches (id) on delete cascade,
  sender_id uuid not null references public.profiles (id) on delete cascade,

  -- 결정 7·10: 사람이 쓰지 않은 줄이 섞인다. text 는 말풍선, 나머지는 시스템 줄로 그린다.
  -- 새 종류가 생기면 값을 늘린다 — 테이블을 나누지 않는다.
  kind text not null default 'text'
    check (kind in ('text', 'left', 'trust_accept')),

  body text not null,
  created_at timestamptz not null default now(),

  -- 길이 상한은 서버(pydantic)와 DB 양쪽에 둔다. 빈 문자열·공백만 있는 메시지는 막는다.
  constraint messages_body_length check (char_length(btrim(body)) between 1 and 1000)
);

comment on table public.messages is
  '매칭 대화의 메시지(ERD §4). 쓰기는 FastAPI 전용, 읽기는 참여 중인 당사자만';
comment on column public.messages.kind is
  'text=사람이 쓴 말풍선 / left=나감 / trust_accept=한쪽 수락. sender_id 는 그 일을 한 사람';

-- 방을 열면 "이 매칭의 최근 50건"을 시간 역순으로 읽는다. 목록 화면의 마지막 메시지도 같은 인덱스를 탄다.
create index messages_match_created_index on public.messages (match_id, created_at desc);
```

**`kind` 를 둘러싼 판단 세 가지**(master 결정, 대장 요청대로 적어 둔다)

1. **시스템 줄도 `messages` 행이다.** 따로 테이블을 만들면 목록의 마지막 줄 · 안 읽은 수 · Realtime 구독 ·
   푸시를 전부 두 벌로 만들어야 한다. 한 칸 추가가 제일 싸다.
2. **`body` 에는 완성된 한국어 문장을 넣는다**(앱이 조립하지 않는다). 닉네임이 나중에 바뀌어도 그때의 문장이
   그대로 남는데, 그게 오히려 기록으로 맞다. 앱은 `kind != 'text'` 면 `CbXi6` SystemMessage 로 그리기만 한다.
3. **양쪽 수락(공개) 순간에는 행을 넣지 않는다.** 14b 시스템 카드는 `matches.trust_passed_at` 에서
   그린다는 ERD §4 규칙이 이미 있고, 거기에 맞춘다.

**14b 시스템 카드(`trust_passed_at` 기반)만 예외이고, 나머지 시스템 줄은 전부 `messages` 행이다.**

```sql
-- 참여 중인 매칭의 메시지만. 채팅방을 나간 사람(left_at)은 자기 대화도 더 못 읽는다.
create policy "messages are readable by active participants"
  on public.messages
  for select
  to authenticated
  using (
    exists (
      select 1
      from public.match_participants mp
```

### Task B2 — 검사 순서 (Step 2)

계획서 Step 2 는 "**인증이 입력 검증보다 먼저다**(설계 §4.6) — 방 소유 확인이 본문 검증보다 앞에 온다" 라고 적었는데,
**실제 순서는 반대로 422 가 먼저다.** `send_message(match_id, body: MessageRequest, ...)` 처럼 본문을 인자로 받으면
FastAPI 가 핸들러 첫 줄을 실행하기 **전에** pydantic 검증을 끝내서, 빈 메시지·1,001자는 방 주인이 아니어도 422 로 떨어진다.
방 소유 확인(404)은 그 뒤다. 남의 방 번호를 넣어도 새어 나가는 정보는 "본문이 규칙에 맞는가" 뿐이라 그대로 두었다.
설계 §4.6 의 401 → 422 순서(인증 자체)는 지켜진다 — 여기서 어긋나는 것은 **소유 확인**과 본문 검증의 순서다.

### 커서 — `before` 하나에서 `before` + `before_id` 로

계획서 B2 표와 Task A3 Step 4 는 `?before=<가장 오래된 created_at>` 하나만 보내기로 했는데,

시각만 보내면 **같은 `created_at` 을 가진 두 줄이 경계에 걸릴 때 한 줄이 빠진다.**
PostgREST 쪽 조건도 `or=(created_at.lt.X,and(created_at.eq.X,id.lt.Y))` 로 같이 바뀌었다.

### 배치 응답에 `passed` 한 칸 추가

계획서 B3 는 `{"reminded": n, "closed": m}` 이었는데 실제 응답은 **`{"reminded": n, "closed": m, "passed": k}`** 다.
양쪽이 다 수락했는데 통과 도장(`trust_passed_at`)이 없는 방을 배치가 대신 찍은 수다 — `/trust` 가 도장 직전에 끊겼을 때
남는 자국이라, 그런 방은 닫지 않고 찍어 준다. **0 이 정상이고 계속 올라오면 `/trust` 가 중간에 끊기고 있다는 뜻이다.**
`backend/DEPLOY.md` §4-1 에도 같은 설명이 있다.

### `reminder_at` 의 8시 보정 — "그날 아침" 이 아니라 두 갈래다

계획서 docstring 은 "조용한 시간(22~8시)에 걸리면 **그날** 아침 8시로 민다" 인데, 구현은 두 갈래로 나뉜다
(`backend/app/chat/gate.py`): **22시 이후면 다음 날 8시**, **0~8시면 같은 날 8시**. 22~24시에 걸린 리마인드를
"그날 8시" 로 밀면 이미 지나간 시각이 되어 창이 영영 열리지 않는다. 밀어야 하는 이유(창이 한 시간짜리 한 번뿐)는 계획서 그대로다.
