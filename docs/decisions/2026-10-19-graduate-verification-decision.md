# 기술 결정 기록 — 졸업생 인증 도입 (2026-10-19)

> 이 문서는 "왜 졸업증명서 사진 + 사람 검수를 넣었는가"를 처음 읽는 사람(면접관 포함)도 따라갈 수 있게 적은 기록이다.
> 근거는 구현 계획서 `docs/superpowers/plans/2026-10-19-graduate-verification.md`(끝의 "구현 편차 기록" 16항목 포함)와 마이그레이션 · 서버 · 앱 코드다.
> 파일 이름은 `docs/decisions/` 에 날짜를 앞에 붙여 한 결정에 한 파일로 둔다(저장소에 결정 기록 폴더가 처음 생겼다 — 같은 모양으로 이어 쓴다).
> 표시: **[사용자 결정]** = 사용자가 직접 정한 것, **[대장 결정]** = 통합대장이 추천대로 확정한 것, **[확인 못 함]** = 이 문서를 쓴 담당이 직접 확인하지 못한 것.

## 0. 한눈에 보기

| 질문 | 답 |
| --- | --- |
| 무엇을 만들었나 | 학교 메일이 없는 **졸업생**이 졸업증명서 사진을 올리면 **사람(관리자)이 검수해** 학교 메일로 가입한 사람과 같은 상태로 가입을 이어 가게 하는 길 |
| 왜 | 졸업하면 학교 메일이 사라져 졸업생이 가입하지 못하고, 출시 초기 유입이 줄어든다는 사용자 판단 **[사용자 결정]** |
| 어떻게 믿나 | 사진만 믿지 않는다. 관리자가 증명서에 인쇄된 **문서확인번호를 발급 기관의 확인 사이트에서 직접 조회**한다. 글자 인식(OCR)은 입력을 미리 채우는 **힌트**일 뿐 최종 판단은 사람이다 |
| 개인정보는 | 사진 · 번호 · 이전 메일은 **결정(승인 · 반려)이 난 순간 지운다**. 남는 것은 학교 · 결정 · 시각 · **해시**뿐이다. 이름 · 생년월일은 어디에도 저장하지 않는다 |
| 지금 켜져 있나 | **코드 기본값은 꺼짐이고, 운영은 2026-10-19 에 켰다**(리비전 `00088-gh5`, 사용자 직접 승인 "졸업생 스위치 켜기 승인"). 켠 근거는 공개 출시 전이라 앱 사용자가 테스터뿐이고 사용자가 시험하려고 켠 것이다. 처리방침(노션)과 이용약관은 10-19 반영 완료. 스토어 개인정보 양식 · 법률 확인 · 실제 졸업증명서 판독 검증은 **공개 출시 전까지** 남은 일이다 |

용어 두 개. **HMAC** = 비밀 키를 섞어 만드는 되돌릴 수 없는 지문(같은 입력이면 같은 지문, 키가 없으면 역산 불가). **OCR** = 사진 속 글자를 컴퓨터가 읽는 것(여기서는 Google Cloud Vision `TEXT_DETECTION`).

## 1. 도입 계기

### 1-1. 사용자의 판단 **[사용자 결정]**

CampusMate 의 가입 규칙은 "학교 메일로 6자리 코드를 받아 인증"이다(소셜 로그인 + 학교 메일 1회). 졸업하면 학교 메일 계정이 닫히는 학교가 많아, **졸업생은 가입 단계에서 막힌다.** 사용자는 출시 초기(스토어 출시 10월 28일쯤, 카드 오픈 11월 2일)에 졸업생 유입이 줄어드는 것을 부담으로 보고 "출시 전에 넣는다"고 정했다(10-19). 계획서 D1 의 대장 추천은 "출시 후 약 1주 뒤 업데이트"였지만 사용자가 출시 전 구현으로 뒤집었다.

### 1-2. 이 기능이 이미 한 번 없어졌다는 맥락 (면접에서 물을 만한 부분)

- 2026-10-17 사용자가 **학생증 · 졸업증명서 사진 인증을 모두 없앴다.** 이유는 두 가지였다. ① 학생증은 AI 로 만들 수 있어서 사진만 받아서는 가짜를 가려낼 수 없고 받는 쪽만 개인정보 부담이 생긴다. ② 학교 메일 코드로 이미 학교를 증명했는데 사진을 또 올리고 사람 검수까지 기다리게 하는 것은 이중 검사다(`학생증_제거_계획_10-17.md`).
- 그때 졸업생은 "졸업생도 학교 이메일로 인증한다"로 정리됐다. 즉 **졸업생도 학교 메일이 있다고 가정**했다.
- 이틀 뒤 이 가정이 틀릴 수 있다는 판단(졸업 후 메일이 사라지면 가입 불가)으로 졸업생 길만 되살렸다.
- **10-17 의 제거 이유와 충돌하지 않게 설계가 달라진 점**: (a) 대상이 재학생 전체가 아니라 **학교 메일이 없는 졸업생만**이다. (b) 사진 한 장의 모양을 보고 판단하는 방식이 아니라 **증명서의 문서확인번호를 발급 기관이 확인해 주는 방식**이라 AI 로 만든 그림만으로는 통과하지 못한다. (c) 사진은 결정 즉시 지워서 "받는 쪽의 개인정보 부담"을 최소로 줄인다. (d) 서버 스위치로 배포와 공개를 떼어 놓았다(코드 기본 꺼짐, 운영은 10-19 켬).

## 2. 고려한 대안과 판단

| # | 대안 | 판단 | 이유 |
| --- | --- | --- | --- |
| A | **지금 그대로**(학교 메일만, 졸업생은 학교가 메일을 남겨 주면 가입) | 기각(보조책으로만 유지) | 졸업 후 메일이 닫히는 학교의 졸업생은 영영 못 들어온다. 졸업생이 쓰는 별도 도메인(예: 동문 메일)이 있으면 `university_email_domains` 에 행을 더해 풀어 주는 길은 출시 후 할 일로 남아 있으나(`출시후_할일` 1-8) 모든 학교를 못 구한다 |
| B | **사진을 올리면 OCR 이 읽고 자동 승인** | 기각 | 10-17 에 없앤 이유 그대로다. 글자는 그림으로도 만들 수 있다. 자동 승인에 쓰면 위조 한 장이 곧 통과다. OCR 은 번호 · 학교 글자를 읽어 관리자 입력 칸을 **미리 채우는 힌트**로만 쓴다 |
| C | **이전 학교 이메일로 인증 코드 발송** | 기각(선택 입력으로만 흡수) | 졸업하면 그 메일이 없어졌을 가능성이 바로 이 기능의 전제다. 또 "검증 안 된 메일을 `school_email_claims`(한 학교 메일 = 한 계정) · `signup_blocks`(재가입 제한)에 넣는" 순간 **남의 학교 메일을 먼저 적어 그 사람의 가입을 막는 선점 공격**이 열린다. 그래서 이전 메일은 **선택 입력, 읽기 전용 점검(이미 다른 계정 것인지 관리자에게만 경고)** 으로만 쓴다 |
| D | **네이버 · 지메일 같은 개인 메일 인증 코드** | 기각 **[사용자 · 대장 결정]** | 개인 메일은 학교나 졸업과 아무 관계가 없다. 코드가 맞아도 졸업생이라는 증거가 0 이다. 졸업생 길에 넣지 않는다 |
| E | **외부 서비스에 졸업 확인을 맡김** | 이번에는 하지 않음 | 새 계약 · 새 의존성(사용자 승인 필요) · 개인정보 위탁이 더해지고, 오픈까지 약 2주라 일정이 맞지 않는다. 이 항목은 저장소에 상세 비교 문서가 없고 대장 전달 요약에 따랐다 **[확인 못 함]** |
| F | **졸업증명서 사진 + 사람이 번호로 진위 확인** | **선택** | 위조에 가장 강한 확인(발급 기관 확인)을 쓰면서도 새 계약 · 새 의존성이 없다. 비용은 **관리자 한 사람의 시간**이다(운영자 1명 기준 "보통 1~2일 안에 알려 드려요"로 약속) |

## 3. 선택한 방식과 이유

**"가입 관문에 인증 방법 고르기를 끼우고, 졸업생 길은 사진 신청 → 글자 인식(힌트) → 관리자 웹 검수 → 승인 시 DB 함수 한 번에 프로필 · 기록 갱신"** (계획서 Architecture).

핵심 설계 선택은 여섯 개다. 각각 짧게 이유를 적는다.

1. **승인되면 학교 메일 사람과 "같은 상태"가 된다.** 승인 함수가 학교 메일 인증이 채우는 두 칸(`profiles.university_id` · `school_email_verified_at`)을 똑같이 채운다. 그래서 학과 입력(3c) · 온보딩 · 매칭 후보(`university_id` 로 조인) · 홈 통계가 **코드 변경 없이** 두 길을 같게 다룬다. 졸업생 표시용 칸(`graduate_verified_at`)은 따로 있지만 내부 칸이고 다른 사람에게 보이지 않는다(D2) — 졸업생이라는 이유로 카드 · 점수가 달라지지 않는다.
2. **새 표 + 새 버킷을 쓴다.** 옛 학생증 표(`student_verification_attempts`)를 재사용하지 않았다. 옛 표는 상태가 enum 이라 값을 못 지우고, 상태를 바꾸는 순간 옛 트리거가 "학생 인증을 다시 해 주세요" 푸시를 쏘며, 출시 후 옛 학생증 코드를 통째로 지우려는 계획과 한 덩어리가 된다. 버킷도 `student-id-temp`(옛 학생증 사진이 남아 있을 수 있음)와 섞이지 않게 `graduate-cert-temp` 를 새로 만들었다.
3. **방법 선택은 서버 칸(`profiles.verification_method`)에 둔다.** 앱 로컬 저장은 기기를 바꾸면 사라지고 관문 계산이 복잡해진다. 서버 칸은 pytest · pgTAP 로 닫히고 정리 배치가 "졸업생 길을 고른 사람"을 알아 지킬 수 있다. 값 `null` = 학교 메일로 간주해서 **옛 앱(vc11 · vc12)과 호환**된다.
4. **서버 스위치(코드 기본 꺼짐)로 배포와 공개를 떼어 놓았다.** 코드가 운영에 나가도 스위치가 없으면 새 앱도 지금과 똑같은 관문(학교 메일)이 나온다. 켜는 것은 환경변수 한 줄이고 끄는 것도 한 줄이다. 실제로 10-19 에 코드를 먼저 배포(`00087-9qj`, 꺼짐)하고 사용자 승인을 받은 뒤 별도 리비전(`00088-gh5`)에서 켰다. 공개 출시 전이라 켜도 사용자가 테스터뿐이라는 점이 켜는 근거였고, 처리방침 · 스토어 양식이 끝나기 전에 일반 사용자에게 열리지 않게 하는 안전장치로 계속 쓰인다.
5. **중복 가입은 해시 두 개로 막는다(D5).** 학교 메일 사람은 "한 학교 메일 = 한 계정" 규칙(`school_email_claims`)으로 막히지만 졸업생에게는 그 메일이 없다. 대신 (가) **문서확인번호 해시**(같은 증명서를 두 계정에 쓰는 것을 막음) + (나) **학번 해시**(같은 사람이 새로 발급받아 두 계정을 만드는 것 · 탈퇴 뒤 재가입을 막음, 서류에 학번이 있을 때 관리자가 선택 입력)를 쓴다. 둘 다 유일 인덱스로 DB 가 막는다. 한쪽만으로는 부족하다 — (가)는 발급할 때마다 번호가 달라 재발급에 뚫리고, (나)는 학번이 안 찍힌 서류에서 비기 때문이다.
6. **반려는 사유 코드 4개로 표준화한다(D10, 문구는 대장 확정).** 앱 · 푸시 · 관리자 웹이 같은 코드를 같은 글자로 보인다: "사진이 잘 안 보여요" / "졸업증명서가 아니에요" / "확인할 수 없는 번호예요" / "아직 지원하지 않는 학교예요". 관리자 웹 상수와 서버 `REASON_TEXT` 를 글자 단위로 대조하는 시험이 있다.

## 4. 검증 흐름 (단계별)

### 4-1. 신청 (사용자 앱 → 서버)

| 단계 | 일어나는 일 | 근거 |
| --- | --- | --- |
| 0 | 앱이 `GET /me/verification-status` 로 서버 스위치(`graduate_enabled`)를 읽는다. **꺼져 있으면 앱은 학교 메일만 있던 때와 똑같다**(방법 고르기 없음, 02 학교 메일 입력이 바로 나옴 — 운영은 10-19 에 켜져 있어 지금은 방법 고르기가 나온다) | `VerificationGate.fromStatus` |
| 1 | 소셜 로그인 → 약관 동의(02-c) → (스위치 켜짐일 때만) **인증 방법 고르기 02-0**: 카드 두 개 중 하나를 고르고 [다음]. 카드를 누르는 것은 앱 안 선택일 뿐이고 `PUT /me/verification-method` 는 [다음]에서 나간다 — 눌러 보다 앱을 닫아도 서버 값이 바뀌지 않는다 | 계획서 1-1 |
| 2 | 졸업증명서 길: 신청 폼 02-g. 사진 1장(앱이 고르는 즉시 압축) + **이전 학교 이메일(선택)** + 개인정보 동의 줄 | 편차 Task 7 |
| 3 | `POST /graduate-verification`(multipart). 서버 관문 순서: 로그인(탈퇴 401) → 정지 → 동의 → 스위치 → 본문 검사 → 방법이 졸업증명서인지 → 이미 인증됐는지 → 이미 대기 중인지 → **신청 횟수(3회)** → 사진(10MB, 앱이 보낸 Content-Type 은 믿지 않고 매직바이트로 jpeg/png 판정) | `applicant_router.py` |
| 4 | **글자 인식**: Vision 이 사진 글자를 읽어 문서확인번호(라벨 `원본대조번호`(서울대학교 양식) · `문서확인번호` · `문서번호` · `확인번호` · `발급번호` 뒤의 영숫자 — 라벨 목록은 같은 날 PR #617 로 넓어졌다)와 학교 이름 후보를 뽑는다. 인식이 실패해도 신청은 접수된다(`ocr_state = failed`). 우리 코드 버그로 인한 예외는 삼키지 않고 500 으로 올린다 | `document_reader.py` |
| 5 | **사진 올리기** → 비공개 버킷 `graduate-cert-temp`(`{profile_id}/{request_id}.jpg`), 그 뒤 신청 행(`pending`) 쓰기. 순서를 "인식 → 올리기 → 행 쓰기"로 한 이유: 인식이 터져도 지울 사진이 없게 하려는 것이다. 행 쓰기가 실패하면 방금 올린 사진을 지우고, 그것도 실패하면 계정 id 만 담아 디스코드로 알린다 | 편차 8 · 15 |
| 6 | 신청 행에 **OCR 번호 · OCR 학교 글자 · 이전 학교 메일**이 **임시로** 들어간다(검수에 필요하다). `ocr_school_text` 에는 OCR 원문이 아니라 학교 이름 목록에 맞은 이름만 저장한다. 이전 메일은 **형식만** 검사하고 `school_email_claims` · `signup_blocks` 는 **읽지도 쓰지도 않는다**(응답이 그 메일의 선점 여부를 어떤 모양으로도 알려 주지 않는다) | 계획서 Global Constraints |
| 7 | 담당자 디스코드에 신청 알림(**신청 id 와 profile_id 만**, 사진 · 번호 · 이메일 없음) | `notify_graduate_request` |

### 4-2. 대기

- 앱은 대기 화면(02-g-2, 앱바 화살표 없음, 시스템 뒤로 = 종료 안내)에 머문다. 30초 폴링과 앱 재개 갱신, 푸시로 관문을 다시 묻는다.
- **대기 중에도 14일 정리 배치가 계정을 지우지 않는다.** 미인증 14일이 지난 계정을 지우는 기존 배치 후보에서 "대기 신청이 있거나 14일 안에 결정된 신청이 있는 프로필"을 SQL 로 빼고, 지우기 직전에 다시 확인한다(`list_unverified_accounts`).
- 대기는 **14일을 넘기지 못한다.** 넘으면 매시 배치가 `cancelled(expired)` 로 닫고 평문을 비우고 사진을 지운다. 신청 횟수는 3회이고 만료로 닫힌 것은 세지 않는다. 횟수를 다 쓰면 앱은 "신청 횟수를 모두 썼어요 + 문의 메일" 화면을 보인다.
- 대기 중에 학교 메일로 따로 인증을 통과하면(옛 앱 · 다른 기기) 배치가 그 신청을 `verified_otherwise` 로 닫고 사진을 지운다.

### 4-3. 검수 (관리자 웹 A10 "졸업생" 메뉴)

- 들어오는 문: 운영자 전용 구글 계정 + **2단계 인증(aal2, 12시간 이내)** + 관리자 명단(`admin_users`). 모든 졸업생 API 는 이 관문 뒤에 있다.
- 화면: 사진은 **5분짜리 서명 주소**로만 보인다. 옆에 OCR 이 읽은 번호 · 학교 후보(OCR 학교 글자와 이전 메일 도메인이 가리키는 학교를 미리 선택)가 **미리 채워져** 있고, **중복 경고**(이전 학교 메일이 이미 다른 계정 것 · 재가입 제한 중 · 같은 문서번호로 이미 승인된 사람)가 관리자에게만 뜬다.
- **사람이 하는 일**: 증명서에 인쇄된 문서확인번호를 **발급 기관의 확인 사이트에 직접 넣어 진짜인지 확인**하고, 맞으면 학교와 번호(필수, OCR 이 한 글자 틀렸으면 여기서 고친다) · 학번(서류에 있을 때 선택)을 입력한다. 이 확인이 위조를 막는 핵심이다.

### 4-4. 승인 (DB 함수 한 번에)

서버가 번호 · 학번을 **그 자리에서 HMAC 해시**해 DB 함수 `admin_review_graduate_request` 에 넘긴다(평문은 이 요청 본문에만 있고 저장 · 로그에 남지 않는다). 함수는 한 트랜잭션 안에서:

1. 관리자 명단 재확인 → 신청 행 잠금(이미 결정됐으면 409 `already_reviewed`)
2. 프로필 잠금(탈퇴면 409, 이미 인증됐으면 409 `already_verified`)
3. 학번 해시가 `signup_blocks` 에 걸려 있으면 409 `rejoin_blocked`
4. 신청 행을 `approved`(학교 · 번호 해시 · 학번 해시 · 시각)로 바꾸고 **평문 칸을 같은 UPDATE 에서 비운다**
5. 프로필 `university_id` · `school_email_verified_at` · `graduate_verified_at` · `verification_method` 갱신
6. `admin_actions` 에 작업 기록 한 줄(해시 · 번호 없음). **이 기록이 실패하면 승인도 되돌아간다**(기록 없는 조치 금지)

같은 증명서(`document_reused`) 또는 같은 사람(`student_reused`)이 이미 승인돼 있으면 유일 인덱스가 거절한다. **서버는 함수가 성공한 뒤에만** 사진을 지우고 푸시를 보낸다.

### 4-5. 반려

관리자가 사유 4개 중 하나를 고른다 → 신청 행이 `rejected` 로 바뀌고 평문이 비워진다. 프로필은 바뀌지 않는다. 푸시 본문은 "졸업생 인증이 반려됐어요 / {사유} · 다시 신청해 주세요". 신청 횟수가 남아 있으면 앱 신청 폼 맨 위에 반려 사유와 남은 횟수가 보인다(미지원 학교 사유면 "학교 이메일로 인증할 수도 있어요"를 함께 안내).

### 4-6. 사진 삭제 (세 겹)

| 겹 | 언제 | 어떻게 |
| --- | --- | --- |
| 1 | 승인 · 반려 **직후** | 서버가 DB 결정이 성공한 뒤 파일을 지우고 `photo_path` 를 비운다 |
| 2 | 1 이 실패하거나 서버가 도중에 죽었을 때 | 결정은 됐는데 `photo_path` 가 남은 행을 **매시 배치(`chat-gate`)** 가 찾아 다시 지운다. 이미 없는 파일(404)은 "지워진 것"으로 본다 |

### 4-7. 결과 알림과 이어가기

- 알림은 기존 종류 `verification_result` 를 재사용한다(알림 종류 check · 앱 enum 변경 0, 옛 앱도 이미 아는 종류). 데이터에는 `route · state · reason` 만 싣는다.
- 앱은 푸시를 받아도 **화면을 직접 옮기지 않고 관문만 다시 묻는다.** 결과에 따라 `AuthRedirect` 가 신청 폼(반려) 또는 학과 입력 3c(승인) → 온보딩으로 옮긴다. 승인 뒤에는 학교 메일 사람과 같은 길이다.
- 탈퇴: 대기 신청을 `account_withdrawn` 으로 닫고 버킷 폴더를 비운다. 졸업생에게는 학교 메일 해시가 없으므로 **재가입 제한(2개월 · 정지 중 탈퇴는 무기한)을 학번 해시로 건다.** 학번을 안 넣은 졸업생은 재가입 제한이 걸리지 않는다(아래 6-3).

### 5-2. 해시 설계

- HMAC-SHA256, 키는 학교 메일 해시와 같은 `identity_hmac_key`(Secret Manager)이고 **입력 앞에 이름공간 접두사**를 붙여 서로 겹치지 않는다: `graduate-document|<번호>` · `graduate-student|<학교 id>|<학번>`. 학교마다 학번 공간이 다르므로 학교 id 를 넣는다.
- 번호는 공백 · 하이픈을 떼고 대문자로 정규화한 뒤 영숫자 4~40자일 때만 해시한다(한글이 섞이면 OCR 이 엉뚱한 글자를 읽은 것으로 보고 거부).
- **한계**: 학번은 공간이 작아(학교당 10^6~10^8) **키가 새면 역산할 수 있다.** 전화번호 해시와 같은 수준의 위험이다. 그래서 키는 코드 · 문서에 없고 Secret Manager 에만 있다.
- 키를 바꾸면 저장된 해시가 모두 무효가 되므로 `key_version` 칸을 둔다(같은 버전끼리만 대조).

### 5-3. 선점 · 우회 방지

- **검증 안 된 이전 메일은 `school_email_claims` · `signup_blocks` 에 쓰지 않는다**(4-1 단계 6). 신청자가 남의 학교 메일을 적어도 그 사람의 가입을 막을 수 없고, 이미 그 메일이 쓰이고 있어도 신청자에게 달라지는 응답이 없다(상태코드 · 본문 · 호출 경로 동일을 시험으로 고정).
- 학교 메일 규칙과의 충돌 방지: "한 학교 메일 = 한 계정"은 졸업생 길에서 문서번호 해시 + 학번 해시로 대신한다. 학번 해시는 `signup_blocks` 에서 학교 메일 해시와 **이름공간이 분리**돼 있다.
- 사진 서명 주소는 5분, 응답에 `storage_path` · 해시 · 학번은 어떤 경우에도 나가지 않는다.

### 5-4. 접근 권한

- 신청 표는 RLS 를 켜고 **정책을 하나도 만들지 않았다**: 클라이언트는 자기 신청도 읽지 못한다. 상태는 서버가 내려 준다. `service_role` 만 네 권한을 가진다.
- 새 DB 함수는 모두 `security invoker` 이고 `public · anon · authenticated` 의 실행 권한을 걷고 `service_role` 에만 준다(`SECURITY DEFINER` 는 쓰지 않았다).
- 관리자 API 는 로그인 → aal2 → 명단 순으로 막고, 쓰기는 같은 요청 안에서 작업 기록을 남긴다.

### 5-5. 로그와 알림

로그 · 디스코드 · 푸시 `data` · `admin_actions` 에 **번호 · 이메일 · 학번 · OCR 글자 · 사진 경로를 쓰지 않는다.** 신청 id 와 profile_id 만 쓴다(공통 규칙 §3). 시험이 `caplog` 로 이를 확인한다.

### 5-6. 켜기 조건과 현재 상태 **[켜기는 사용자 승인 사항 — 운영은 10-19 승인받아 켰다]**

1. 처리방침 변경: 수집 항목(졸업증명서 사진 · 이전 학교 이메일 · 문서확인번호), 목적, 보유 기간, 처리 위탁 · 국외 이전(Google Cloud Vision), 관리자 열람 기록, 동의 방식.
2. 스토어 개인정보 양식(구글 데이터 보안 · 애플 앱 개인정보) 변경. 10-17 에 사진 수집을 줄이는 방향으로 양식을 단순화했으므로 **다시 늘어나는 항목**이다. 칸 이름은 스토어 현재 화면을 보고 확정해야 한다 **[확인 못 함]**.
3. 법률 확인: 졸업증명서의 고유식별정보(주민번호 인쇄 여부) · 별도 동의 필요 여부 · 국외 처리 고지 · 학번 해시가 개인정보인지 등(계획서 0-5).
4. 켜기: `gcloud run services update ... --update-env-vars GRADUATE_VERIFICATION_ENABLED=true`(배포 문서 `backend/DEPLOY.md` §4-14).

## 7. 함께 나간 작은 결정 셋 (같은 날 머지 · 배포)

### 7-1. 인증샷 여러 장 + 단톡방 이어서 제출 (PR #613) **[사용자 결정, 대장 결정 6건]**

- **문제(사용자 원문 요지)**: 단톡방 공유는 월 3회인데 하나 내고 승인 대기를 기다려야 다음 것을 낼 수 있어 번거롭다. 에브리타임 · 단톡방 모두 사진을 3장씩 낼 수 있게.
- **결정**: ① 제출 1건당 **사진 1~3장**, 월 한도(에브리타임 1 · 단톡방 3)는 그대로. 한도는 "이번 달(한국 시간) **검수 중 + 승인**"으로 세고 반려는 뺀다. ② 단톡방은 **검수 중이어도 한도 안이면 이어서 제출**할 수 있게 "항목당 검수 중 한 줄" 부분 유일 인덱스를 지웠다.
- **데이터 모델**: `storage_path text` → `storage_paths text[]`(1~3개, check 제약). 새 표(`heart_task_submission_photos`)는 사진별 해시가 필요해지는 날로 미뤘다 — 지금 요구는 "순서 있는 경로 최대 3개"뿐이라 RLS · 트리거 · 정리 면이 두 배가 되는 이득이 없다.
- **동시 제출이 한도를 넘지 않게**: 사람 · 항목마다 `pg_advisory_xact_lock` 을 잡는다. 두 기기가 마지막 한 칸을 동시에 노려도, 기다린 쪽이 먼저 온 쪽이 커밋한 뒤의 새 스냅샷으로 세어 거절된다(READ COMMITTED 에서 "넣고 나서 다시 세기"는 둘 다 통과해 쓸 수 없다).
- **서버는 multipart 한 요청**으로 사진을 받는다(1장씩 올리고 확정하는 방식은 임시 업로드 표 · 확정 API · 구조적 고아 파일이 생겨 기각). 응답에는 **옛 여섯 칸을 그대로 두고** `can_submit · max_photos · pending[]` 을 더했다 — 옛 앱은 모르는 칸을 무시하고 `photo` 한 장으로 계속 낼 수 있다.
- **배포 틈을 받아들였다(D5)**: 옛 `storage_path` 칸을 없애므로 마이그레이션 직후 서버를 바로 배포해야 하고, **서버만 이전 리비전(00086)으로 되돌리면 인증샷 제출 · 관리자 사진 보기가 깨진다.** 사용자 19명 · 출시 전이라 두 단계 호환 마이그레이션 대신 이 틈을 택했다.

### 7-2. 알림을 눌러 연 화면에서 뒤로가기 = 홈 (PR #614) **[사용자 결정, 인증샷 승인 알림에서 발견]**

- **원인**: 알림 탭이 `router.go` 로 화면 스택을 통째로 바꿔 홈이 아래에 없었다. 승인 알림을 눌러 인증샷 목록이 열리면 뒤로 갈 곳이 없었다.
- **결정**: `PushRoute.open` 한 곳에서 처리한다. 탭 3개(홈 · 오늘 · 대화 목록) · 채팅방(스스로 대화 목록으로 돌아간다) · 친구 후기 쓰기 시트는 예전처럼 `go`, 나머지는 **홈을 깔고 그 위에 `push`** 한다. 꺼진 앱 · 백그라운드 · 실행 중 세 갈래의 알림 이동이 모두 이 함수를 쓴다.
- 졸업생 인증 결과 푸시(`graduate_verification`)는 이 규칙과 별개로 **화면을 옮기지 않고 관문만 다시 묻는다**(4-7).

### 7-3. 저녁 알림 제한(방해 금지 22~08시)은 새 가입자부터 꺼짐 (PR #614) **[사용자 결정 10-19]**

- 앱 · 서버 · DB 기본값을 모두 `false` 로 바꿨다(서버 `NOTIFICATION_DEFAULTS`, 앱 `NotificationPreferences`, 컬럼 기본값). 사용자 결정이며 구체적인 이유는 이 문서 담당이 확인하지 못했다 **[확인 못 함]**.
- **함정**: 서버가 "설정 행이 없으면 켜짐"으로 읽고 있었다. 컬럼 기본값만 바꾸면 **설정 행이 아직 없는 기존 사용자가 조용히 꺼짐이 된다.** 그래서 마이그레이션이 (1) 설정 행이 없는 기존 사용자에게 `quiet_hours = true` 로 행을 먼저 채우고 (2) 그다음 컬럼 기본값을 `false` 로 바꾼다. 이미 행이 있는 사람은 건드리지 않는다.
- **적용 순서**: 마이그레이션 → 서버 → 앱. 서버가 먼저 나가면 기존 사용자의 제한이 꺼진다.
