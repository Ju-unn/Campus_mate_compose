# 기술 결정 기록 — 웹 버전 추가 계획: 앱 코드를 같이 쓰는 "방식 A" (2026-10-27)

> 앱(Android · iOS)은 지금처럼 운영하면서 같은 서비스의 **웹 버전을 더하기로 한 날(2026-10-27)** 의 결정과, 그날까지 확인한 사실을 적은 기록이다. **아직 구현 전이다** — 계획과 "웹으로 빌드는 되는가" 점검까지만 했다.
> 파일 이름은 `docs/decisions/` 관례(날짜 + 주제, 한 결정에 한 파일)를 따른다. 구현이 시작되면 이 문서의 5절에 결과를 덧붙이고, 큰 갈래가 생기면 따로 파일을 만든다.
> 표시: **[사용자 결정]** = 사용자가 직접 정한 것(이 문서 담당은 원문을 직접 보지 못했고 통합대장이 전달했다), **[대장 전달]** = 통합대장이 직접 확인해 전달한 값, **[문서 담당 확인]** = 이 문서 담당이 저장소에서 직접 센 것, **[확인 못 함]** = 근거를 찾지 못한 것.

## 1. 계기

- 2026-10-27 사용자가 "앱은 그대로 운영하면서 웹 버전을 추가한다"고 정했다 **[사용자 결정]**. 이유는 사용자 원문 그대로 「앱도 운영하고 웹도 운영하고 싶어서 그래」, 「앱은 현상태 유지해 앱도 유지하면서 웹버전으로 만들고 싶은거야」다(대장이 이 세션에서 직접 본 원문). 대상 사용자 · 시점 · 우선순위는 전달받지 못했다 **[확인 못 함]**.
- 이 저장소에는 이미 Flutter 웹 앱이 하나 있다 — 운영자용 `admin_web/`(Vercel). 하지만 그것은 **앱과 따로 빌드하고 서로 import 하지 않는** 별도 프로젝트다(`README.md` 저장소 구조 표, `admin_web/README.md`). 이번 결정은 그 방식이 아니라 **사용자용 앱(`frontend/`)을 웹으로도 내는 것**이다.

## 2. 고른 방식과 대안

- **방식 A(채택)**: 코드를 한 벌로 두고, 웹에서 안 되는 곳만 웹용 파일로 갈라 놓는다. 앱 쪽 기존 파일은 건드리지 않고 **옆에 웹용 파일을 더하는** 방식이라 앱 심사 중인 지금 앱 동작이 바뀔 위험을 줄인다는 취지로 읽는다(이 문장은 규칙 ①에서 이 문서 담당이 읽어 낸 것이고, 사용자가 이유를 밝힌 말은 전달받지 못했다).
- **대안 B**: 관리자 웹(`admin_web/`)처럼 **완전히 별도 프로젝트**로 만든다. 앱 코드는 한 줄도 안 고치지만 화면을 복사해야 하고, 고칠 때 두 곳을 고쳐야 한다. 대장이 A · B 를 제시했고 사용자가 「그럼 A로 가자」로 A 를 골랐다(사용자 원문, 대장 전달). 선택 이유를 사용자가 더 밝힌 말은 없다.

## 3. 저장소에서 확인한 사실 **[문서 담당 확인]**

**3-1. 웹으로 가져갈 때 걸릴 코드**
- `frontend/lib` 에서 `dart:io` 를 import 하는 파일은 **22개**다. 대장이 전달한 숫자와 같다. 묶으면 — 사진 고르기 · 압축(`auth/model/image_compressor.dart`, `me/model/photo_slot.dart`, `me/viewmodel/avatar_regen_pick_view_model.dart`, `profile/*photos*`), 얼굴 검사(`auth/model/face_detector.dart`), 인증샷(`billing/*heart_task*`), 졸업생 인증(`graduate/*`), 임시 저장(`core/draft/*`), FAQ 캐시(`faq/model/faq_cache.dart`), 연락처 이름 저장(`safety/model/contact_name_store.dart`).
- `kIsWeb` 분기는 이미 `lib` 안에 있다(import 줄을 포함해 12줄). 예: 애플 로그인 단추는 `!kIsWeb && iOS` 일 때만 보이고(`auth/view/start_view.dart`), 앱 내 결제 창구는 웹이면 `null` 을 돌려준다(`billing/model/in_app_heart_store_gateway.dart`). 즉 일부는 웹을 염두에 두고 만들어져 있다.
- 네이티브에 기대는 패키지(`frontend/pubspec.yaml`): `google_mlkit_face_detection`(얼굴 검사) · `flutter_contacts`(연락처) · `in_app_purchase`(하트 결제) · `firebase_messaging`(푸시) · `firebase_crashlytics` · `firebase_performance` · `firebase_analytics` · `google_sign_in` · `kakao_flutter_sdk_user` · `kakao_flutter_sdk_share` · `sign_in_with_apple`. 이 중 어디가 웹에서 막히는지는 **실행 점검 전이라 추정**이다(대장 전달 추정과 같다: 카카오 · 구글 · 애플 로그인의 웹 방식, ML Kit 얼굴 검사, 연락처, 결제, 푸시 · Crashlytics).
- `frontend/web/` 폴더(`index.html` · `manifest.json` · 아이콘)는 이미 있으나 `manifest.json` 의 이름 · 설명이 Flutter 기본값("A new Flutter project.")이라 웹을 내보내기 전에 고쳐야 한다.

**3-2. 서버 쪽**
- 사용자용 API 에는 CORS 허용이 **없다**. 지금 CORS 는 관리자 웹용으로만 `ADMIN_ALLOWED_ORIGINS` 가 비어 있지 않을 때 켜진다(`backend/app/main.py` 96 ~ 97행 · `backend/app/admin/cors.py` · `backend/app/settings.py`). 모바일 앱은 `Origin` 을 보내지 않아 지금까지 상관이 없었다.
- **웹 주소를 그 목록에 더하는 것만으로는 부족할 수 있다**: 현재 설정은 허용 메서드가 `GET` · `POST`, 허용 헤더가 `Authorization` · `Content-Type` 뿐인데, 사용자용 API 에는 `PUT` 2개 · `PATCH` 4개 · `DELETE` 6개 경로가 있다(`backend/app` 의 라우터 데코레이터를 센 값). 이 미들웨어는 앱 전체에 걸리므로, 사용자용 웹을 열 때는 허용 메서드 · 헤더를 손볼지, 관리자 웹과 사용자 웹의 설정을 나눌지 정해야 한다. 이 판단은 코드 읽기만으로 한 것이고 시험하지 않았다.

## 5. 다음 단계와 기록 자리

1. **브라우저 실행 점검**(대장 할 일): 빌드가 되는 것과 화면이 도는 것은 다르다. 크롬으로 띄워 화면별로 멈추는 곳을 표로 만든다. 결과는 이 절에 덧붙인다.
2. 점검 표를 보고 웹용 파일로 나눌 곳의 순서를 정한다(로그인 → 사진 올리기 → 연락처 → 푸시 → 결제 순이 자연스러워 보이나, 순서는 점검 뒤 사용자가 정한다).
3. 패키지가 필요하면 **하나씩** 사용자에게 승인을 받는다.
4. 합치기 전에 `flutter.yml` · `ios-build.yml` 이 통과하는지 본다(앱이 깨지지 않았다는 증거).
5. 점검용 작업 폴더는 `../campus_mate_compose-web-check`(detached HEAD, main `4b170d40`)다. 정리는 git 담당 몫이고 이 문서 담당은 건드리지 않았다.

## 6. 남은 위험 · 확인하지 못한 것

- 웹 버전의 대상 사용자 · 일정 · 우선순위는 근거를 못 찾아 쓰지 않았다 **[확인 못 함]**. 서버 CORS 변경안은 **아직 설계 전**이다.
- "빌드 오류 0개" 는 대장이 돌린 결과를 전달받은 값이다. 이 문서 담당은 `flutter build web` 을 돌리지 않았다.
- 22개 파일 · 패키지 목록은 저장소에서 직접 센 것이지만, 그중 **실제로 웹에서 깨지는 곳이 어디인지는 모른다**(실행 점검 전).
- 웹 결제(PG 선정 · 약관 · 수수료 · 환불 정책 A 와의 연결)는 이번 기록의 범위 밖이다.
- 사용자용 웹은 모바일 앱과 달리 주소가 공개된다. 로그인 · 토큰 보관(브라우저 저장소) · 사진 업로드의 개인정보 취급은 설계 때 별도로 점검해야 한다(코드 근거 없음, 일반 원칙).
