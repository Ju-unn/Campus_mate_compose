# CampusMate — DESIGN.md

CampusMate 의 디자인 시스템 단일 원본(Source of Truth). 화면을 만들거나 고칠 때 **이 문서의 토큰만 참조**한다.

- 대상: Flutter (Android + iOS), 모바일 전용
- 설계 문서: `docs/superpowers/specs/2026-09-05-campusmate-foundation-design.md`
- 토큰 구현 위치: `lib/core/theme/`
- 최초 작성: 2026-09-05

---

## 0. 이 문서의 근거

두 레퍼런스 추출본(Apple, Airbnb)에서 CampusMate 에 맞는 것만 상속했다. 원본 파일은 삭제했다.

- **Apple** — 제품이 주인공이고 UI 는 물러난다(CampusMate 의 제품은 **하루 한 장의 카드**), 브랜드 색은 하나, 깊이는 그림자 대신 **표면 색 변화**, 디스플레이 음수 자간, 여백이 곧 받침대
- **Airbnb** — 사진이 먼저인 카드와 부드러운 라운드, 그림자는 **딱 한 단계**, 디스플레이 굵기는 과하지 않게(사진이 무게를 담당), 4px 기반 간격, **타이포가 크게 소리치는 순간은 한 곳뿐**
- **버린 것** — Apple 라이트/다크 타일 교차(마케팅 문법), Airbnb 서브 브랜드 색(Luxe/Plus), 데스크톱 그리드·푸터·호버, Apple 17px 본문(한글 본문은 16px)

## 1. 디자인 원칙

CampusMate 는 **스와이프 앱이 아니다.** 아침 7시에 한 장이 도착하고, 수락하거나 거절하면 그날은 끝난다. 화면은 그 리듬을 따라야 한다. 무한 스크롤의 자극이 아니라 **하루에 한 번 열어보는 편지**의 감각을 목표로 한다.

바탕은 **순백**, 잉크는 `#222222`, 그리고 **Rausch(`{colors.primary}` — #FF385C) 단 하나**가 모든 상호작용을 담당한다. Airbnb 의 색 체계를 그대로 따랐다. Rausch 는 한 화면에 한두 곳에만 나타난다. 카드의 사진과 사람의 문장이 무게를 담당하고, UI 는 그것을 받쳐주는 자리에 머무른다.

대학생 개인정보(사진·연락처)를 다루는 서비스이므로 **신뢰감이 심미성보다 우선**한다. 학생 인증 뱃지, 신고·차단 진입점은 어떤 화면에서도 숨기거나 흐리지 않는다. (2026-09-08 수정: 등록비 폐지로 "결제 금액 표기" 관련 서술은 삭제 — 이제 하트 구매 금액에만 해당)

**핵심 특징**

- 단일 강조색. Rausch 는 수락 버튼 · 활성 탭 · 내 채팅 말풍선 · 뱃지 카운트에만 쓴다
- 그림자는 오늘 탭 요약 카드·잠금 카드에만. 나머지 표면은 전부 평면이며 깊이는 표면 색으로 구분한다 — **2026-09-13 완전 확정(§13-82 완전 해결): 사용자 결정은 "요약 카드만 그림자".** `daily-card-summary`·`daily-card-locked`(§8.1)가 노출되는 오늘의 카드 화면 전부(`W0CjO`·`Keynu`·`VT4tS`·`kCfXv`·10d `eDPkz`·10e `wDKXv` — **2026-09-14 §13-96으로 화면이 늘어나 "4장" 고정 카운트 대신 컴포넌트 기준으로 서술 정정**)에 §6 카드 그림자(두 겹)를 넣는다. **10b·14c는 그림자 없음**(2026-09-13 사용자 결정으로 확정, 24 경유 확인·9c 승인 — 종전 "범위 밖·미정" 상태 해소)
- 하루 한 장이라는 제약이 화면의 중심. 카드 스택 미리보기, 남은 장 수 표시, 좌우 스와이프 제스처를 만들지 않는다
- 사진 비율은 전부 4:5 세로. 사람의 상반신이 안정적으로 담기는 비율이다
- 한글 조판 우선. Pretendard, 본문 행간 1.6, 디스플레이 자간 −0.03em
- 궁합 점수 같은 **숫자는 사용자에게 노출하지 않는다** (§13 미결 1)
- **모든 화면에서 닉네임으로 표시한다.** 실명은 앱 어디에도 노출하지 않는다(2026-09-10 개정, §8.7)
- 오늘 탭 카드는 요약(`daily-card-summary`)만 보여주고, 탭하면 10b 화면으로 이동해 나머지 전부를 보여준다 — 뒤집기 없음 (2026-09-13, §13-80, §8.1)

## 2. 색상

### 2.1 브랜드

Airbnb 의 색 체계를 그대로 가져왔다. 캔버스는 **순백**, 잉크는 **#222222**, 그리고 **Rausch(#FF385C) 단 하나**가 모든 상호작용을 담당한다.

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{colors.primary}` | `#FF385C` | Rausch. 모든 CTA 채움, 하트, 활성 탭, 카운트 뱃지, 워드마크 |
| `{colors.primary-pressed}` | `#E00B41` | 눌림 상태 (Airbnb 의 Rausch Active) |
| `{colors.primary-text}` | `#C4224B` | **흰 배경 위 핑크 텍스트·링크 전용.** 채움에는 쓰지 않는다 |
| `{colors.primary-wash}` | `#FFF0F2` | 아주 옅은 핑크 표면. 수락 대기 행, 선택된 칩 |
| `{colors.primary-disabled}` | `#E5E5E5` | 비활성 버튼 채움 · `button-secondary`·`button-danger` 채움 · `religion-select` 비선택 칸 (2026-09-15 사용자 결정으로 토큰화). 연한 핑크는 대비 1.55:1 이라 쓰지 않는다 — §8.3 |
| `{colors.on-primary}` | `#FFFFFF` | Rausch 채움 위의 텍스트·아이콘 |

**Rausch 를 텍스트에 그대로 쓰지 않는 이유.** `#FF385C` 는 흰 배경 대비 **3.52:1** 로 본문 기준(4.5:1)에 미달한다. 그래서 텍스트·링크는 `{colors.primary-text}`(`#C4224B`, 5.71:1)를 쓰고, `#FF385C` 는 **채움 전용**으로 둔다. 색은 거의 같아 보이지만 읽히는 정도가 다르다.

**버튼 라벨은 18/700 이다.** 흰 글씨가 Rausch 위에서 3.52:1 이므로, WCAG 의 큰 글씨 예외(18.66px 이상 굵은 글씨 → 3:1)에 기대야 한다. 18px 은 그 기준에 0.66px 모자라는 **의도적 허용 편차**다. Airbnb 자신도 이 지점을 통과하지 못한다(그들은 16/500). 브랜드 색을 우선한 결정이며, 여기서 더 밝게 가면 안 된다.

| 남아 있는 편차 | 값 | 대응 |
| --- | --- | --- |
| Rausch 위 흰 버튼 라벨 18/700 | 3.52:1 | 큰 글씨 예외 경계선. 허용 |
| Rausch 뱃지 위 흰 숫자 11px | 3.52:1 | 허용. **단, 뱃지 숫자가 유일한 정보 전달 수단이 되면 안 된다** |

### 2.2 표면

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{colors.canvas}` | `#FFFFFF` | 모든 화면의 바닥. **순백이다** |
| `{colors.surface-soft}` | `#F7F7F7` | 입력 필드 채움, 상대 말풍선, 태그 칩 |
| `{colors.surface-strong}` | `#F2F2F2` | 원형 아이콘 버튼 바탕, 살짝 더 무거운 채움 |
| `{colors.surface-ink}` | `#222222` | 잉크 표면. 학생 인증 뱃지, 사진 위 오버레이 칩 |
| `{colors.scrim}` | `#000000` @ 50% | 모달 뒤 딤, 모자이크 배너 위 덮개 |

캔버스가 순백이므로 카드(흰색)와 바닥이 같은 색이다. **분리는 1px 헤어라인과 라운드가 만든다.** 그림자에 기대지 않는다.

### 2.3 텍스트

| 토큰 | 값 | 흰 배경 대비 | 용도 |
| --- | --- | --- | --- |
| `{colors.ink}` | `#222222` | 15.9:1 | 제목, 이름, 강조 본문. 순검정을 쓰지 않는다 |
| `{colors.body}` | `#3F3F3F` | 10.5:1 | 긴 본문. 잉크가 무거운 자리 |
| `{colors.muted}` | `#6A6A6A` | 5.4:1 | 보조 설명, 메타 정보, 시각, 캡션 |
| `{colors.disabled}` | `#929292` | 3.1:1 | 비활성 텍스트 전용 (대비 요건 면제 대상) |
| `{colors.on-ink}` | `#FFFFFF` | 15.9:1 | 잉크 표면 위 텍스트 |

### 2.4 경계선

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{colors.hairline}` | `#DDDDDD` | 기본 1px 구분선. 리스트·섹션·카드 테두리(단, `daily-card-summary`·10b·`daily-card-locked`(`kMqr5`) 카드 자체 테두리는 `{colors.hairline-soft}` `#EBEBEB`를 쓴다 — 2026-09-13, 9c 발견, §13-81) |
| `{colors.hairline-soft}` | `#EBEBEB` | 더 옅은 구분선. 긴 스크롤 본문 |
| `{colors.outline}` | `#767676` | **컨트롤 경계선.** 입력 필드, 아웃라인 버튼. 흰 배경 4.54:1 |

**Airbnb 의 `border-strong`(#C1C1C1)을 쓰지 않았다.** 흰 배경 대비 1.80:1 로 비텍스트 대비 3:1 에 미달한다. 입력 필드 테두리는 그 컨트롤이 어디까지인지 알려주는 유일한 단서이므로 여기만 `#767676` 로 올렸다. 장식용 구분선은 Airbnb 그대로 `#DDDDDD` 를 쓴다.

### 2.5 의미색

| 토큰 | 값 | 흰 배경 대비 | 용도 |
| --- | --- | --- | --- |
| `{colors.error}` | `#C13515` | 5.5:1 | 인증 실패, 입력 오류, 신고 확인 |
| `{colors.success}` | `#25795A` | 5.1:1 | 매칭 성사, 학생 인증 완료 |

`{colors.error}` 와 Rausch 는 색상환에서 가깝다. **에러는 항상 아이콘 + 문구를 동반**하고, Rausch 표면 위에는 올리지 않는다.

실제 계산값이다. 팔레트를 바꾸면 다시 계산해서 갱신한다.

### 2.7 다크 모드

**MVP 범위에서 제외한다.** 1인 개발 · 2개월 일정에서 두 벌의 팔레트를 검증할 여력이 없고, 검증하지 않은 다크 모드는 없느니만 못하다.

대신 나중에 넣을 수 있게 만든다. `AppColors` 는 의미 기반 토큰만 노출하고, **위젯은 `AppColors` 를 직접 읽는다**(2026-09-15 사용자 결정 — 종전 "`Theme.of(context).colorScheme` 을 통해서만"에서 개정). `ThemeData.colorScheme` 은 Material 기본 위젯용으로만 채운다. 다크 팔레트는 **토큰 값 한 벌을 추가**하는 것으로 끝나야 한다. `MaterialApp` 에는 `themeMode: ThemeMode.light` 를 명시해 시스템 다크에 끌려가지 않게 고정한다.

## 3. 타이포그래피

### 3.1 폰트

**Pretendard** 하나로 전부 처리한다. 별도 디스플레이 서체를 두지 않는다.

```
fontFamily: 'Pretendard'
fontFamilyFallback: ['Apple SD Gothic Neo', 'Noto Sans KR', 'sans-serif']
```

- 라이선스: SIL Open Font License 1.1 — 앱 번들 포함 가능
- 번들 방식: **정적 4종**(`Pretendard-Regular` · `Medium` · `SemiBold` · `Bold`, 400/500/600/700)을 `assets/fonts/` 에 두고 `pubspec.yaml` 에 등록한다(2026-09-15 사용자 결정 — 종전 가변 폰트 `PretendardVariable.ttf` 에서 개정. 쓰는 굵기가 4단계뿐이라 가변 폰트가 필요 없다). 출처는 [orioncactus/pretendard](https://github.com/orioncactus/pretendard) 릴리스이고 라이선스 원문을 함께 커밋한다. 웹폰트 CDN 을 쓰지 않는다 (오프라인 동작, 첫 프레임 깜빡임 방지)
- 사용 굵기: **400 / 500 / 600 / 700** 네 단계. 그 외는 쓰지 않는다
- 숫자에는 `FontFeature.tabularFigures()` 를 적용한다. **하트 잔액·가격·타이머(카운트다운)** 숫자만 대상이다(2026-09-15 사용자 결정 — 나이·키·요금 전체로 넓히지 않는다). 코드는 `AppTypography.countdown` 에 이미 적용돼 있고, 하트 잔액·가격은 조각 1 위젯에서 적용한다

### 3.3 원칙

- **본문은 16px.** 12px 미만 텍스트를 만들지 않는다. `{type.badge}` 11px 이 하한이고, 뱃지는 항상 옆의 텍스트가 의미를 보완한다
- **한글 본문 행간은 1.6.** 한글은 디센더 리듬이 없어 라틴 기준(1.4~1.5)으로는 답답하다
- **자간은 크기가 클수록 좁힌다.** 20px 이상에만 음수 자간을 주고, 14px 이하에는 주지 않는다. 작은 한글에 음수 자간을 주면 가독성이 무너진다
- **굵기 500 은 채팅 말풍선 전용.** 나머지는 400 / 600 / 700 사다리를 쓴다
- **크게 소리치는 곳은 카운트다운 하나뿐.** 48px 은 "다음 카드까지 06:12:40" 한 군데에만 쓴다. 이 앱에서 가장 중요한 정보는 기다림이다
- **한글 줄바꿈을 통제한다.** 이름·대학명처럼 끊기면 안 되는 문자열에는 `softWrap: false` + `TextOverflow.ellipsis` 를 준다

## 4. 레이아웃

### 4.1 간격

기본 단위 **4px**.

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{space.xxs}` | 4 | 아이콘과 라벨 사이, 칩 내부 세로 |
| `{space.xs}` | 8 | 인접 요소 최소 간격, 터치 타깃 사이 |
| `{space.sm}` | 12 | 리스트 행 내부 세로 패딩 |
| `{space.md}` | 16 | **화면 좌우 기본 여백**, 카드 내부 패딩 |
| `{space.lg}` | 24 | 블록 사이, 큰 카드 내부 패딩 |
| `{space.xl}` | 32 | 섹션 사이 |
| `{space.xxl}` | 48 | 화면 상단 여백, 빈 상태 위아래 |

- 화면 좌우 여백은 전 화면 `{space.md}`(16) 로 고정한다. 화면마다 다르게 두지 않는다
- 인접한 터치 타깃 사이는 최소 `{space.xs}`(8)

### 4.2 세이프 에어리어

- 하단 고정 바(수락/거절 액션 바, 채팅 입력창, 바텀 내비)는 **세이프 에어리어 아래 패딩을 더한다**. `SafeArea(top: false)` 로 감싸고 제스처 인디케이터를 침범하지 않는다
- 스크롤 콘텐츠에는 고정 바 높이만큼 `bottom` 인셋을 준다. 리스트 마지막 항목이 바 뒤로 숨으면 안 된다
- 앱바는 상태바 아래에서 시작한다. 사진 위에 앱바를 띄우는 경우 위쪽에 스크림 그라데이션을 깔아 텍스트 대비를 확보한다

### 4.3 여백 철학

오늘의 카드 화면은 의도적으로 비어 있다. 요약 카드(`daily-card-summary`) 하나 외에 아무것도 두지 않는다(2026-09-13 개정 — 종전 결정 대기 화면의 거절·수락 버튼은 제거됐고, 거절·수락은 원래부터 액션 바가 있던 10b에서만 한다, §8.1). 매칭 커플 지표 띠·후보 목록은 넣지 않는다. 배너·프로모션·추천 목록을 이 화면에 추가하지 않는다. **추가 카드 결제 유도(잠금 카드)는 `W0CjO`·`Keynu`·`VT4tS`·`kCfXv` 4곳에 도입한다(2026-09-13 사용자 결정, §13-84) — `daily-card-locked`(§8.1) + `x2yPl` 시트(§9). 화면 안에서는 위에서부터 [이번 주기 무료 카드 → 이번 주기 잠금 카드 → 이전 주기에 산 카드(결정 전까지 쌓임)] 순서로 쌓는다(2026-09-14 사용자 결정, §13-83·88 해결 — 종전 "구매 카드 먼저" 순서를 뒤집음, §8.9 `pending-decision-queue` 참조).**

반대로 채팅 목록과 설정 화면은 밀도를 높인다. 정보를 찾으러 온 화면이므로 스크롤을 줄이는 쪽이 낫다.

### 5.2 사진

**두 종류를 구분한다 — 표시용(만화 아바타)과 실사진.** (경쟁사 조사 반영, 설계 문서 §2.5·§6.1과 연동)

**아바타 화풍 = 썸타임 "블라인드 아바타" 스타일 2D(2026-09-14 구체화, §13-113)** — 원본 사진의 옷·머리·배경은 유지하고 얼굴만 단순화한다. 시안 인물 사진은 전부 AI 생성이다: 나(늑대 닉네임)=남자, 상대(토끼·여우비·봄비·초코라떼 등 닉네임)=여자. **리빌 규칙 요약**(아래 항목들과 동일 원칙): 카드·레일·결정 대기 큐·대화 목록 = 아바타 / 내 프로필(15) 사진 슬롯·5b 아바타 리빌·14b 신뢰 확인 후 채팅방 헤더·14c 상대 프로필 상세 = 실사진.

- **공개용 실사진 2~4장 + 그중 1장을 아바타 원본으로 지정한다(2026-09-13 개정, §13-51. 종전 "정확히 2장"(2026-09-08, 설계 문서 §13 미결4)은 폐기).** 온보딩 사진 단계는 두 페이지다. ① **공개용 실사진 업로드** — 갤러리 다중 선택으로 **최소 2장, 최대 4장**. 쌍방 수락 + 신뢰 확인을 마쳐야만 상대에게 공개된다. ② **아바타 원본 선택** — ①에서 올린 사진 중 **1장**을 골라 AI 만화 아바타로 변환한다. **아바타 원본으로 고른 사진도 신뢰 확인을 통과하면 다른 실사진과 함께 공개된다. 어느 사진이 원본인지만 상대에게 드러내지 않는다**(2026-09-13 확정, ERD.md §11-5). 두 번째 페이지 하단에 "상호 수락 전에는 아바타 사진만 보여요" 안내를 고정 노출한다
- **사진 파일은 10MB 이하 JPEG·PNG만 올린다**(2026-09-14, ERD.md §11-25·설계 §7.4). 앱이 업로드 전에 사진을 압축하고 JPEG로 다시 인코딩한다 — 학생증 사진도 같다. 파일 내용(매직 바이트) 검사는 FastAPI가 한다
- 평소 카드·프로필·채팅 헤더에는 **만화 아바타만** 노출된다
- **교체 정책이 비대칭이다.** 공개용 실사진은 **언제든 무료로 교체**할 수 있다. 아바타 교체(= 아바타용 사진 변경)는 **최초 1회 무료, 이후 10하트**다 — OpenAI 이미지 생성 비용이 실제로 발생하는 유일한 지점이기 때문이다(§8.10)
- **실사진은 원칙적으로 비공개다.** 매칭 후 신뢰 확인 게이트(설계 문서 §2.5)에서 양쪽이 모두 수락해야만, 그 상대에게 한해 실사진이 공개된다. 그 전까지는 어떤 화면·API 응답에도 실사진이 담기지 않는다
- 표시용 사진 위에는 `ai-avatar-badge`를 작게 얹는다 — "AI가 그려준 얼굴이에요" 톤. 나중에 실사진을 보고 느낄 괴리를 온보딩 시점부터 낮춰둔다
- **내 프로필(§9 화면15)에는 예외적으로 실사진도 함께 보여준다.** "상대에게는 이렇게 보여요"(표시용) + "나만 보는 실제 사진" 두 섹션으로 나눈다 — 얼굴 판별·변환이 잘 됐는지 본인이 확인할 수 있어야 한다. 실사진이 2~4장이므로 이 섹션은 **가로 스와이프 슬라이더 + 점 인디케이터**다(2026-09-13, §13-51)
- **신뢰 확인을 마친 상대의 실사진도 슬라이더로 본다.** 채팅방의 정보 카드 버블 → `상대 프로필 보기` → **상대 프로필 상세**(§9 화면14c)에서 실사진 2~4장을 가로 슬라이더로 넘겨 본다(2026-09-13, §13-52)
- **모든 인물 사진(표시용 기준)은 4:5 세로.** 카드, 프로필, 채팅방 헤더 전부 동일하다
- 아바타는 원형. 리스트 40dp, 채팅 헤더 32dp, 프로필 96dp
- 카드 사진은 `{radius.lg}` 로 클리핑하고, 하단에 이름을 얹을 경우 아래쪽 40% 에 잉크 스크림 그라데이션을 깐다
- **모자이크 레일·배너는 서버 픽셀레이션이 필요 없다.** 표시용 사진이 애초에 만화 아바타라 비식별이므로, 동의 여부와 무관하게 그대로 노출한다(8.9절 갱신 — 이전의 동의 기반 서버 픽셀레이션 규칙은 폐기)
- 사진이 없는 프로필은 `{colors.primary-wash}` 바탕 + 이니셜 잉크 텍스트로 대체한다. 회색 사람 아이콘은 쓰지 않는다

### 5.4 마스코트와 일러스트

하트 귀를 가진 흰 토끼. 원본은 `design/designMaterials/` 에 있다. **남자 캐릭터는 파란 목도리·파란 하트 속귀(`mascot-male.png`), 여자 캐릭터는 핑크 목도리·핑크 하트 속귀(`mascot-female.png`)**로 구분한다. 색만으로 구분하지 않고 목도리 형태를 함께 쓰며, 두 캐릭터의 얼굴 비율·외곽선·몸 형태는 같은 가족으로 유지한다.

마스코트의 역할은 하나다 — **화면에 보여줄 사람이 아직 없을 때 그 자리를 지키는 것.** 서비스가 작을 때 빈 화면은 "망한 앱"으로 읽히지만, 빈 화면에 캐릭터가 있으면 "아직 이른 앱"으로 읽힌다.

- 기본 그림체는 깨끗한 2D 외곽선 위에 **부드러운 2.5D 볼륨 음영과 작은 하이라이트**만 더한다. 실사 털·플라스틱 장난감 질감·과한 광택은 쓰지 않는다
- 파란색은 남자 마스코트와 브랜드 일러스트의 작은 보조 포인트에만 쓴다. **CTA·링크·선택 상태는 계속 `{colors.primary}` / `{colors.primary-text}`만 사용**한다 — 파란색을 두 번째 상호작용 색으로 확장하지 않는다

**쓰지 않는 곳** — 오늘의 카드 안, 프로필, 채팅방, 결제 시트, 신고·차단 흐름. 사람의 얼굴과 돈과 안전이 걸린 화면에 캐릭터를 넣지 않는다. 결제 화면의 캐릭터는 판단을 흐리는 장치로 읽힌다.

- **한 화면에 한 마리.** 두 마리가 동시에 보이면 소개팅 앱이 아니라 캐릭터 앱이 된다
- 마스코트는 **장식이지 정보가 아니다.** 마스코트만으로 상태를 알리지 않는다. 항상 문구가 함께 간다
- 마스코트 외곽선이 흰색이므로 `{colors.canvas}` 또는 `{colors.primary-wash}` 위에만 놓는다. 사진 위에 얹지 않는다
- 실사 일러스트(커플 그림 등)는 **온보딩과 마케팅에만** 쓴다. 앱 안의 반복 화면에 넣으면 금방 질린다

그림자는 **한 단계만** 존재한다.

| 단계 | 처리 | 적용 대상 |
| --- | --- | --- |
| 평면 | 그림자 없음 | 화면의 95%. 앱바, 리스트, 입력, 버튼, 바텀 내비 |
| 카드 | `0 2px 8px rgba(26,22,25,0.06)` + `0 8px 24px rgba(26,22,25,0.08)` | 오늘 탭 요약 카드(`daily-card-summary`)·잠금 카드(`daily-card-locked`) — **2026-09-13 완전 확정(§13-82 완전 해결, 사용자 결정 "요약 카드만 그림자"). 노출 화면은 §1·§8.1 참조(2026-09-14 §13-96으로 확대돼 고정 카운트 서술은 뺐다). 10b·14c는 그림자 없음**. 바텀시트 — §8.8 `bottom-sheet` 규격은 이 등급("카드" 그림자)으로 서술돼 있으나 **실측은 3갈래로 갈린다(2026-09-13, 9c 발견, §13-82 기록)**: 기존 시트 4개는 `0 -2px 16px` 한 겹, `15b`(`aGaPA`)·신규 `x2yPl`은 그림자 없음 — 세 갈래 통일 여부는 정식 결정 대기, 지금은 실측대로 기록만 한다 |
| 스크림 | `{colors.scrim}` 50%(2026-09-14 정정, §13-113 — 종전 55% 표기가 §2.2 `{colors.scrim}` 토큰값(50%)과 어긋나 있었다) | 모달 뒤, 모자이크 배너 위 |

버튼·칩·앱바·리스트에 그림자를 넣지 않는다. Flutter 기본 `Card` 의 `elevation` 을 그대로 쓰면 이 규칙이 깨지므로, `AppElevation.card` 상수를 통해 `BoxShadow` 를 직접 지정한다.

깊이는 그림자가 아니라 **표면 색 차이**로 만든다. `canvas` → `surface` → `surface-ink` 순서가 곧 층위다.

## 7. 모션

| 토큰 | 시간 | 커브 | 용도 |
| --- | --- | --- | --- |
| `{motion.press}` | 120ms | `Curves.easeOut` | 눌림 피드백 (투명도·색) |
| `{motion.standard}` | 220ms | `Curves.easeOutCubic` | 화면 전환, 시트 열림, 상태 변화 |
| `{motion.emphasis}` | 420ms | `Curves.easeOutBack` | 매칭 성사 · 카드 등장 |

- **누름 반응은 150ms 안에 보인다.** 반응 없는 탭은 고장으로 읽힌다
- **레이아웃을 흔드는 눌림 효과를 쓰지 않는다.** 색·투명도만 바꾸고 크기·위치는 고정한다
- `{motion.emphasis}` 는 하루에 최대 두 번(카드 등장, 매칭 성사)만 등장한다
- **`MediaQuery.disableAnimations` 를 존중한다.** 켜져 있으면 모든 시간을 0 으로 만들고 최종 상태를 즉시 그린다
- 로딩은 스피너 대신 **스켈레톤**을 쓴다. 카드·리스트 모두 최종 레이아웃과 같은 크기의 블록으로 자리를 잡아 레이아웃 이동을 없앤다

## 8. 컴포넌트

### 8.1 오늘의 카드 `daily-card`

**카드 뒤집기 구조 폐기, 요약 카드 + 화면 이동으로 교체(2026-09-13 사용자 결정, 9c 검수 통과·버그 0, `.pen` W0CjO·Keynu·VT4tS·kCfXv 반영, §13-80).** 오늘 탭 첫 화면은 소개받은 1명의 **요약 카드**(`daily-card-summary`)만 둔다. 탭하면 **10b(상대 프로필 상세 · 결정) 화면으로 이동**한다 — 종전 "탭하면 Y축으로 뒤집혀 뒷면이 나온다"는 폐기됐다. 거절·수락은 10b에서만 하고, 이 화면에는 액션 바를 두지 않는다.

**앞면 — `daily-card-summary` (오늘 탭 첫 화면, 2026-09-13 신규)**

**요약 카드 구조 확정(2026-09-14, 사용자 결정, §13-83 해결).** 카드 328×231(2026-09-14 개정, 종전 205 — 배지 행 신설로 확대), `{colors.surface-soft}`(`#F7F7F7`, `review-strip`과 같은 배경) 채움, `{radius.lg}` 24, `{colors.hairline-soft}` 1px 테두리, **§6 카드 그림자 두 겹(2026-09-13 재도입, §13-82 해결) — 그림자는 요약 카드에만 넣는다(§1)**. 패딩 사방 20(2026-09-14 개정, 종전 32/20/24/20 — 배지 행 신설로 상단도 20으로 통일. **간격 토큰표에 20이 없어 토큰표 밖 드리프트로 기록 — 토큰화 여부는 별도 결정 대기**). 내부는 세로 간격 12의 **Card Top**(0번) = [`Badge Row`(오른쪽 정렬, 간격 6 — 토큰표 밖 드리프트, 별도 결정 대기, 높이 30) / `Summary Row`]

   - **학생 인증** — `{colors.surface-ink}`(`#222222`) 채움, 흰 글씨, `badge-check` 아이콘("학교 인증"은 폐기). 항상 오른쪽 끝
   - **구매 카드** — `{colors.primary-pressed}`(`#E00B41`, 2026-09-14 사용자 결정 — 종전 `{colors.primary}` #FF385C에서 변경) 채움, 흰 글씨, `shopping-bag` 아이콘. 결정 대기 큐의 구매한 카드에만 노출. 흰 11/600 대비 4.89:1로 AA 통과(§2.1 참조) — 종전 3.52:1 예외 기록은 이 색 변경으로 필요 없어져 삭제
   - **무료 카드 초기화** — `{colors.primary-disabled}` 채움, `#222222` 글씨, `clock-3` 아이콘, "O요일 오전 N시까지" 형식으로 다음 무료 카드 지급 시각을 안내(예: "목요일 오전 7시까지")
2. **`Summary Row`** — 사진 원형 96dp(표시용 만화 아바타) + 흰 링 3px. 오른쪽에 닉네임·나이(`{type.title}` 20/600)와 학교·학과(14, `#6A6A6A`)를 사진 세로 가운데 정렬로 배치
3. **구분선(1px `#EBEBEB`) + 링크 행** — "프로필 자세히 보기 ›"(14/600, `#C4224B` = `{colors.primary-text}`) + `chevron-right` 18dp. 우측 `chevron-right` 단독 배치는 폐기, 카드 전체가 탭 영역인 것은 동일

**관심사 칩 없음.** 관심사는 10b 상세에서만 노출한다(2026-09-13 결정 유지).

- **카드는 화면에 하나만 존재한다.** 뒤에 다음 카드가 쌓인 듯한 시각 효과를 넣지 않는다
- 매칭 커플 지표 띠 · 후보 목록은 이 화면에 두지 않는다(§4.3). **추가 카드 결제 유도(잠금 카드)는 `W0CjO`·`Keynu`·`VT4tS`·`kCfXv` 4곳에 도입**(2026-09-13 사용자 결정, §13-84 해결)

- **`button-danger-strong` 신설(2026-09-13, 사용자 결정, §13-74).** 되돌릴 수 없는 행동(탈퇴 최종 확인 등) 전용 강조 변형 — `button-danger`(채움 옅음 + 에러색 텍스트)와 달리 **채움 자체가 `{colors.error}`**. 흰 글씨 대비는 #C13515 위라 충분. 56dp 채움 버튼(primary·secondary·danger·danger-strong·disabled 전부)의 라벨은 **18/700**(CLAUDE.md §7 "버튼 라벨은 18/700" 원칙과 통일) — 표에 라벨 크기 열이 없어 이 규칙을 별도로 명시한다. `button-text`(48dp)만 14px 예외.
- **인라인 버튼 높이 변형(2026-09-13, 사용자 결정, §13-75).** 표의 56dp는 **화면 하단 전체폭 CTA** 기준이고, 인라인 버튼(입력 옆·폼 제출·카드 안·채팅 입력 옆)은 맥락에 따라 낮아진다 — 시안 수정 없이 아래 규격을 그대로 인정: **52dp**(입력 옆·폼 제출: Verify Code·Invite·Edit Profile·Submit Review), **44dp**(카드 안: View Profile), **40dp**(채팅 입력 옆: Send). 토스 라운드 스케일(32→8/38→10/48→14/56→16)에 없는 중간값이라 라운드는 시안 실측값을 그대로 따른다.
- **`button-text` 표 텍스트색 오기 정정(2026-09-13 라운드7, datingapp-60 발견, §13-70).** `{colors.primary}`로 적혀 있었으나 흰 배경 위 텍스트 규칙(§2.1·§2.4)상 `{colors.primary-text}`(#C4224B)가 맞다 — 기존 시안(`03b` "나중에 확인하기" 등)도 전부 이 값. **표가 틀렸던 것으로 확인, 정정.** 크기(48dp·14px, 2026-09-12 결정)는 문서가 맞았고, 여러 화면에서 16/600으로 벗어나 있던 것은 시안 쪽을 14px로 재작업해 맞춘다(사용자 결정, §13-70)
- **버튼 라운드를 토스(TDS Mobile) 비례로 교체(2026-09-12, 사용자 — "버튼은 토스처럼 가자, 색상은 우리껄로").** 기존엔 버튼 높이와 무관하게 전부 `{radius.sm}`(8px, Airbnb 기준)를 썼다. 토스 TDS 버튼 스케일(32px→8 / 38px→10 / 48px→14 / 56px→16, 높이에 비례해 라운드가 커짐)을 그대로 가져오되 **색상·토큰 체계는 우리 걸 유지** — 56dp 버튼(primary·secondary·disabled) = 16px. **`button-danger`도 48→56dp로 통일(2026-09-12, 사용자 — "탈퇴는 왜 높이 동일하게 안 해?")** — secondary와 똑같이 채움이 있는 필(fill) 버튼인데 danger만 48이어야 할 근거가 없었다. 배경 없는 `button-text`만 48dp·14px로 남긴다(시각적 무게가 원래 다르므로). `{radius.sm}`(8px) 전역 토큰 자체는 안 건드리고(칩·입력 필드 등 다른 컴포넌트는 그대로) 버튼 컴포넌트에만 리터럴로 적용 — 이제 `{radius.sm}` 표기가 아니므로 위 표는 실제 픽셀값으로 적음. 참여 배지류(28dp 필 버튼)는 이미 `{radius.pill}`(9999)라 영향 없음
- **버튼 3종(secondary·danger·disabled) 채움을 `#E5E5E5`로 한 단계 진하게 조정(2026-09-12, 사용자 — "거절 버튼이 잘 안 보여").** 기존 `{colors.surface-strong}`(`#F2F2F2`)는 흰 배경 위에서 버튼처럼 안 읽혔다. `{colors.surface-strong}` 토큰 자체는 그대로 두고(원형 아이콘 버튼 바탕·상태 배지 등 다른 용도에 계속 쓰임) 버튼 3종의 채움만 리터럴로 살짝 더 진하게 뗐다 — 전용 토큰을 새로 만들 정도의 변화는 아니라고 판단 — 2026-09-15 `{colors.primary-disabled}` 로 토큰화(§2.1)
- **아웃라인 버튼을 쓰지 않는다(2026-09-09 변경).** `button-secondary`·`button-danger`·카드 액션 바 거절 모두 테두리 없이 채움(`{colors.primary-disabled}`, 2026-09-12부터 — 위 갱신 참조)으로 통일한다. 위험 신호는 `button-danger` 의 `{colors.error}` 라벨이 담당한다. 사진·서류 업로드 존도 같은 원칙 — 테두리 없이 `{colors.surface-soft}` 채움 + 내부 아이콘·라벨로 탭 영역을 알린다. 입력 필드(`text-field`)만 예외로 `{colors.outline}` 1px 를 유지한다(§2.4, 컨트롤 경계가 유일한 단서)
- 눌림: `button-primary` 는 `{colors.primary-pressed}`, 나머지는 `{colors.surface-soft}` 배경이 깔린다
- 비활성 버튼에 **연한 핑크를 쓰지 않는다.** Airbnb 는 `#FFD1DA` + 흰 글씨를 쓰지만 대비가 1.55:1 이라 읽히지 않는다. `{colors.primary-disabled}` 채움 + `{colors.disabled}` 텍스트를 쓴다
- 아이콘 전용 버튼은 시각 크기가 24dp 여도 터치 영역을 **48dp** 로 확장한다
- **재화 하트 글리프를 `button-primary` 채움(`{colors.primary}`) 위에 올릴 때는 on-primary 변형(`heart-flat-vector-on-primary-v1`)을 쓴다(2026-09-13 라운드5, §13-63 해결, §5.4).** 원본 `heart-flat-vector-v3`는 연분홍이라 같은 계열 핑크 버튼 위에서 대비가 약하다. 흰·연분홍 배경 위(잔액·리워드 등)에서는 계속 원본을 쓴다 — on-primary 변형의 흰 테두리가 오히려 떠 보인다

### 8.6 대화 탭

대화 탭은 **수락 대기**(위) + **대화 중**(아래) 두 섹션으로 구성된다. 채팅 동시 개수 상한은 없앴으므로(설계 문서 §2.5) 대화 중 목록이 5행을 넘을 수 있다 — 그래서 `acceptance-section`은 **상단에 sticky로 고정**해, 목록이 길어져도 수락 대기가 항상 먼저 보이게 한다. 전용 탭을 따로 두지 않는 근거는 "1인당 수락 유입이 하루 평균 0.3~0.5건이라 전용 탭이 대부분 비어 있다"는 이유 하나로 좁아졌다.

- `section-header` — `{type.subtitle}`, `{colors.ink}`, 좌측 정렬. 우측에 건수(`{type.body-small}`, `{colors.muted}`) — **"N명"으로 명시한다(2026-09-14 개정, §13-106) — 종전 "3 / 5" 같은 분수 표기 폐기. 예: 수락 대기 "2명", 대화 중 "3명". 노드 `Pr7mN`·`vcwaP`.** 위 `{space.lg}` / 아래 `{space.sm}`
- `acceptance-section` — 수락 대기 섹션. **건수가 0이면 섹션 전체를 그리지 않는다** (빈 섹션 금지). 대화 목록이 길어져도 상단에 sticky 로 고정한다
- `acceptance-row` — **정보 위 / 결정 아래 2단 구조.** 배경 `{colors.primary-wash}`, `{radius.md}`, 패딩 `{space.sm}`, 행 사이 `{space.xs}`
  - 윗단: 아바타 44dp 원형 + 이름·나이(`{type.subtitle}`) + 대학·학과(`{type.body-small}`, `{colors.muted}`)
  - 아랫단: **거절**(`button-secondary`, 폭 104) + **수락하고 대화 시작**(`button-primary`, 나머지 폭). 둘 다 높이 **44dp**
  - 버튼을 한 줄에 이름과 나란히 두지 않는다. 학과명이 긴 경우("컴퓨터과학과") 가운데 열이 줄바꿈되며 버튼이 어긋난다 — 시안에서 확인된 실제 문제다
  - 대화 중 행과 **배경색으로 구분**한다. 동작이 다른 리스트(수락/거절 vs 열기)를 같은 표면에 섞지 않는다
  - 윗단을 탭하면 상대 프로필 전체가 열린다. 결정은 프로필을 본 뒤에도 할 수 있어야 한다
- `chat-list-row` — 아바타 40dp 원형, 이름(`{type.subtitle}`), 마지막 메시지(`{type.body-small}`, `{colors.muted}`, 1줄), 우측에 시각(`{type.caption}`)과 `count-badge`. 행 높이 72, 배경 `{colors.canvas}`, 구분선 `{colors.hairline}`
- `bubble-mine` — `{colors.primary}` 채움, `{colors.on-primary}` 텍스트(`{type.body}`, 굵기 500), `{radius.md}` (우하단만 `{radius.sm}`)
- `bubble-theirs` — `{colors.surface-soft}` 채움, `{colors.ink}` 텍스트, `{radius.md}` (좌하단만 `{radius.sm}`)
- 말풍선 최대 폭 화면의 **78%**. 시각은 말풍선 밖 아래에 `{type.caption}` / `{colors.muted}`
- `chat-input-bar` — 하단 고정, `{colors.surface}`, 상단 `{colors.hairline}` 1px, 세이프 에어리어 준수. 전송 버튼은 원형 40dp `{colors.primary}`
- `trust-gate-sheet` — 매칭 24시간 경과 후 미응답 상태로 채팅방에 들어갈 때마다 뜨는 `bottom-sheet`(설계 문서 §2.5) + 24시간 시점 푸시. **개정(2026-09-14, 사용자 결정, §13-92 해결, 화면 `p0XJA6` §9 14f).** "카카오톡 아이디를 공유할까요?" + 설명 + 응답 기한 카운트다운(매칭 성립 + 48시간이 기한이라 카운트다운은 남은 시간) + **저장된 카카오톡 아이디 표시**("공유할 카카오톡 아이디 · hong_gildong · 변경" → `16e-1`) + 그 아래 "카카오톡 아이디로 친구 추가 허용" 안내 + `button-primary`(수락하고 공유하기) / `button-text`(거절하기). **입력칸 없음** — 카카오톡 아이디는 가입(`04-1b`, §13-91)에서 이미 받았으므로 이 시트에서는 저장된 값을 보여주고 바꾸는 것만 한다
  - 쌍방 수락 시: 채팅방 헤더 사진이 표시용 아바타 → 실사진으로 전환되는 순간 `{motion.emphasis}`를 쓴다(매칭 성사와 같은 급의 순간으로 취급). 대화창에는 "OO님과 카카오톡 아이디를 주고받았어요" 시스템 메시지 + 카톡 아이디를 담은 전용 정보 카드 버블이 붙는다
  - **내가 수락, 상대 미응답** — 화면 `SJWl0`(§9 14g): 헤더 아래 배너 "수락했어요. 상대의 응답을 기다리고 있어요 / 응답 기한까지 hh:mm:ss · 둘 다 수락하면 카카오톡 아이디와 실제 사진이 공개돼요"(2026-09-14 캡션 정정 — 종전 "카카오톡 아이디가 공개돼요"에 실제 사진 공개를 추가, 설계 문서 §2.5와 일치). 상대가 거절해도 알리지 않고 기한에 조용히 종료(2.2절 원칙과 동일 톤)
  - **내가 거절** — 화면 `KGjJx`(§9 14h): 배너 "이 대화는 21시간 뒤 종료돼요 / 응답 기한이 지나면 대화 목록에서 사라져요". **문구 정정(2026-09-14)**: 종전 "48시간 뒤 이 대화가 종료돼요"는 기한 정의(매칭 성립 시각 + 48시간)와 맞지 않아, 지금부터 남은 시간을 그대로 보여주는 표기로 바꿨다
- **상대가 탈퇴한 채팅** (신규, 2026-09-13 확정 — 설계 문서 §2.6, ERD.md §11-15) — 게이트를 통과한 매칭만 해당. 읽기·신고만 되고 메시지 입력은 막히며, 30일 뒤 대화 목록에서 사라진다. 화면 시안은 후속 조각에서 만든다

### 8.7 이름 표기 (2026-09-10 전면 개정)

**앱 어디에서도 실명을 보여주지 않는다. 사용자를 가리키는 이름은 항상 닉네임이다.**
예전의 `김○○` 마스킹 방식(매칭 전 마스킹 → 매칭 후 실명 공개)은 폐기했다. 근거는 설계 문서
§13 미결5·37 — 카드가 닉네임을 보여주는 쪽으로 바뀌면서 가릴 실명이 화면에 존재하지 않는다.

| 위치 | 표기 | 예 |
| --- | --- | --- |
| 오늘의 카드 요약 · 10b 상세 | 닉네임 | `여우비, 23` |
| 수락 대기 행 | 닉네임 | `초코라떼, 25` |
| 대화 중 목록 · 채팅방 | 닉네임 | `여우비` |
| `friend-review-card` 리뷰어 | 닉네임 | `달빛` |
| 내 프로필 (화면 15) | 내 닉네임 | `여우비` |
| 설정 > 계정 정보 (화면 16) | **본인만** 실명 조회 | `실명 (비공개)  홍길동` |

- **매칭 성사 후에도 닉네임을 그대로 쓴다.** 실명 공개 단계가 없다 — 신뢰 확인 게이트(§2.5)에서
  실사진과 카카오톡 아이디가 공개되므로, 앱이 실명까지 노출할 이유가 없고 유출 표면만 넓어진다.
  "이제 서로의 이름을 볼 수 있어요" 문구도 제거
- 실명(`real_name`)은 학생증 인증·운영 조회 전용이라 **서버 응답 어디에도 담기지 않는다** —
  `profile_private.real_name`(민감 컬럼)에만 저장한다(설계 문서 §7.3, ERD.md §11-2. "설계 문서 §7 예외 2"는
  설계 문서에 없는 참조였다). 본인 실명은 설정 > 계정 정보에서만, 그 자리에서 왜 받는지 한 줄 안내
- `○`(U+25CB) 마스킹 문자·스크린리더 예외 규칙은 더 이상 쓰지 않는다 — 닉네임은 실명이
  아니므로 가리지 않고 그대로 읽어준다
- 닉네임 제약·중복·변경 정책은 `nickname-field`(§8.5)와 설계 문서 §5.3

- `account-delete-sheet` (신규) — `bottom-sheet` 기반. 삭제되는 항목 안내(`list-row` — 프로필·매칭 기록·채팅·쓴/받은 지인 리뷰·투표 글과 표·남은 하트 전부, "**30일 뒤 완전 삭제**"와 "**결제 내역은 법에 따라 보관**"을 강조 문구로 명시, **탈퇴는 되돌릴 수 없음을 함께 안내(2026-09-14, ERD.md §11-21)**, 2026-09-13 확정 — 설계 문서 §2.6, ERD.md §11-15) + `button-danger`("영구 삭제") + `button-text`("취소"). 이중 확인: `button-danger` 탭 시 같은 시트 안에서 문구가 "정말 삭제할까요?"로 바뀌고 버튼이 한 번 더 노출(재확인 없이 즉시 삭제되지 않도록). **마스코트는 아쉬워하는 표정의 핑크 목도리 여자 버전(`mascot-female-sad.png`)으로 넣는다(2026-09-09 시안 반영).** 울거나 붙잡는 표정처럼 탈퇴를 죄책감으로 막는 연출은 쓰지 않는다. 탈퇴 전에 **매칭 일시중지를 먼저 제안**하는 문구를 시트 상단에 둔다(설계 문서 §2.6, 재가입 2개월 제한이 있으므로 대안을 먼저 보여준다)

- `friend-review-card` (신규, 2026-09-08 — 설계 문서 §2.8 지인 리뷰) — 카드 상세와 프로필에 노출되는 지인 평가 한 장. 구성은 좌측부터 **대학 로고(20dp) + 만화 아바타(32dp) + 리뷰어 닉네임(`{type.label}`, 2026-09-10 — 마스킹 실명에서 변경)**, 그 아래 **장점 태그 `chip` 여러 개 + 자유 텍스트 한 줄(`{type.body-small}`, 2줄 말줄임)**.
  - **가로 스크롤 레일로 배치한다** — 리뷰 개수 제한이 없으므로(전부 노출) 카드 세로 길이가 늘어나지 않게 `mosaic-rail`과 같은 가로 스크롤 패턴을 쓰고, 3장 이상이면 끝에 "더보기"를 둔다
  - **리뷰가 0개면 블록 전체를 숨긴다** — `stat-panel`·`review-strip`과 동일한 원칙(§8.9). 빈약한 상태를 보여주는 것보다 안 보여주는 게 낫다
  - 각 카드에 `flag` 신고 아이콘(기존 신고 컴포넌트 재사용). 신고 누적 시 자동 블라인드(설계 문서 §13 미결18)
  - **로고 이미지는 사용자가 직접 제공한다(2026-09-08).** 대학별 파일을 `design/designMaterials/university/` 에 두고 학교 코드와 파일명을 1:1로 맞춘다. 파일을 갖고 있는 것과 쓸 권리가 있는 것은 다르므로 **상표권 확인은 그대로 남는다** — 사용 지침상 불가하면 상징색 배경 + 학교명 텍스트의 자체 배지로 폴백한다(**이 문서 §13-29 — 종전 "설계 문서 §13 미결29"로 잘못 표기돼 있었다. 설계 문서(spec doc)가 아니라 이 문서(DESIGN.md) 자신의 §13-29 "대학 로고 파일 미수령" 항목을 가리켜야 했고, 2026-09-13 spec doc 미결29가 전혀 다른 주제(매칭 상대 차단)로 완전 해결 처리되면서 충돌이 드러나 이번에 정정했다**)

- `review-compose-sheet` (신규, 2026-09-08) — 지인 리뷰 작성 `bottom-sheet`. 상대 아바타+이름 → **장점 태그 다중 선택(`chip` 그리드, 최대 3개, 12종 고정 목록 — 2026-09-13 확정, §13-25)** → 자유 텍스트 한 줄 `text-field`(**선택 사항, 최대 100자** 카운터 노출) → `button-primary`("리뷰 남기기"). 온보딩에서 추천 코드 입력 직후, 그리고 추천인이 푸시를 탭했을 때 이 시트가 뜬다. **태그 12종**: 약속을 잘 지켜요·대화가 편해요·배려가 깊어요·유머 감각이 좋아요·성실해요·솔직해요·이야기를 잘 들어줘요·긍정적이에요·센스 있어요·다정해요·차분해요·리액션이 좋아요 — 외모 관련 태그는 넣지 않는다(지인이 외모를 평가하면 리뷰가 품평이 됨). **시안은 현 상태 유지(사용자 결정, 2026-09-13)** — 시안(원본 `NHcsP`, 유저플로우 사본 `Zr9gA`)은 태그 6종(배려가 깊어요·약속을 잘 지켜요·대화가 편해요·유머 감각이 좋아요·연락이 성실해요·취미가 다양해요)만 있고 "최대 3개" 안내 없음, 한마디 라벨 "한마디를 남겨주세요"(선택 사항 표시 없음)에 글자 수 "0/80"으로 위 12종·최대 3개·100자 결정과 다르지만 시안은 수정하지 않는다. **구현은 시안이 아니라 이 문서의 확정 사항(12종 고정 목록, 최대 3개, 자유 코멘트 선택·100자)을 따른다**

### 8.9 메인 화면

메인의 목적은 두 가지다.

1. **지금 CampusMate 안에 사람이 있다는 것을 보여준다**
2. **카드를 한 장 더 받고 싶게 만든다**

순서가 있다. 사람이 있다는 확신이 먼저 서야 카드를 더 받을 이유가 생긴다. 그래서 위에서 아래로 **내 현황 → 사람 → 규모 → 학교 → 유도** 순으로 쌓는다.

| 순서 | 블록 | 답하는 질문 |
| --- | --- | --- |
| 1 | `hero-today` | 오늘 내 카드는 어떻게 됐나 |
| 2 | `mosaic-rail` | 여기 사람이 있나 |
| 3 | `stat-panel` | 이 서비스가 돌아가고 있나 |
| 4 | `review-strip` | 남들은 이 앱을 어떻게 평가하나 |
| 5 | `campus-strip` | 내 학교 사람이 있나 |
| 6 | `more-card-cta` | 더 만나려면 뭘 하면 되나 |

**`hero-today`** — 메인 최상단. `{radius.xl}`, 카드 폭 전체, 내부 CTA 버튼(`button-secondary`, 흰 채움) 기준으로 위아래 20px 대칭 여백

- 카드가 대기 중일 때: `{colors.primary}` 채움 + "오늘의 카드가 도착했어요" + `button-secondary` "지금 확인하기" — 높이 160 (CTA 48/`{radius.md}` 14, 텍스트-버튼 사이 간격 24)
- 결정 대기 카드가 남아 있을 때: `{colors.primary-wash}`(`#FFF0F2`) 채움 + "결정 대기 카드가 N장 남아 있어요" + `button-secondary` "이어서 확인하기" + 우상단 `count-badge`(§8.9 결정 대기 큐 배지) — 높이 160 (CTA 48/`{radius.md}` 14)
- **두 상태 모두 높이 160으로 통일한다**(§13 미결46) — 같은 배너 슬롯이 상태에 따라 색만 바뀌는 것이므로 높이가 다르면 화면이 덜컥거린다
- 이미 확인했을 때: `{colors.surface-soft}` 채움 + 카운트다운(32/700) + "내일 오전 7시"
- **이 배너가 오늘 탭으로 가는 유일한 유도 지점**이다. 다른 곳에서 카드를 열게 하지 않는다

**`mosaic-rail`** — 표시용(만화 아바타) 4:5 카드가 가로로 **자동 슬라이드**한다. 카드 폭 120, 간격 `{space.sm}`, `{radius.md}`

- 속도는 느리게(약 20초에 한 바퀴), 이징 없이 **선형 등속**. 빠르면 광고처럼 보인다
- **축소 모션이 켜져 있으면 자동 슬라이드를 멈춘다.** 손으로 밀 수는 있게 남긴다
- 자동 회전 콘텐츠이므로 **일시정지 수단을 제공**한다 (탭하면 멈춤, `pause` 아이콘). WCAG 2.2.2 요건이다
- **탭해도 프로필이 열리지 않는다.** 미리보기 유도 금지 규칙(§10)은 여기에도 적용된다

*동의·서버 처리가 필요 없어졌다.* 표시용 사진은 애초에 AI가 그린 만화 아바타라 실물을 특정할 수 없다. 그래서 이전 버전의 "내 사진을 메인 화면에 흐리게 노출" 동의 옵션과 서버 픽셀레이션 처리는 전부 없앴다(5.2절 갱신) — **모든 사용자의 표시용 사진이 그대로 레일에 오른다.** 아직 표시용 사진이 없는 계정(변환 대기 중 등)만 `{colors.primary-wash}` 색 블록 + 마스코트로 채운다.

**`stat-panel`** — 3칸 가로. 각 칸: 아이콘 20dp(`{colors.primary}`) → 숫자(`{type.title}`) → 라벨(`{type.caption}`, `{colors.muted}`). 배경 `{colors.surface-soft}`, `{radius.md}`

| 칸 | 아이콘 | 라벨 | 집계 |
| --- | --- | --- | --- |
| 1 | `send` | 전달된 카드 | 서비스 시작 이후 누적 |
| 2 | `user-plus` | 가입 수 | 인증 완료 계정 누적 |
| 3 | `message-circle` | 시작된 대화 | 상호 수락으로 열린 채팅방 누적 |

세 지표 모두 **누적**이다. 누적은 줄어들지 않으므로 어제보다 작아 보이는 날이 없다. "오늘"·"이번 주" 단위는 조용한 날에 숫자가 주저앉아 오히려 죽어 보인다 — 그래서 뺐다.

**`review-strip`** — 가로 한 줄. 좌측 별점(`{type.title}`, 예: "4.8") + 별 아이콘 5개(채움/외곽 혼합) + "(143명 평가)" 캡션(2026-09-14 예시값 정정, §13-106 — 종전 "1,204명"은 `stat-panel` "시작된 대화" 예시값과 겹치던 오기재였다), 우측 `button-text` "리뷰 남기기" → 스토어 리뷰 페이지로 딥링크. 배경 `{colors.surface-soft}`, `{radius.md}`

- 데이터는 앱스토어·플레이스토어 리뷰 API 값을 그대로 쓴다. **숫자를 합성하거나 반올림 이상으로 꾸미지 않는다** (§8.9 지표 규칙과 동일 원칙)
- 리뷰 수가 임계값 미만이면(§13 미결 9와 동일한 사고방식) 이 블록 전체를 숨긴다 — 빈약한 숫자를 보여주는 것보다 안 보여주는 게 낫다
- "리뷰 남기기" 버튼은 스토어 페이지로 연결된다. **보상은 주지 않는다** — 애플·구글 정책이 리뷰 대가 제공을 금지하므로 하트 무료 획득 항목에서 제외했다(§8.10, 2026-09-08)
- **메인의 모든 상태에 일괄 적용한다(2026-09-14 사용자 결정, §13-100 참조)** — 기본 메인(`bpA8x`)과 그 유저플로우 사본 전부에 `stat-panel` 바로 아래로 넣는다. 이 블록이 추가되며 해당 화면 높이 780 → **884**

**`campus-strip`** — 참여 중인 대학 이름을 칩으로 가로 나열. `{type.caption}`, `{colors.muted}`. 어떤 학교가 들어와 있는지가 곧 신뢰 신호다. 학교 수가 적을 때는 숫자("20개 대학")를 앞세우지 말고 이름만 보여준다

**`more-card-cta`** — 메인 하단. `{colors.primary-wash}` 바탕, `{radius.lg}`, 좌측 마스코트 72dp + 우측 문구 2줄(완성도 게이지)

**카드를 더 받는 수단 (§13 미결 12 — 확정).**

- **프로필 완성도 (기본, 무상).** "자기소개를 채우면 더 잘 맞는 카드를 받아요" — 매칭 벡터 품질을 실제로 올리므로 거짓이 아니다. 완성도 게이지(0~100%)를 함께 보여준다. **완성도는 자기소개·태그·설문·사진으로 계산한다 — 사진이 2~4장 가변이 되면서 2026-09-13부터 변수에 포함된다**(종전 "사진은 정확히 2장 고정이라 변수 아님"은 폐기, 설계 문서 §13 미결4 해결·§13-51). 사진 장수가 완성도에 몇 % 반영되는지 정확한 배점은 아직 미정 — 조각 2에서 확정
- **하트로 추가 카드 — 구매 입구는 오늘 탭 잠금 카드(§8.1 `daily-card-locked`) → `x2yPl` 시트(§9 화면10c) 하나뿐이다**(2026-09-14, §13-97·101 — 메인 하트 CTA와 "메인 · 추가 카드 사용 완료"(구 09c) 화면은 삭제). `18a` 무료 획득 목록은 `x2yPl` 시트 안에서 계속 진입 가능
  - **지급 주기당 1장까지, 다음 카드가 오기 전까지는 언제든 살 수 있다**(2026-09-08 수정). 제한하는 것은 **사는 시점이 아니라 여는 횟수**다 — 상한이 주기당 1장으로 그대로라 "돈을 내면 카드가 계속 나온다"가 되지는 않는다. 지급일 당일에만 구매 경로를 열어 두던 이전 규칙은 폐기한다. 사고 싶은 순간과 살 수 있는 순간이 어긋나면 리듬은 지켜지지 않으면서 결제만 막힌다
  - **구매한 카드는 갱신돼도 사라지지 않는다.** 갱신 한 시간 전에 산 카드가 한 시간 만에 증발하면 그건 결제 사고다. 무상 카드는 다음 지급 때 만료되고, **무응답으로 만료된 경우에만** 상대가 재노출 대상으로 돌아간다 — 수락·거절한 상대, 매칭 이력 상대는 영구 제외(2026-09-13 확정, ERD.md §11-4. "설계 문서 §13 미결31"은 실제로는 지인 리뷰 목록 항목이라 없는 참조였다). **구매한 카드는 수락·거절을 누를 때까지 결정 대기 큐에 남는다**(바로 아래). **결정 대기 중에도 추가 구매를 계속 허용한다**(2026-09-14 사용자 결정, §13-83 해결) — 이번 주기에 새로 산 카드는 잠금 카드 자리에 열리고, 그 주기엔 잠금 카드가 다시 노출되지 않는다(§8.1)
  - 초대 보상(친구 초대 시 카드 +1)은 보류한다 — 사람 수를 늘리는 정직한 방법이지만, 대학 이메일 인증과 중복 계정 방지 설계가 선행되어야 한다

**`pending-decision-queue` (신규, 2026-09-08, 쌓기 순서 2026-09-14 확정 — §13-83·88 해결).** 구매한 추가 카드가 만료되지 않으므로 "아직 수락·거절하지 않은 카드"가 쌓일 수 있다. 별도 화면을 만들지 않고 **오늘의 카드(화면 10)를 큐로 확장**한다 — 탭·구역 헤더 없이 위에서부터 **[이번 주기 무료 카드 → 이번 주기 잠금 카드 → 이전 주기에 산 카드(결정 전까지 쌓임)]** 순서로 보여준다(2026-09-14 사용자 결정 — 종전 "구매 카드 먼저" 순서를 뒤집음).

- 메인 `hero-today` 우상단에 `count-badge` 로 결정 대기 장수를 표시한다. 0이면 배지를 그리지 않는다(§8.8 빈 요소 금지 원칙)
- 큐가 비면 기존 화면 11(카드 소진 · 대기)로 그대로 이어진다
- **산 카드는 만료 없음, 무료 카드는 다음 지급 때 만료** — 만료 규칙이 서로 다른 두 종류이므로 화면 안에서 위치(무료가 위, 구매가 아래)로 구분한다. 결정 대기 중에도 추가 구매는 계속 허용된다(§8.1)
- 구매 카드는 똑같은 `daily-card-summary` 구조를 쓰고 `Badge Row`(§8.1)의 "구매 카드" 배지로 구분한다. 결정 대기 화면(`Keynu`·`VT4tS`·`kCfXv`)은 "10 오늘의 카드 · 결정 대기 구매 카드 있음"으로 개명, 높이 918(§9 화면10)

**`my-record`** — "내가 받은 수락 3회 · 대화 3개". 개인 기록은 서비스가 작아도 항상 의미가 있다. 지표가 비어 있는 초기에는 이 블록이 `stat-panel` 을 대신한다

**지표에 관한 규칙 — 이것이 메인 설계의 핵심이다.**

1. **어떤 숫자도 조작하지 않는다.** 부풀린 접속자 수는 표시광고법상 거짓·과장 표시이고, 스토어 심사 대상이며, 들키면 신뢰가 한 번에 무너진다
2. **동시접속자를 쓰지 않는다.** 초기에 "지금 접속 3명"이 뜨면 서비스가 죽어 보인다. 가장 크게 보이고 싶은 자리에 가장 약한 숫자를 놓는 셈이다
3. **매칭률처럼 정의가 모호한 지표를 쓰지 않는다.** 무엇을 무엇으로 나눈 값인지 한 줄로 설명할 수 없으면 넣지 않는다
4. **데이터가 없으면 숫자를 지어내지 않고 자리를 바꾼다.** 임계값 미만인 칸은 숨기고, 세 칸이 모두 미달이면 `stat-panel` 전체를 **마스코트 72dp + "첫 기록이 쌓이는 중이에요" 한 줄**로 대체한다(`.pen` 스니펫 `Tklrw`, 남성 마스코트로 통일 — 기본 09b 보드가 아니라 대체 상태 스니펫). 숫자가 준비되면 같은 자리에 그대로 들어온다 (§13 미결 9)
5. 숫자는 **천 단위 구분 기호**를 넣는다

### 8.10 하트(재화) · 스토어

**하트는 이제 유일한 수익원이다(설계 문서 §2.4, 2026-09-08 등록비 폐지).** 그래도 여전히 **완전히 선택적인** 편의 재화라는 성격은 그대로다 — 매칭·카드 조회·채팅 등 핵심 기능 어디에도 하트를 요구하지 않는다. 하트로 살 수 있는 것은 **추가 카드(§8.9, 50하트)와 아바타 재생성(10하트, 최초 1회 무료) 둘뿐**이다. 어느 쪽도 매칭 품질에 영향을 주지 않는다 — 추가 카드도 동일한 벡터 매칭 큐를 그대로 쓴다(§13 미결19 원칙).

**`review-pending`** (검수 대기 화면) — 3b 학생증 인증 대기 화면과 동일한 패턴 재사용: 마스코트 128dp(§5.4 표) + "확인하고 있어요" + 설명 "영업일 기준 1~2일 안에 알려드릴게요". 이 화면에서 나가도 되고, 완료/반려 시 알림으로 안내(§13 신규 미결 — 알림 채널 미정)

### 8.11 커뮤니티

**목적은 하나 — 오늘 카드가 없는 날에도 열어볼 이유를 최소한으로 만드는 것**(최종보고서 §6-8 권고: "매칭 외 콘텐츠는 스코프를 강하게 제한"). 그래서 컴포넌트는 `poll-card` 하나로 제한한다 — 타로·미니게임·스토리형 콘텐츠 등 썸타임의 나머지 체류 장치는 가져오지 않는다.

**`poll-card`** — 리스트형 피드의 기본 단위. `{radius.md}` 카드, 내부 패딩 `{space.md}`

- 상단: `verified-chip` 스타일의 익명 표시("익명") + 작성 시각(상대 시간, `{type.caption}`)
- 중앙: 질문 텍스트(`{type.subtitle}`, 최대 2줄, 넘치면 말줄임)
- **투표 전**: 좌우 2개 버튼. 라벨이 기본값("찬성"/"반대")이면 텍스트 없이 **O·X 아이콘 버튼만**(좌 O = 찬성 파랑 `#2D96DE` 채움, 우 X = 반대 `{colors.primary}` 채움, 흰 아이콘, 2026-09-11 변경 — 종전 O=`{colors.primary}`·X=`{colors.surface-strong}`에서 사용자 요청으로 교체). 커스텀 라벨이면 라벨 텍스트를 담은 `button-secondary` 2개. 버튼 하나를 누르면 투표 확정 — **투표는 되돌릴 수 없다**(재투표로 결과를 조작하지 못하게)
- **투표 후 / 남의 투표 결과를 볼 때**: 버튼 자리가 **도넛 차트**(지름 96, 두께 12, 두 색은 `{colors.primary}` vs `{colors.surface-strong}`)로 바뀌고, 안쪽에 우세한 쪽의 퍼센트(`{type.title}`)를 표시. 도넛 아래 "찬성 62% · 반대 38%" 텍스트 한 줄과 "127명 참여" 캡션
- 하단: `chevron-right`로 상세(전체 댓글·참여자 수) 진입 — 상세 화면은 이번 스코프에서는 **투표 비율 상세 + 참여자 수만** 보여주고 댓글은 만들지 않는다(모더레이션 부담, §13 신규 미결)

**`poll-composer`** (질문 작성 화면) — `app-bar` "익명으로 질문하기" + 질문 입력 `text-field`(멀티라인, 최대 80자 카운터) + 옵션 A/B 라벨 입력(기본값 "찬성"/"반대", 자유 수정 가능) + `button-primary` "익명으로 올리기". 상단에 "작성자 정보는 절대 공개되지 않아요" 안내 1줄

- **모더레이션은 이번 스코프에 포함하지 않는다** — 신고 버튼(`flag`, 기존 신고 컴포넌트 재사용)만 카드마다 붙이고, 처리 정책은 조각6(safety)에서 별도 결정(§13 신규 미결)

**커뮤니티 탭 피드 구조** — `app-bar`(제목 "커뮤니티" + 우측 `+`아이콘 버튼 → `poll-composer`) + `poll-card` 세로 리스트(무한 스크롤) + 빈 상태는 기존 `empty-state` 패턴("아직 질문이 없어요" + "질문 올리기" `button-secondary`)

### 8.12 지인 차단

**목적** — 연락처에 저장된 특정 지인과 서로의 프로필이 매칭 후보에 뜨지 않게 한다.

**2026-09-08 수정 — 전화번호 수집과 "차단할 사람 고르기"를 분리했다.** 지인 차단은 상호 대조라서, 차단하는 쪽(B)이 차단당하는 쪽(A)을 걸러내려면 A의 번호가 시스템에 먼저 등록돼 있어야 한다 — A가 지인 차단에 관심이 없어도 마찬가지다. 그래서:

- **전화번호 등록은 회원가입 필수** — 04 온보딩 1(기본 정보) 화면에서 생년·키·성별과 함께 받는다(§9 화면 4 참조). 별도 소개·동의 화면 없음
- **차단할 사람을 고르는 것(8d, `contact_blocks`)만 선택 사항** — 원할 때 설정 탭에서 진행한다

> **마스코트를 쓰지 않는다.** §5.4의 "신고·차단 흐름에 마스코트 금지" 원칙을 그대로 적용한다 — 참고한 경쟁사 화면(썸타임)은 마스코트를 쓰지만, 이 흐름은 개인정보와 안전이 걸린 화면이라 CampusMate 자체 원칙이 우선한다. 아이콘은 `shield-check`.

**8d 차단할 연락처 선택** (설정 탭에서만 진입, 온보딩에는 없음)

- OS 연락처 권한 요청 다이얼로그(시스템 기본) 이후 진입
- 연락처 리스트, 각 행은 이름 + 마스킹된 번호(`010-****-1234`) + 우측 체크박스, 다중 선택
- 상단 검색창, 하단 고정 `button-primary` "선택 완료 (N명)" — N은 실시간 카운트, 0명이면 비활성
- 완료 시 16b 화면으로 돌아가 갱신된 차단 목록을 바로 보여준다

**설정 탭 진입점** — 기존 `16 설정` 화면의 "차단 목록"(매칭·채팅 상대 차단, 조각 6 기존 기능) 행과 **이름이 겹치므로 구분**: 새 행 "**연락처 차단**"을 별도로 추가한다. 설명 문구 "연락처 속 지인이 나를 발견하지 못하도록 차단해요" + `chevron-right`

**16b 연락처 차단 관리** (설정 진입점 → 이 화면)

- **이름·마스킹 번호의 출처 — 확정(2026-09-13 사용자 결정, ERD.md §11-9).** 서버는 지인 연락처의 이름·번호를 원본으로 갖고 있지 않다(HMAC 해시만 저장, §8.12 상단). 8d에서 고를 때 앱이 이름·마스킹 번호를 **기기 안에만** 저장하고, FastAPI가 등록 응답으로 돌려준 `contact_blocks.id`를 키로 짝지어 이 화면에 보여준다. **앱을 재설치하거나 기기를 바꾸면** 그 키에 대응하는 이름이 로컬에 없으므로 "이전에 차단한 연락처"로 표시하되(이름·번호 없이), 차단·해제 자체는 서버 쪽 HMAC 매칭으로 그대로 동작한다
- 상단 `button-secondary` "+ 추가"(8d 연락처 선택으로 이동) + 차단된 연락처 리스트(이름 + 마스킹 번호, 기기에 없으면 "이전에 차단한 연락처" + 우측 `trash-2` 아이콘 버튼으로 개별 해제)
- **`trash-2` 탭 시 `bottom-sheet` 로 재차 확인한다(2026-09-09 변경)** — "차단을 해제할까요? / 이 연락처가 다시 카드에 나타날 수 있어요." + `button-primary` "해제" 위, 중립 채움(`{colors.surface-strong}`, 테두리 없음) "취소" 아래. 즉시 반영·되돌리기 스낵바는 쓰지 않는다 — 지인이 나를 발견하지 못하게 하는 설정이라 실수로 푸는 비용이 크고, 스낵바는 스크롤·이탈로 쉽게 놓친다
- 빈 상태: 기존 `empty-state` 패턴 + "아직 차단한 연락처가 없어요" + "+ 추가" 유도

### 8.13 자주 묻는 질문 `faq` (신규, 2026-09-08)

**왜 만드는가.** 이 앱에는 설명 없이는 오해를 사는 규칙이 여럿이다 — 카드가 매일 오지 않고, 산 카드를 바로 여러 장 열 수 없고, 실사진이 매칭 전엔 안 보이고, 받은 리뷰를 지울 수 없다. 규칙 하나하나를 그 자리에서 길게 설명하면 화면이 무거워지므로, **짧은 고지는 그 자리에 두고 자세한 설명은 여기로 모은다.**

**`faq-row`** — 질문 한 줄(`{type.label}`) + 우측 `chevron-down` 20dp. 탭하면 같은 카드 안에서 답변(`{type.body}`, `{colors.muted}`)이 펼쳐진다. 펼침·접힘은 `{motion.standard}`. 화면 이동이 아니라 아코디언인 이유는 **찾는 사람이 목록과 답을 번갈아 본다**는 것 하나다.

- 카테고리별 `section-header` 로 묶는다 — **카드·매칭 / 하트·결제 / 사진·프로필 / 지인 리뷰 / 안전·신고 / 계정**
- 상단에 `text-field` 검색 1개. 질문·답변 본문을 모두 대상으로 하는 단순 부분일치면 충분하다
- 한 번에 하나만 펼친다(아코디언). 여러 개가 동시에 열리면 스크롤 위치를 잃는다
- **빈 상태 없음.** 문구를 서버에서 받아오는데 실패하면 마지막 캐시를 그린다. 캐시도 없으면 이 진입점 자체를 숨긴다

**진입점 두 곳.**

| 위치 | 형태 |
| --- | --- |
| 설정(16) | `list-row` "자주 묻는 질문" + `chevron-right` |
| 하트 스토어(15e, 구 18)·결제 확인 시트(18d) | `app-bar` 우측 `help-circle` 20dp — 눌리면 **하트·결제 카테고리로 스크롤된 상태**로 연다 |

**문구는 Supabase `faq` 테이블에서 받는다(2026-09-08 확정).** 하드코딩하면 오타 하나 고치는 데도 스토어 심사가 필요하다. 초기 운영에서 문구가 가장 많이 바뀌는 영역이라 원격 수정이 가능해야 한다. 앱은 마지막 응답을 로컬에 캐시해 오프라인·실패 시에도 그대로 그린다.

## 10. Do / Don't

### Do

- Rausch 는 한 화면에 **한두 곳**만. 수락 버튼이 있으면 그 화면의 Rausch 는 거기서 끝이다
- 모든 탭 가능한 요소는 **48dp 이상**의 터치 영역을 갖는다
- 색으로 전달하는 모든 상태에 **아이콘이나 텍스트를 함께** 붙인다
- 에러는 **문제가 생긴 필드 바로 아래**에 놓는다
- 하트 잔액·가격·타이머 숫자에는 tabular figures 를 적용한다
- 사진은 로딩 전에 4:5 자리를 미리 잡아둔다
- 신고·차단은 채팅방과 프로필 양쪽에서 두 번의 탭 안에 도달한다
- 결제 금액과 성별 차등 조건은 결제 시트에 **그대로 적는다**
- 사용자를 가리키는 이름은 전 화면에서 닉네임이다. 실명(`real_name`)은 서버 응답에 아예 담지 않는다 (§8.7)

### Don't

- **좌우 스와이프 제스처를 만들지 않는다.** 이 앱은 덱이 아니다
- 카드 뒤에 다음 카드가 쌓인 듯한 시각 효과를 만들지 않는다
- 궁합 점수·일치율 같은 숫자를 노출하지 않는다
- 그라데이션 배경을 쓰지 않는다. 브랜드 그라데이션도 만들지 않는다
- 이모지를 아이콘으로 쓰지 않는다. 모든 아이콘은 벡터 한 가족(외곽선 1.5px)에서 가져온다
- 하트 아이콘을 남발하지 않는다. 수락은 하트가 아니라 체크로 표현한다
- 버튼·칩·앱바에 그림자를 넣지 않는다
- 플레이스홀더를 라벨 대신 쓰지 않는다
- 비활성 버튼에 연한 핑크(`#FFD1DA`)를 쓰지 않는다
- 오늘의 카드 화면에 배너·추천·프로모션을 추가하지 않는다
- 위젯 안에 `Color(0xFF...)` 리터럴이나 하드코딩된 수치를 쓰지 않는다
- 결제 유도에 카운트다운 타이머를 쓰지 않는다(원가 취소선 병기는 2026-09-14부터 허용, §13-114)
- 상대의 실명을 어디에도 노출하지 않는다 — 매칭 전후 모두, 푸시 알림 문구 포함. 항상 닉네임을 쓴다
- 카드에 스와이프 제스처를 걸지 않는다. 요약 카드 전체가 탭 영역이다 (§8.1)

## 11. 반응형 · 접근성

### 11.1 화면 폭

| 이름 | 폭 | 처리 |
| --- | --- | --- |
| 소형 | 320–359 | 카드 사진 4:5 유지, `{type.display}` 를 28 로 낮춤. 액션 바 라벨 한 줄 유지 |
| 표준 | 360–429 | 기준 설계 폭. 좌우 여백 16 |
| 대형 | 430–599 | 좌우 여백 20 으로 확대. 나머지 동일 |
| 태블릿·폴더블 | 600+ | 콘텐츠 최대 폭 **480** 으로 고정하고 가운데 정렬. 카드가 화면 전체로 늘어나지 않게 한다 |

- 가로 스크롤이 발생하면 버그다
- 가로 방향(landscape)에서도 카드 화면이 깨지지 않아야 한다. 카드를 스크롤 가능하게 만들고 액션 바를 고정한다

### 11.2 접근성

- 본문 대비 4.5:1, 컨트롤 경계 3:1 (§2.6 검증 완료)
- 터치 타깃 iOS 44pt / Android 48dp 이상, 인접 간격 8dp 이상
- 시스템 글꼴 확대(최대 배율 2.0)에서 레이아웃이 깨지지 않아야 한다. 고정 높이 컨테이너 안에 긴 한글을 넣지 않는다
- 모든 아이콘 버튼에 `Semantics(label:)` 를 준다. 장식용 아이콘은 `ExcludeSemantics` 로 접근성 트리에서 감춘다
- 스크린 리더 포커스 순서가 시각 순서와 일치해야 한다
- 축소 모션 설정을 존중한다 (§7)
- 인증코드 필드는 붙여넣기와 자동완성을 허용한다

## 14. 개발용 컴포넌트 라이브러리 보드 (신설, 2026-09-14, §13-110)

`.pen`에 화면 시안과 별도로 **"1b. 컴포넌트 라이브러리 (개발용)"** 보드(x-2800, y0)를 신설했다. 화면 인라인에 흩어져 있던 컴포넌트를 한 곳에 모아 구현 참고용으로 카탈로그화한 것이지, 이 문서(§8)의 컴포넌트 정의를 대체하지 않는다 — **정식 스펙은 계속 §8이고, 이 보드는 웹 UI 패턴을 모바일에 맞게 정리한 실측 카탈로그다.**

### 14.1 구성

섹션 17~63, 총 47개 컴포넌트 카테고리: Typography 13종 · Separator · AspectRatio · Badge·Tag · CountBadge · Avatar · IconButton · Spinner · Label · Input(Field, 구 TextInput) · Textarea · Select · SearchField · Checkbox · RadioGroup · Switch(Off 신설) · Toggle · RangeSlider · Input OTP · Questionnaire · Toast · Alert·Notice · Empty · Skeleton · Marker(진행 단계) · Tooltip·Popover · AlertSheet·ActionSheet·MenuItem·Scrim · AppBar 5종 · BottomNav · SectionHeader · Item·Settings · Tabs · Card · Carousel · Attachment 3종 · HeartBalance 3종 · ChatListRow·AcceptanceRow · ChatInputBar · Bubble·Message · SystemMessage·DateDivider · TrustRevealBubble · DailyCardSummary·Locked · HeartTaskRow · ContactRow·BlockedUserRow · HeartBundleCard·HeartPurchaseBar.

### 14.2 웹 → 모바일 매핑 (사용자 결정)

| 웹 컴포넌트 | 모바일 대응 |
| --- | --- |
| Dialog | Sheet |
| Alert Dialog | AlertSheet |
| Dropdown · Context Menu | ⋯에서 여는 ActionSheet |
| Tooltip · Popover | 말풍선 1회성 안내 |
| Select | 탭하면 시트가 열리는 필드 |
| Attachment | 업로드 존 (채팅은 텍스트만 유지, §2.5 원칙 불변) |
| Marker | 진행 단계 표시 (06-2b 체크리스트와 동일 패턴) |

**"Item"** = RecyclerView / `ListView.builder` 한 칸 — 카드 등 반복 셀 전체를 가리키는 이름이다. 59번 섹션에 리스트 아이템 색인을 둔다.

### 14.3 이 라운드에 새로 정리된 패턴 (기존 문서에 없던 것)

- `SystemMessage` — 채팅 스트림에 끼는 시스템 안내 알약 (`trust-reveal-bubble`과는 별개의 더 가벼운 변형)
- `DateDivider` — 채팅 날짜 구분선
- `Tooltip · Popover` — 1회성 안내 말풍선
- `ActionSheet` — 신고·차단 등 메뉴형 시트
- `Radio` 동그라미 — 긴 목록에서 단일 선택할 때 쓰는 원형 라디오

### 14.4 라이브러리 마스터 아이콘 변경 (화면 반영 완료, 2026-09-14, §13-116)

업로드 존 아이콘 `#929292`→`#C4224B`, 서류 업로드 아이콘 `badge-check`→`image-plus`(`#C4224B`). 라이브러리 마스터에서 먼저 바꿨고, 같은 날 전 화면 인스턴스 교체(§13-116)로 화면에도 반영됐다.

### 14.5 발견된 문서·실측 드리프트

라이브러리를 만들며 발견한 문서·실측 드리프트 6건은 §13-109(사용자 결정 대기)에 있다. `mbti-toggle`(§8.5)의 "체크 아이콘" 서술은 오기재라 바로 정정했다(§13-110).

### 14.6 화면 인라인 → 1b 인스턴스 교체 완료 (2026-09-14, §13-116)

**원칙**: 화면의 공통 요소는 1b 보드 마스터의 인스턴스로 구성한다(Flutter 위젯과 1:1 대응) — 새 화면을 만들 때도 1b 마스터를 먼저 찾아 쓴다. 2026-09-14 교체(약 480건)는 구조만 바꿨고 보이는 모습은 그대로다.

**인라인으로 남긴 예외** (2026-09-19 갱신, §13-118 해결 — 옛 "오늘 활성 내비게이션"과 Bottom Bar CTA 는 마스터 인스턴스 교체가 끝나 아래 목록에서 제외했다):
- Keynu(11 카드 대기) 화면의 `DailyCardLocked`(`kMqr5`)와 배지(`QYm41`) — Pencil Replace가 항상 실패해 인라인 유지
- Typography 텍스트 — 정책상 교체 안 함(2026-09-19 사용자 결정으로 인라인 유지 확정, §13-118③ — 새로 만드는 화면부터는 마스터를 쓴다)
- AspectRatio·Separator — 대상에서 제외

**id**: 화면 프레임 id 는 그대로이고 교체된 요소 id 는 바뀌었다. 이 문서의 "현재 상태" 서술(§8.1 daily-card-locked, §9 화면7c·14c·15·15d)은 새 id 로 갱신했다. 그 밖에 적힌 요소 id 는 화면 id 기준으로 읽는다.
