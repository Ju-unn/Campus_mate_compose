# CampusMate — DESIGN.md

CampusMate 의 디자인 시스템 단일 원본(Source of Truth). 화면을 만들거나 고칠 때 **이 문서의 토큰만 참조**한다.

- 대상: Flutter (Android + iOS), 모바일 전용
- 설계 문서: `docs/superpowers/specs/2026-09-05-campusmate-foundation-design.md`
- 토큰 구현 위치: `lib/core/theme/`
- 최초 작성: 2026-09-05

---

## 0. 이 문서의 근거

두 개의 레퍼런스 추출본(Apple, Airbnb)을 분석해 CampusMate 에 맞는 것만 상속했다. 원본 파일은 삭제했고, 상속 내역만 여기 남긴다.

**Apple 에서 가져온 것**

- 제품이 주인공, UI 는 뒤로 물러난다 → CampusMate 의 "제품"은 **하루 한 장의 카드**다
- 브랜드 색은 단 하나. 두 번째 브랜드 색을 만들지 않는다
- 그림자는 사실상 쓰지 않는다. 깊이는 **표면 색 변화**로 만든다
- 디스플레이 크기에 음수 자간을 준다
- 여백이 곧 받침대다

**Airbnb 에서 가져온 것**

- 사진이 먼저인 카드, 부드러운 라운드
- 그림자는 **딱 한 단계**만 정의한다
- 디스플레이 굵기를 과하게 올리지 않는다 (사진이 무게를 담당)
- 4px 기반 간격 체계
- 시스템 전체에서 **타이포가 크게 소리치는 순간은 한 곳뿐**

**버린 것**

- Apple 의 라이트/다크 타일 교차 — 마케팅 페이지 문법이라 앱에 맞지 않는다
- Airbnb 의 서브 브랜드 색(Luxe/Plus) — 색을 늘릴 이유가 없다
- 양쪽의 데스크톱 그리드·푸터·호버 규칙 — 모바일 전용이라 해당 없음
- Apple 의 17px 본문 — 한글 본문은 16px 이 기준이다

## 1. 디자인 원칙

CampusMate 는 **스와이프 앱이 아니다.** 아침 7시에 한 장이 도착하고, 수락하거나 거절하면 그날은 끝난다. 화면은 그 리듬을 따라야 한다. 무한 스크롤의 자극이 아니라 **하루에 한 번 열어보는 편지**의 감각을 목표로 한다.

바탕은 **순백**, 잉크는 `#222222`, 그리고 **Rausch(`{colors.primary}` — #FF385C) 단 하나**가 모든 상호작용을 담당한다. Airbnb 의 색 체계를 그대로 따랐다. Rausch 는 한 화면에 한두 곳에만 나타난다. 카드의 사진과 사람의 문장이 무게를 담당하고, UI 는 그것을 받쳐주는 자리에 머무른다.

대학생 개인정보(사진·연락처)를 다루는 서비스이므로 **신뢰감이 심미성보다 우선**한다. 학생 인증 뱃지, 신고·차단 진입점은 어떤 화면에서도 숨기거나 흐리지 않는다. (2026-09-08 수정: 등록비 폐지로 "결제 금액 표기" 관련 서술은 삭제 — 이제 하트 구매 금액에만 해당)

**핵심 특징**

- 단일 강조색. Rausch 는 수락 버튼 · 활성 탭 · 내 채팅 말풍선 · 뱃지 카운트에만 쓴다
- 그림자는 **오늘의 카드 한 곳**에만. 나머지 표면은 전부 평면이며 깊이는 표면 색으로 구분한다
- 하루 한 장이라는 제약이 화면의 중심. 카드 스택 미리보기, 남은 장 수 표시, 좌우 스와이프 제스처를 만들지 않는다
- 사진 비율은 전부 4:5 세로. 사람의 상반신이 안정적으로 담기는 비율이다
- 한글 조판 우선. Pretendard, 본문 행간 1.6, 디스플레이 자간 −0.03em
- 궁합 점수 같은 **숫자는 사용자에게 노출하지 않는다** (§13 미결 1)
- **모든 화면에서 닉네임으로 표시한다.** 실명은 앱 어디에도 노출하지 않는다(2026-09-10 개정, §8.7)
- 카드는 **뒤집힌다.** 앞면은 결정에 필요한 최소한, 뒷면은 나머지 전부 (§8.1)

## 2. 색상

### 2.1 브랜드

Airbnb 의 색 체계를 그대로 가져왔다. 캔버스는 **순백**, 잉크는 **#222222**, 그리고 **Rausch(#FF385C) 단 하나**가 모든 상호작용을 담당한다.

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{colors.primary}` | `#FF385C` | Rausch. 모든 CTA 채움, 하트, 활성 탭, 카운트 뱃지, 워드마크 |
| `{colors.primary-pressed}` | `#E00B41` | 눌림 상태 (Airbnb 의 Rausch Active) |
| `{colors.primary-text}` | `#C4224B` | **흰 배경 위 핑크 텍스트·링크 전용.** 채움에는 쓰지 않는다 |
| `{colors.primary-wash}` | `#FFF0F2` | 아주 옅은 핑크 표면. 수락 대기 행, 선택된 칩 |
| `{colors.on-primary}` | `#FFFFFF` | Rausch 채움 위의 텍스트·아이콘 |

**Rausch 를 텍스트에 그대로 쓰지 않는 이유.** `#FF385C` 는 흰 배경 대비 **3.52:1** 로 본문 기준(4.5:1)에 미달한다. 그래서 텍스트·링크는 `{colors.primary-text}`(`#C4224B`, 5.71:1)를 쓰고, `#FF385C` 는 **채움 전용**으로 둔다. 색은 거의 같아 보이지만 읽히는 정도가 다르다.

**버튼 라벨은 18/700 이다.** 흰 글씨가 Rausch 위에서 3.52:1 이므로, WCAG 의 큰 글씨 예외(18.66px 이상 굵은 글씨 → 3:1)에 기대야 한다. 18px 은 그 기준에 0.66px 모자라는 **의도적 허용 편차**다. Airbnb 자신도 이 지점을 통과하지 못한다(그들은 16/500). 브랜드 색을 우선한 결정이며, 여기서 더 밝게 가면 안 된다.

| 남아 있는 편차 | 값 | 대응 |
| --- | --- | --- |
| Rausch 위 흰 버튼 라벨 18/700 | 3.52:1 | 큰 글씨 예외 경계선. 허용 |
| Rausch 뱃지 위 흰 숫자 11px | 3.52:1 | 허용. **단, 뱃지 숫자가 유일한 정보 전달 수단이 되면 안 된다** |

### 2.2 표면

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{colors.canvas}` | `#FFFFFF` | 모든 화면의 바닥. **순백이다** |
| `{colors.surface-soft}` | `#F7F7F7` | 입력 필드 채움, 상대 말풍선, 태그 칩 |
| `{colors.surface-strong}` | `#F2F2F2` | 원형 아이콘 버튼 바탕, 살짝 더 무거운 채움 |
| `{colors.surface-ink}` | `#222222` | 잉크 표면. 학생 인증 뱃지, 사진 위 오버레이 칩 |
| `{colors.scrim}` | `#000000` @ 50% | 모달 뒤 딤, 모자이크 배너 위 덮개 |

캔버스가 순백이므로 카드(흰색)와 바닥이 같은 색이다. **분리는 1px 헤어라인과 라운드가 만든다.** 그림자에 기대지 않는다.

### 2.3 텍스트

| 토큰 | 값 | 흰 배경 대비 | 용도 |
| --- | --- | --- | --- |
| `{colors.ink}` | `#222222` | 15.9:1 | 제목, 이름, 강조 본문. 순검정을 쓰지 않는다 |
| `{colors.body}` | `#3F3F3F` | 10.5:1 | 긴 본문. 잉크가 무거운 자리 |
| `{colors.muted}` | `#6A6A6A` | 5.4:1 | 보조 설명, 메타 정보, 시각, 캡션 |
| `{colors.disabled}` | `#929292` | 3.1:1 | 비활성 텍스트 전용 (대비 요건 면제 대상) |
| `{colors.on-ink}` | `#FFFFFF` | 15.9:1 | 잉크 표면 위 텍스트 |

### 2.4 경계선

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{colors.hairline}` | `#DDDDDD` | 기본 1px 구분선. 리스트·섹션·카드 테두리 |
| `{colors.hairline-soft}` | `#EBEBEB` | 더 옅은 구분선. 긴 스크롤 본문 |
| `{colors.outline}` | `#767676` | **컨트롤 경계선.** 입력 필드, 아웃라인 버튼. 흰 배경 4.54:1 |

**Airbnb 의 `border-strong`(#C1C1C1)을 쓰지 않았다.** 흰 배경 대비 1.80:1 로 비텍스트 대비 3:1 에 미달한다. 입력 필드 테두리는 그 컨트롤이 어디까지인지 알려주는 유일한 단서이므로 여기만 `#767676` 로 올렸다. 장식용 구분선은 Airbnb 그대로 `#DDDDDD` 를 쓴다.

### 2.5 의미색

| 토큰 | 값 | 흰 배경 대비 | 용도 |
| --- | --- | --- | --- |
| `{colors.error}` | `#C13515` | 5.5:1 | 인증 실패, 입력 오류, 신고 확인 |
| `{colors.success}` | `#25795A` | 5.1:1 | 매칭 성사, 학생 인증 완료 |

`{colors.error}` 와 Rausch 는 색상환에서 가깝다. **에러는 항상 아이콘 + 문구를 동반**하고, Rausch 표면 위에는 올리지 않는다.

### 2.6 대비 검증표

실제 계산값이다. 팔레트를 바꾸면 다시 계산해서 갱신한다.

| 조합 | 비율 | 기준 | 판정 |
| --- | --- | --- | --- |
| `ink` / `canvas` | 15.91:1 | 4.5 | 통과 |
| `body` / `canvas` | 10.53:1 | 4.5 | 통과 |
| `muted` / `canvas` | 5.41:1 | 4.5 | 통과 |
| `primary-text` / `canvas` | 5.71:1 | 4.5 | 통과 |
| `on-primary` / `primary-pressed` | 4.89:1 | 4.5 | 통과 |
| `on-ink` / `surface-ink` | 15.91:1 | 4.5 | 통과 |
| `error` / `canvas` | 5.54:1 | 4.5 | 통과 |
| `success` / `canvas` | 5.13:1 | 4.5 | 통과 |
| `outline` / `canvas` (컨트롤 경계) | 4.54:1 | 3.0 | 통과 |
| 사진 스크림 45% 위 흰 이름 20/600 | 3.30:1 | 3.0 | 통과 |
| 사진 스크림 57% 위 흰 메타 14 | 4.71:1 | 4.5 | 통과 |
| `on-primary` / `primary` (버튼 라벨 18/700) | 3.52:1 | 3.0 | **큰 글씨 예외로 허용 — §2.1** |
| ~~`primary` / `canvas` (텍스트)~~ | 3.52:1 | 4.5 | **미달 — 텍스트에는 `primary-text` 를 쓴다** |
| ~~Airbnb `border-strong` #C1C1C1~~ | 1.80:1 | 3.0 | **미달 — `outline` 으로 대체** |

### 2.7 다크 모드

**MVP 범위에서 제외한다.** 1인 개발 · 2개월 일정에서 두 벌의 팔레트를 검증할 여력이 없고, 검증하지 않은 다크 모드는 없느니만 못하다.

대신 나중에 넣을 수 있게 만든다. `AppColors` 는 의미 기반 토큰만 노출하고, 위젯은 `Theme.of(context).colorScheme` 을 통해서만 색을 읽는다. 다크 팔레트는 **토큰 값 한 벌을 추가**하는 것으로 끝나야 한다. `MaterialApp` 에는 `themeMode: ThemeMode.light` 를 명시해 시스템 다크에 끌려가지 않게 고정한다.

## 3. 타이포그래피

### 3.1 폰트

**Pretendard** 하나로 전부 처리한다. 별도 디스플레이 서체를 두지 않는다.

```
fontFamily: 'Pretendard'
fontFamilyFallback: ['Apple SD Gothic Neo', 'Noto Sans KR', 'sans-serif']
```

- 라이선스: SIL Open Font License 1.1 — 앱 번들 포함 가능
- 번들 방식: `assets/fonts/PretendardVariable.ttf` 를 `pubspec.yaml` 에 등록한다. 웹폰트 CDN 을 쓰지 않는다 (오프라인 동작, 첫 프레임 깜빡임 방지)
- 사용 굵기: **400 / 500 / 600 / 700** 네 단계. 그 외는 쓰지 않는다
- 숫자에는 `FontFeature.tabularFigures()` 를 적용한다. 카운트다운·나이·키·요금이 자릿수 때문에 흔들리면 안 된다

### 3.2 위계

| 토큰 | 크기 | 굵기 | 행간 | 자간 | 용도 |
| --- | --- | --- | --- | --- | --- |
| `{type.countdown}` | 48 | 700 | 1.10 | −0.03em | **시스템에서 가장 큰 한 곳.** 다음 카드까지 남은 시간 |
| `{type.display}` | 32 | 700 | 1.30 | −0.03em | 온보딩 단계 헤드라인, 매칭 성사 화면 |
| `{type.headline}` | 24 | 700 | 1.35 | −0.02em | 화면 제목 |
| `{type.title}` | 20 | 600 | 1.40 | −0.02em | 카드의 이름·나이, 섹션 헤드, 채팅 상대 이름 |
| `{type.subtitle}` | 17 | 600 | 1.45 | −0.01em | 리스트 행 제목, 설문 문항 |
| `{type.body}` | 16 | 400 | 1.60 | −0.01em | 자기소개 본문, 채팅 메시지, 설명 문단 |
| `{type.body-strong}` | 16 | 600 | 1.60 | −0.01em | 본문 내 강조 |
| `{type.body-small}` | 14 | 400 | 1.55 | 0 | 메타 정보(학과·키·MBTI), 채팅 미리보기 |
| `{type.label}` | 18 | 700 | 1.20 | −0.01em | 전체 폭 버튼 라벨. Rausch 위 대비 확보를 위해 굵고 크게 (§2.1) |
| `{type.label-small}` | 14 | 600 | 1.20 | 0 | 리스트 안의 작은 버튼, 칩 버튼 |
| `{type.caption}` | 12 | 400 | 1.40 | 0 | 보조 설명, 타임스탬프, 약관 |
| `{type.badge}` | 11 | 600 | 1.30 | 0.02em | 인증 뱃지, 카운트 뱃지 |

### 3.3 원칙

- **본문은 16px.** 12px 미만 텍스트를 만들지 않는다. `{type.badge}` 11px 이 하한이고, 뱃지는 항상 옆의 텍스트가 의미를 보완한다
- **한글 본문 행간은 1.6.** 한글은 디센더 리듬이 없어 라틴 기준(1.4~1.5)으로는 답답하다
- **자간은 크기가 클수록 좁힌다.** 20px 이상에만 음수 자간을 주고, 14px 이하에는 주지 않는다. 작은 한글에 음수 자간을 주면 가독성이 무너진다
- **굵기 500 은 채팅 말풍선 전용.** 나머지는 400 / 600 / 700 사다리를 쓴다
- **크게 소리치는 곳은 카운트다운 하나뿐.** 48px 은 "다음 카드까지 06:12:40" 한 군데에만 쓴다. 이 앱에서 가장 중요한 정보는 기다림이다
- **한글 줄바꿈을 통제한다.** 이름·대학명처럼 끊기면 안 되는 문자열에는 `softWrap: false` + `TextOverflow.ellipsis` 를 준다

## 4. 레이아웃

### 4.1 간격

기본 단위 **4px**.

| 토큰 | 값 | 용도 |
| --- | --- | --- |
| `{space.xxs}` | 4 | 아이콘과 라벨 사이, 칩 내부 세로 |
| `{space.xs}` | 8 | 인접 요소 최소 간격, 터치 타깃 사이 |
| `{space.sm}` | 12 | 리스트 행 내부 세로 패딩 |
| `{space.md}` | 16 | **화면 좌우 기본 여백**, 카드 내부 패딩 |
| `{space.lg}` | 24 | 블록 사이, 큰 카드 내부 패딩 |
| `{space.xl}` | 32 | 섹션 사이 |
| `{space.xxl}` | 48 | 화면 상단 여백, 빈 상태 위아래 |

- 화면 좌우 여백은 전 화면 `{space.md}`(16) 로 고정한다. 화면마다 다르게 두지 않는다
- 인접한 터치 타깃 사이는 최소 `{space.xs}`(8)

### 4.2 세이프 에어리어

- 하단 고정 바(수락/거절 액션 바, 채팅 입력창, 바텀 내비)는 **세이프 에어리어 아래 패딩을 더한다**. `SafeArea(top: false)` 로 감싸고 제스처 인디케이터를 침범하지 않는다
- 스크롤 콘텐츠에는 고정 바 높이만큼 `bottom` 인셋을 준다. 리스트 마지막 항목이 바 뒤로 숨으면 안 된다
- 앱바는 상태바 아래에서 시작한다. 사진 위에 앱바를 띄우는 경우 위쪽에 스크림 그라데이션을 깔아 텍스트 대비를 확보한다

### 4.3 여백 철학

오늘의 카드 화면은 의도적으로 비어 있다. 카드 하나와 버튼 두 개 외에 아무것도 두지 않는다. 배너·프로모션·추천 목록을 이 화면에 추가하지 않는다.

반대로 채팅 목록과 설정 화면은 밀도를 높인다. 정보를 찾으러 온 화면이므로 스크롤을 줄이는 쪽이 낫다.

### 5.2 사진

**두 종류를 구분한다 — 표시용(만화 아바타)과 실사진.** (경쟁사 조사 반영, 설계 문서 §2.5·§6.1과 연동)

- **사진은 정확히 2장을 받는다(2026-09-08 확정, 설계 문서 §13 미결4).** ① **아바타용 사진** — 서버가 AI로 **만화 캐릭터 스타일 표시용 사진**을 생성하는 원본. 원본 자체는 어디에도 노출되지 않는다. ② **공개용 실사진** — 쌍방 수락 시에만 상대에게 공개된다. 두 장을 서로 다른 사진으로 고를 수 있다(아바타는 잘 나온 사진, 공개용은 다른 사진을 쓰고 싶을 수 있으므로)
- 평소 카드·프로필·채팅 헤더에는 **만화 아바타만** 노출된다
- **교체 정책이 비대칭이다.** 공개용 실사진은 **언제든 무료로 교체**할 수 있다. 아바타 교체(= 아바타용 사진 변경)는 **최초 1회 무료, 이후 10하트**다 — OpenAI 이미지 생성 비용이 실제로 발생하는 유일한 지점이기 때문이다(§8.10)
- **실사진은 원칙적으로 비공개다.** 매칭 후 신뢰 확인 게이트(설계 문서 §2.5)에서 양쪽이 모두 수락해야만, 그 상대에게 한해 실사진이 공개된다. 그 전까지는 어떤 화면·API 응답에도 실사진이 담기지 않는다
- 표시용 사진 위에는 `ai-avatar-badge`를 작게 얹는다 — "AI가 그려준 얼굴이에요" 톤. 나중에 실사진을 보고 느낄 괴리를 온보딩 시점부터 낮춰둔다
- **내 프로필(§9 화면15)에는 예외적으로 실사진도 함께 보여준다.** "상대에게는 이렇게 보여요"(표시용) + "나만 보는 실제 사진" 두 섹션으로 나눈다 — 얼굴 판별·변환이 잘 됐는지 본인이 확인할 수 있어야 한다
- **모든 인물 사진(표시용 기준)은 4:5 세로.** 카드, 프로필, 채팅방 헤더 전부 동일하다
- 아바타는 원형. 리스트 40dp, 채팅 헤더 32dp, 프로필 96dp
- 카드 사진은 `{radius.lg}` 로 클리핑하고, 하단에 이름을 얹을 경우 아래쪽 40% 에 잉크 스크림 그라데이션을 깐다
- **모자이크 레일·배너는 서버 픽셀레이션이 필요 없다.** 표시용 사진이 애초에 만화 아바타라 비식별이므로, 동의 여부와 무관하게 그대로 노출한다(8.9절 갱신 — 이전의 동의 기반 서버 픽셀레이션 규칙은 폐기)
- 사진이 없는 프로필은 `{colors.primary-wash}` 바탕 + 이니셜 잉크 텍스트로 대체한다. 회색 사람 아이콘은 쓰지 않는다

### 5.4 마스코트와 일러스트

하트 귀를 가진 흰 토끼. 원본은 `design/designMaterials/` 에 있다. **남자 캐릭터는 파란 목도리·파란 하트 속귀(`mascot-male.png`), 여자 캐릭터는 핑크 목도리·핑크 하트 속귀(`mascot-female.png`)**로 구분한다. 색만으로 구분하지 않고 목도리 형태를 함께 쓰며, 두 캐릭터의 얼굴 비율·외곽선·몸 형태는 같은 가족으로 유지한다.

마스코트의 역할은 하나다 — **화면에 보여줄 사람이 아직 없을 때 그 자리를 지키는 것.** 서비스가 작을 때 빈 화면은 "망한 앱"으로 읽히지만, 빈 화면에 캐릭터가 있으면 "아직 이른 앱"으로 읽힌다.

- 기본 그림체는 깨끗한 2D 외곽선 위에 **부드러운 2.5D 볼륨 음영과 작은 하이라이트**만 더한다. 실사 털·플라스틱 장난감 질감·과한 광택은 쓰지 않는다
- 파란색은 남자 마스코트와 브랜드 일러스트의 작은 보조 포인트에만 쓴다. **CTA·링크·선택 상태는 계속 `{colors.primary}` / `{colors.primary-text}`만 사용**한다 — 파란색을 두 번째 상호작용 색으로 확장하지 않는다
- `Campus Heart Orbit · SVG`는 캠퍼스 아치·학사모·하트 궤도를 한 덩어리로 묶은 보조 일러스트다. 로그인처럼 첫 인상을 만드는 화면에만 쓰며, Lucide 조작 아이콘을 대신하지 않는다

**쓰지 않는 곳** — 오늘의 카드 안, 프로필, 채팅방, 결제 시트, 신고·차단 흐름. 사람의 얼굴과 돈과 안전이 걸린 화면에 캐릭터를 넣지 않는다. 결제 화면의 캐릭터는 판단을 흐리는 장치로 읽힌다.

- **한 화면에 한 마리.** 두 마리가 동시에 보이면 소개팅 앱이 아니라 캐릭터 앱이 된다
- 마스코트는 **장식이지 정보가 아니다.** 마스코트만으로 상태를 알리지 않는다. 항상 문구가 함께 간다
- 마스코트 외곽선이 흰색이므로 `{colors.canvas}` 또는 `{colors.primary-wash}` 위에만 놓는다. 사진 위에 얹지 않는다
- 실사 일러스트(커플 그림 등)는 **온보딩과 마케팅에만** 쓴다. 앱 안의 반복 화면에 넣으면 금방 질린다

## 6. 깊이

그림자는 **한 단계만** 존재한다.

| 단계 | 처리 | 적용 대상 |
| --- | --- | --- |
| 평면 | 그림자 없음 | 화면의 95%. 앱바, 리스트, 입력, 버튼, 바텀 내비 |
| 카드 | `0 2px 8px rgba(26,22,25,0.06)` + `0 8px 24px rgba(26,22,25,0.08)` | **오늘의 카드**, 바텀시트 |
| 스크림 | `{colors.scrim}` 55% | 모달 뒤, 모자이크 배너 위 |

버튼·칩·앱바·리스트에 그림자를 넣지 않는다. Flutter 기본 `Card` 의 `elevation` 을 그대로 쓰면 이 규칙이 깨지므로, `AppElevation.card` 상수를 통해 `BoxShadow` 를 직접 지정한다.

깊이는 그림자가 아니라 **표면 색 차이**로 만든다. `canvas` → `surface` → `surface-ink` 순서가 곧 층위다.

## 7. 모션

| 토큰 | 시간 | 커브 | 용도 |
| --- | --- | --- | --- |
| `{motion.press}` | 120ms | `Curves.easeOut` | 눌림 피드백 (투명도·색) |
| `{motion.standard}` | 220ms | `Curves.easeOutCubic` | 화면 전환, 시트 열림, 상태 변화 |
| `{motion.emphasis}` | 420ms | `Curves.easeOutBack` | 매칭 성사 · 카드 등장 |
| `{motion.flip}` | 460ms | `Curves.easeInOutCubic` | 카드 앞↔뒤 뒤집기 |

- **누름 반응은 150ms 안에 보인다.** 반응 없는 탭은 고장으로 읽힌다
- **레이아웃을 흔드는 눌림 효과를 쓰지 않는다.** 색·투명도만 바꾸고 크기·위치는 고정한다
- `{motion.emphasis}` 는 하루에 최대 두 번(카드 등장, 매칭 성사)만 등장한다
- `{motion.flip}` 은 Y축 180° 회전이다. `easeOutBack` 을 쓰지 않는다 — 되튐이 들어가면 카드가 흔들리는 것처럼 보인다
- **`MediaQuery.disableAnimations` 를 존중한다.** 켜져 있으면 모든 시간을 0 으로 만들고 최종 상태를 즉시 그린다
- 로딩은 스피너 대신 **스켈레톤**을 쓴다. 카드·리스트 모두 최종 레이아웃과 같은 크기의 블록으로 자리를 잡아 레이아웃 이동을 없앤다

## 8. 컴포넌트

### 8.1 오늘의 카드 `daily-card`

이 앱의 주인공. `{colors.surface}` 바탕, `{radius.lg}` 라운드, 카드 그림자 1단계.

**신원은 사진 위에, 목소리는 사진 아래에.** 4:5 사진과 이름·학교·자기소개를 세로로 쌓으면 360×780 화면에 들어가지 않는다(계산상 537dp 필요, 가용 506dp). 그래서 신원 정보는 사진 위 스크림에 얹고, 흰 영역에는 본인이 쓴 문장만 남긴다.

**사진 영역 (카드 폭 × 4:5, 상단만 `{radius.lg}` 클리핑, 표시용 만화 아바타 사진을 쓴다)**

1. 우상단 `{space.md}` 위치에 `verified-chip`("학교 인증")만 얹는다
2. 하단 60%에 잉크 스크림 그라데이션 (투명 → 72%)
3. 스크림 위에 아래에서부터 — 대학·학과 한 줄(`{type.body-small}`, `#EDE7E9`) / 이름·나이(`{type.title}`, `{colors.on-primary}`)

**흰 영역 (`{space.md}` 패딩, 2026-09-12 개정 — 사진은 깨끗하게 비우고 정보를 흰 영역으로 내림)**

1. `tag-chip` 최대 3개(관심사 — 기존 `tag-chip-overlay` 방식 폐기, 사진 위가 아니라 흰 배경 기본 칩 스타일로)
2. 자기소개(`{type.body}`, 최대 2줄 + "더보기")
3. "탭해서 자세히 보기" 뒤집기 어포던스(`refresh-cw` 아이콘 + `{colors.primary-text}` 텍스트)

- **카드는 화면에 하나만 존재한다.** 뒤에 다음 카드가 쌓인 듯한 시각 효과를 넣지 않는다
- 사진 위에는 이름·학교와 인증 배지만 남고, 나머지(태그·소개)는 전부 흰 영역 — 사진이 텍스트에 가려지지 않는다

**뒷면 — `daily-card-back`**

카드를 탭하면 Y축으로 뒤집혀 뒷면이 나온다(`{motion.flip}`). 앞면은 결정에 필요한 최소한만 담고, **나머지 전부는 뒷면에** 둔다. 화면을 옮기지 않으므로 오늘 탭의 여백 철학이 유지되고, 4:5 사진과 전체 정보가 한 화면에 들어가지 않는 문제(앞면 설계 참고)도 함께 풀린다.

- 바탕 `{colors.surface}`, 앞면과 **같은 크기·같은 `{radius.lg}`**. 크기가 변하면 뒤집기가 아니라 화면 전환으로 읽힌다. **크기는 2026-09-12부로 328×580**(구 508 — 아래 항목이 늘면서 커짐)
- 담는 것 (위에서부터): 이름·나이 → 학과·키·MBTI·학번(4칸 통계 줄) → 성향 슬라이더 3축(활동성·낯가림·계획성, `trait-slider` 축약 미리보기 — §8.5 10축 중 대표 3개) → **외모 타입**(동물상 이미지 48dp + 동물상·인상 텍스트, 2026-09-12 신규) → 관심 태그 전체 → 자기소개 전문 · **신고/차단 진입점**
- 상단에 이름(`{type.title}`)을 다시 적는다. 사진이 없으므로 누구인지 잃지 않게 한다
- **앞뒤 모두에 뒤집기 어포던스를 둔다.** 앞면 하단에 "자세히 보기", 뒷면 상단에 "사진 보기" (`button-text`)
- 액션 바(거절/수락)는 **뒤집어도 그대로 남는다.** 뒷면에서도 바로 결정할 수 있어야 한다
- 접근성: 뒤집기는 탭이며 제스처 전용이 아니다. 스크린 리더에는 `Semantics(button: true, label: "자세히 보기")` 로 노출하고, 뒤집힌 뒤 뒷면으로 포커스를 옮긴다. 뒷면이 보일 때 앞면은 `ExcludeSemantics` 로 감춘다
- **축소 모션에서는 회전 대신 교차 페이드**(160ms)로 대체한다
- Flutter 구현: `AnimationController` + `Transform(Matrix4.rotationY)`. 진행도 0.5 를 넘는 순간 앞/뒷면 위젯을 교체하고, 뒷면에 `Matrix4.rotationY(pi)` 를 한 번 더 적용해 거울상을 되돌린다

### 8.2 카드 액션 바 `card-action-bar`

화면 하단 고정. 세이프 에어리어 위. 배경 `{colors.canvas}`, 상단에 `{colors.hairline}` 1px.

- **거절** — 좌측, `{colors.surface-strong}` 채움, 테두리 없음, `{colors.ink}` 라벨, 폭 40%
- **수락** — 우측, `{colors.primary}` 채움, `{colors.on-primary}` 라벨, 폭 60%
- 두 버튼 높이 **56dp**, 간격 `{space.sm}`

수락이 시각적으로 더 크다. 거절을 어렵게 만들지는 않되, 기본 행동이 무엇인지는 분명히 한다.

### 8.3 버튼

| 이름 | 채움 | 텍스트 | 테두리 | 높이 | 라운드 |
| --- | --- | --- | --- | --- | --- |
| `button-primary` | `{colors.primary}` | `{colors.on-primary}` | 없음 | 56 | 16 |
| `button-secondary` | `#E5E5E5` | `{colors.ink}` | 없음 | 56 | 16 |
| `button-text` | 없음 | `{colors.primary}` | 없음 | 48 | — |
| `button-danger` | `#E5E5E5` | `{colors.error}` | 없음 | 56 | 16 |
| `button-disabled` | `#E5E5E5` | `{colors.disabled}` | 없음 | 56 | 16 |

- **버튼 라운드를 토스(TDS Mobile) 비례로 교체(2026-09-12, 사용자 — "버튼은 토스처럼 가자, 색상은 우리껄로").** 기존엔 버튼 높이와 무관하게 전부 `{radius.sm}`(8px, Airbnb 기준)를 썼다. 토스 TDS 버튼 스케일(32px→8 / 38px→10 / 48px→14 / 56px→16, 높이에 비례해 라운드가 커짐)을 그대로 가져오되 **색상·토큰 체계는 우리 걸 유지** — 56dp 버튼(primary·secondary·disabled) = 16px. **`button-danger`도 48→56dp로 통일(2026-09-12, 사용자 — "탈퇴는 왜 높이 동일하게 안 해?")** — secondary와 똑같이 채움이 있는 필(fill) 버튼인데 danger만 48이어야 할 근거가 없었다. 배경 없는 `button-text`만 48dp·14px로 남긴다(시각적 무게가 원래 다르므로). `{radius.sm}`(8px) 전역 토큰 자체는 안 건드리고(칩·입력 필드 등 다른 컴포넌트는 그대로) 버튼 컴포넌트에만 리터럴로 적용 — 이제 `{radius.sm}` 표기가 아니므로 위 표는 실제 픽셀값으로 적음. 참여 배지류(28dp 필 버튼)는 이미 `{radius.pill}`(9999)라 영향 없음
- **버튼 3종(secondary·danger·disabled) 채움을 `#E5E5E5`로 한 단계 진하게 조정(2026-09-12, 사용자 — "거절 버튼이 잘 안 보여").** 기존 `{colors.surface-strong}`(`#F2F2F2`)는 흰 배경 위에서 버튼처럼 안 읽혔다. `{colors.surface-strong}` 토큰 자체는 그대로 두고(원형 아이콘 버튼 바탕·상태 배지 등 다른 용도에 계속 쓰임) 버튼 3종의 채움만 리터럴로 살짝 더 진하게 뗐다 — 전용 토큰을 새로 만들 정도의 변화는 아니라고 판단
- **아웃라인 버튼을 쓰지 않는다(2026-09-09 변경).** `button-secondary`·`button-danger`·카드 액션 바 거절 모두 테두리 없이 채움(`#E5E5E5`, 2026-09-12부터 — 위 갱신 참조)으로 통일한다. 위험 신호는 `button-danger` 의 `{colors.error}` 라벨이 담당한다. 사진·서류 업로드 존도 같은 원칙 — 테두리 없이 `{colors.surface-soft}` 채움 + 내부 아이콘·라벨로 탭 영역을 알린다. 입력 필드(`text-field`)만 예외로 `{colors.outline}` 1px 를 유지한다(§2.4, 컨트롤 경계가 유일한 단서)
- 눌림: `button-primary` 는 `{colors.primary-pressed}`, 나머지는 `{colors.surface-soft}` 배경이 깔린다
- 비활성 버튼에 **연한 핑크를 쓰지 않는다.** Airbnb 는 `#FFD1DA` + 흰 글씨를 쓰지만 대비가 1.55:1 이라 읽히지 않는다. `#E5E5E5` 채움 + `{colors.disabled}` 텍스트를 쓴다
- 아이콘 전용 버튼은 시각 크기가 24dp 여도 터치 영역을 **48dp** 로 확장한다

### 8.5 입력

- `text-field` — `{colors.surface-soft}` 채움, `{colors.outline}` 1px, `{radius.sm}`, 높이 56, 패딩 16×14
  - 라벨은 **필드 위에 항상 보이게** 둔다. 플레이스홀더를 라벨 대신 쓰지 않는다
  - 포커스: 테두리 `{colors.ink}` 2px. 글로우·링 없음
  - 에러: 테두리 `{colors.error}` 2px + 필드 **바로 아래** 에러 문구(`{type.caption}`, `{colors.error}`) + 경고 아이콘
- `nickname-field` — 닉네임 입력 전용(2026-09-10 신규). `text-field` 기반 + **인라인 중복확인 상태**를 필드 바로 아래에 둔다
  - 허용: 한글 완성형(가–힣) + 영문, **2~5자**. 숫자·특수문자·공백·한글 자모 단독은 입력 단계에서 막는다
  - 상태 3종(필드 아래, `{type.caption}`): `확인 중…`(`{colors.muted}` + 스피너) / `사용할 수 있어요`(`{colors.success}` + `check`) / `이미 쓰고 있어요`(`{colors.error}` + 경고 아이콘). 색만으로 전달하지 않는다(아이콘 동반)
  - 입력이 멈추고 **500ms** 뒤 서버 중복 검사 1회. 검사 통과 전까지 "다음으로" 비활성
  - 규칙 위반 시 문구: `한글·영문 2~5자로 지어주세요` / `띄어쓰기·기호는 뺄게요`

### 8.6 대화 탭

대화 탭은 **수락 대기**(위) + **대화 중**(아래) 두 섹션으로 구성된다. 채팅 동시 개수 상한은 없앴으므로(설계 문서 §2.5) 대화 중 목록이 5행을 넘을 수 있다 — 그래서 `acceptance-section`은 **상단에 sticky로 고정**해, 목록이 길어져도 수락 대기가 항상 먼저 보이게 한다. 전용 탭을 따로 두지 않는 근거는 "1인당 수락 유입이 하루 평균 0.3~0.5건이라 전용 탭이 대부분 비어 있다"는 이유 하나로 좁아졌다.

- `section-header` — `{type.subtitle}`, `{colors.ink}`, 좌측 정렬. 우측에 건수(`{type.body-small}`, `{colors.muted}`). 위 `{space.lg}` / 아래 `{space.sm}`
- `acceptance-section` — 수락 대기 섹션. **건수가 0이면 섹션 전체를 그리지 않는다** (빈 섹션 금지). 대화 목록이 길어져도 상단에 sticky 로 고정한다
- `acceptance-row` — **정보 위 / 결정 아래 2단 구조.** 배경 `{colors.primary-wash}`, `{radius.md}`, 패딩 `{space.sm}`, 행 사이 `{space.xs}`
  - 윗단: 아바타 44dp 원형 + 이름·나이(`{type.subtitle}`) + 대학·학과(`{type.body-small}`, `{colors.muted}`)
  - 아랫단: **거절**(`button-secondary`, 폭 104) + **수락하고 대화 시작**(`button-primary`, 나머지 폭). 둘 다 높이 **44dp**
  - 버튼을 한 줄에 이름과 나란히 두지 않는다. 학과명이 긴 경우("컴퓨터과학과") 가운데 열이 줄바꿈되며 버튼이 어긋난다 — 시안에서 확인된 실제 문제다
  - 대화 중 행과 **배경색으로 구분**한다. 동작이 다른 리스트(수락/거절 vs 열기)를 같은 표면에 섞지 않는다
  - 윗단을 탭하면 상대 프로필 전체가 열린다. 결정은 프로필을 본 뒤에도 할 수 있어야 한다
- `chat-list-row` — 아바타 40dp 원형, 이름(`{type.subtitle}`), 마지막 메시지(`{type.body-small}`, `{colors.muted}`, 1줄), 우측에 시각(`{type.caption}`)과 `count-badge`. 행 높이 72, 배경 `{colors.canvas}`, 구분선 `{colors.hairline}`
- `bubble-mine` — `{colors.primary}` 채움, `{colors.on-primary}` 텍스트(`{type.body}`, 굵기 500), `{radius.md}` (우하단만 `{radius.sm}`)
- `bubble-theirs` — `{colors.surface-soft}` 채움, `{colors.ink}` 텍스트, `{radius.md}` (좌하단만 `{radius.sm}`)
- 말풍선 최대 폭 화면의 **78%**. 시각은 말풍선 밖 아래에 `{type.caption}` / `{colors.muted}`
- `chat-input-bar` — 하단 고정, `{colors.surface}`, 상단 `{colors.hairline}` 1px, 세이프 에어리어 준수. 전송 버튼은 원형 40dp `{colors.primary}`
- `trust-gate-sheet` — 매칭 24시간 경과 후 미응답 상태로 채팅방에 들어갈 때마다 뜨는 `bottom-sheet`(설계 문서 §2.5). "카카오톡 아이디를 공유할까요?" + 설명 문구(둘 다 동의해야 공개되고, 48시간 안에 응답이 없으면 대화가 종료된다는 안내) + 카톡 아이디 `text-field`(처음 한 번만 받고 이후 재사용) + `button-primary`(수락) / `button-text`(거절) + 48시간 카운트다운
  - 쌍방 수락 시: 채팅방 헤더 사진이 표시용 아바타 → 실사진으로 전환되는 순간 `{motion.emphasis}`를 쓴다(매칭 성사와 같은 급의 순간으로 취급). 대화창에는 "OO님과 카카오톡 아이디를 주고받았어요" 시스템 메시지 + 카톡 아이디를 담은 전용 정보 카드 버블이 붙는다
  - 거절 또는 48시간 무응답 시: 채팅방 상단에 "48시간 뒤 이 대화가 종료돼요" 배너를 띄우고, 시한이 지나면 대화 목록에서 조용히 사라진다. 상대가 거절했는지는 알 수 없다(2.2절 원칙과 동일 톤)

### 8.7 이름 표기 (2026-09-10 전면 개정)

**앱 어디에서도 실명을 보여주지 않는다. 사용자를 가리키는 이름은 항상 닉네임이다.**
예전의 `김○○` 마스킹 방식(매칭 전 마스킹 → 매칭 후 실명 공개)은 폐기했다. 근거는 설계 문서
§13 미결5·37 — 카드가 닉네임을 보여주는 쪽으로 바뀌면서 가릴 실명이 화면에 존재하지 않는다.

| 위치 | 표기 | 예 |
| --- | --- | --- |
| 오늘의 카드 (앞·뒷면) | 닉네임 | `여우비, 23` |
| 수락 대기 행 | 닉네임 | `초코라떼, 25` |
| 대화 중 목록 · 채팅방 | 닉네임 | `여우비` |
| `friend-review-card` 리뷰어 | 닉네임 | `달빛` |
| 내 프로필 (화면 15) | 내 닉네임 | `여우비` |
| 설정 > 계정 정보 (화면 16) | **본인만** 실명 조회 | `실명 (비공개)  홍길동` |

- **매칭 성사 후에도 닉네임을 그대로 쓴다.** 실명 공개 단계가 없다 — 신뢰 확인 게이트(§2.5)에서
  실사진과 카카오톡 아이디가 공개되므로, 앱이 실명까지 노출할 이유가 없고 유출 표면만 넓어진다.
  "이제 서로의 이름을 볼 수 있어요" 문구도 제거
- 실명(`real_name`)은 학생증 인증·운영 조회 전용이라 **서버 응답 어디에도 담기지 않는다**
  (설계 문서 §7 예외 2). 본인 실명은 설정 > 계정 정보에서만, 그 자리에서 왜 받는지 한 줄 안내
- `○`(U+25CB) 마스킹 문자·스크린리더 예외 규칙은 더 이상 쓰지 않는다 — 닉네임은 실명이
  아니므로 가리지 않고 그대로 읽어준다
- 닉네임 제약·중복·변경 정책은 `nickname-field`(§8.5)와 설계 문서 §5.3

- `bottom-sheet` — `{colors.surface}`, 상단만 `{radius.md}`, 카드 그림자, 상단 중앙에 4×36 그랩 핸들(`{colors.hairline}`)
- `empty-state` — 아이콘 48dp(`{colors.muted}`), 제목 `{type.subtitle}`, 설명 `{type.body-small}`, 필요 시 `button-secondary`. 위아래 `{space.xxl}`
- ~~`purchase-sheet` — 등록비 결제~~ **폐기(2026-09-08, 등록비 폐지).** 화면 9(등록비 결제)와 함께 제거. 규칙("가격 옆에 취소선 할인가·카운트다운 타이머 쓰지 않는다")은 §8.10 하트 스토어가 그대로 승계
- `account-delete-sheet` (신규) — `bottom-sheet` 기반. 삭제되는 항목 안내(`list-row` — 프로필·매칭 기록·채팅 전부, "되돌릴 수 없어요" 강조 문구) + `button-danger`("영구 삭제") + `button-text`("취소"). 이중 확인: `button-danger` 탭 시 같은 시트 안에서 문구가 "정말 삭제할까요?"로 바뀌고 버튼이 한 번 더 노출(재확인 없이 즉시 삭제되지 않도록). **마스코트는 아쉬워하는 표정의 핑크 목도리 여자 버전(`mascot-female-sad.png`)으로 넣는다(2026-09-09 시안 반영).** 울거나 붙잡는 표정처럼 탈퇴를 죄책감으로 막는 연출은 쓰지 않는다. 탈퇴 전에 **매칭 일시중지를 먼저 제안**하는 문구를 시트 상단에 둔다(설계 문서 §2.6, 재가입 2개월 제한이 있으므로 대안을 먼저 보여준다)

- `friend-review-card` (신규, 2026-09-08 — 설계 문서 §2.8 지인 리뷰) — 카드 상세와 프로필에 노출되는 지인 평가 한 장. 구성은 좌측부터 **대학 로고(20dp) + 만화 아바타(32dp) + 리뷰어 닉네임(`{type.label}`, 2026-09-10 — 마스킹 실명에서 변경)**, 그 아래 **장점 태그 `chip` 여러 개 + 자유 텍스트 한 줄(`{type.body-small}`, 2줄 말줄임)**.
  - **가로 스크롤 레일로 배치한다** — 리뷰 개수 제한이 없으므로(전부 노출) 카드 세로 길이가 늘어나지 않게 `mosaic-rail`과 같은 가로 스크롤 패턴을 쓰고, 3장 이상이면 끝에 "더보기"를 둔다
  - **리뷰가 0개면 블록 전체를 숨긴다** — `stat-panel`·`review-strip`과 동일한 원칙(§8.9). 빈약한 상태를 보여주는 것보다 안 보여주는 게 낫다
  - 각 카드에 `flag` 신고 아이콘(기존 신고 컴포넌트 재사용). 신고 누적 시 자동 블라인드(설계 문서 §13 미결18)
  - **로고 이미지는 사용자가 직접 제공한다(2026-09-08).** 대학별 파일을 `design/designMaterials/university/` 에 두고 학교 코드와 파일명을 1:1로 맞춘다. 파일을 갖고 있는 것과 쓸 권리가 있는 것은 다르므로 **상표권 확인은 그대로 남는다** — 사용 지침상 불가하면 상징색 배경 + 학교명 텍스트의 자체 배지로 폴백한다(설계 문서 §13 미결29 — 번호 오기 정정, 종전 '미결33'은 존재하지 않는 항목이었다)

- `review-compose-sheet` (신규, 2026-09-08) — 지인 리뷰 작성 `bottom-sheet`. 상대 아바타+이름 → **장점 태그 다중 선택(`chip` 그리드)** → 자유 텍스트 한 줄 `text-field`(글자수 카운터 노출) → `button-primary`("리뷰 남기기"). 온보딩에서 추천 코드 입력 직후, 그리고 추천인이 푸시를 탭했을 때 이 시트가 뜬다

### 8.9 메인 화면

메인의 목적은 두 가지다.

1. **지금 CampusMate 안에 사람이 있다는 것을 보여준다**
2. **카드를 한 장 더 받고 싶게 만든다**

순서가 있다. 사람이 있다는 확신이 먼저 서야 카드를 더 받을 이유가 생긴다. 그래서 위에서 아래로 **내 현황 → 사람 → 규모 → 학교 → 유도** 순으로 쌓는다.

| 순서 | 블록 | 답하는 질문 |
| --- | --- | --- |
| 1 | `hero-today` | 오늘 내 카드는 어떻게 됐나 |
| 2 | `mosaic-rail` | 여기 사람이 있나 |
| 3 | `stat-panel` | 이 서비스가 돌아가고 있나 |
| 4 | `review-strip` | 남들은 이 앱을 어떻게 평가하나 |
| 5 | `campus-strip` | 내 학교 사람이 있나 |
| 6 | `more-card-cta` | 더 만나려면 뭘 하면 되나 |

**`hero-today`** — 메인 최상단. `{radius.xl}`, 카드 폭 전체, 높이 150 내외

- 카드가 대기 중일 때: `{colors.primary}` 채움 + "오늘의 카드가 도착했어요" + `button-secondary`(흰 채움) "지금 확인하기"
- 이미 확인했을 때: `{colors.surface-soft}` 채움 + 카운트다운(32/700) + "내일 오전 7시"
- **이 배너가 오늘 탭으로 가는 유일한 유도 지점**이다. 다른 곳에서 카드를 열게 하지 않는다

**`mosaic-rail`** — 표시용(만화 아바타) 4:5 카드가 가로로 **자동 슬라이드**한다. 카드 폭 120, 간격 `{space.sm}`, `{radius.md}`

- 속도는 느리게(약 20초에 한 바퀴), 이징 없이 **선형 등속**. 빠르면 광고처럼 보인다
- **축소 모션이 켜져 있으면 자동 슬라이드를 멈춘다.** 손으로 밀 수는 있게 남긴다
- 자동 회전 콘텐츠이므로 **일시정지 수단을 제공**한다 (탭하면 멈춤, `pause` 아이콘). WCAG 2.2.2 요건이다
- **탭해도 프로필이 열리지 않는다.** 미리보기 유도 금지 규칙(§10)은 여기에도 적용된다

*동의·서버 처리가 필요 없어졌다.* 표시용 사진은 애초에 AI가 그린 만화 아바타라 실물을 특정할 수 없다. 그래서 이전 버전의 "내 사진을 메인 화면에 흐리게 노출" 동의 옵션과 서버 픽셀레이션 처리는 전부 없앴다(5.2절 갱신) — **모든 사용자의 표시용 사진이 그대로 레일에 오른다.** 아직 표시용 사진이 없는 계정(변환 대기 중 등)만 `{colors.primary-wash}` 색 블록 + 마스코트로 채운다.

**`stat-panel`** — 3칸 가로. 각 칸: 아이콘 20dp(`{colors.primary}`) → 숫자(`{type.title}`, tabular figures) → 라벨(`{type.caption}`, `{colors.muted}`). 배경 `{colors.surface-soft}`, `{radius.md}`

| 칸 | 아이콘 | 라벨 | 집계 |
| --- | --- | --- | --- |
| 1 | `send` | 전달된 카드 | 서비스 시작 이후 누적 |
| 2 | `user-plus` | 가입 수 | 인증 완료 계정 누적 |
| 3 | `message-circle` | 시작된 대화 | 상호 수락으로 열린 채팅방 누적 |

세 지표 모두 **누적**이다. 누적은 줄어들지 않으므로 어제보다 작아 보이는 날이 없다. "오늘"·"이번 주" 단위는 조용한 날에 숫자가 주저앉아 오히려 죽어 보인다 — 그래서 뺐다.

**`review-strip`** — 가로 한 줄. 좌측 별점(`{type.title}`, 예: "4.8") + 별 아이콘 5개(채움/외곽 혼합) + "(1,204명 평가)" 캡션, 우측 `button-text` "리뷰 남기기" → 스토어 리뷰 페이지로 딥링크. 배경 `{colors.surface-soft}`, `{radius.md}`

- 데이터는 앱스토어·플레이스토어 리뷰 API 값을 그대로 쓴다. **숫자를 합성하거나 반올림 이상으로 꾸미지 않는다** (§8.9 지표 규칙과 동일 원칙)
- 리뷰 수가 임계값 미만이면(§13 미결 9와 동일한 사고방식) 이 블록 전체를 숨긴다 — 빈약한 숫자를 보여주는 것보다 안 보여주는 게 낫다
- "리뷰 남기기" 버튼은 스토어 페이지로 연결된다. **보상은 주지 않는다** — 애플·구글 정책이 리뷰 대가 제공을 금지하므로 하트 무료 획득 항목에서 제외했다(§8.10, 2026-09-08)

**`campus-strip`** — 참여 중인 대학 이름을 칩으로 가로 나열. `{type.caption}`, `{colors.muted}`. 어떤 학교가 들어와 있는지가 곧 신뢰 신호다. 학교 수가 적을 때는 숫자("20개 대학")를 앞세우지 말고 이름만 보여준다

**`more-card-cta`** — 메인 하단. `{colors.primary-wash}` 바탕, `{radius.lg}`, 좌측 마스코트 72dp + 우측 문구 2줄 + `button-secondary`

**카드를 더 받는 수단 (§13 미결 12 — 확정).** 두 갈래를 함께 둔다.

- **프로필 완성도 (기본, 무상).** "자기소개를 채우면 더 잘 맞는 카드를 받아요" — 매칭 벡터 품질을 실제로 올리므로 거짓이 아니다. 완성도 게이지(0~100%)를 함께 보여준다. **완성도는 자기소개·태그·설문으로만 계산한다 — 사진은 정확히 2장으로 고정이라(설계 문서 §13 미결4) 변수가 아니다**
- **하트로 추가 카드 (신규 채택).** 완성도 문구 아래 작은 `button-text` "하트로 카드 한 장 더 받기" + 하트 아이콘 12dp + "50" — 보유 하트가 50 미만이면 버튼이 비활성(Disabled) 상태로 바뀌고 §8.10 하트 스토어로 연결
  - **지급 주기당 1장까지, 다음 카드가 오기 전까지는 언제든 살 수 있다**(2026-09-08 수정). 제한하는 것은 **사는 시점이 아니라 여는 횟수**다 — 상한이 주기당 1장으로 그대로라 "돈을 내면 카드가 계속 나온다"가 되지는 않는다. 지급일 당일에만 버튼을 노출하던 이전 규칙은 폐기한다. 사고 싶은 순간과 살 수 있는 순간이 어긋나면 리듬은 지켜지지 않으면서 결제만 막힌다
  - 버튼은 **주기 내내 노출**된다. 그 주기의 1장을 이미 열었으면 비활성 + "다음 카드가 오면 한 장 더 열 수 있어요"로 바뀐다 — 숨기지 않고 남은 횟수를 드러내는 쪽이 정직하다
  - **구매한 카드는 갱신돼도 사라지지 않는다.** 갱신 한 시간 전에 산 카드가 한 시간 만에 증발하면 그건 결제 사고다. 무상 카드는 다음 지급 때 만료되고 상대가 재노출 대상으로 돌아가지만(설계 문서 §13 미결31), **구매한 카드는 수락·거절을 누를 때까지 결정 대기 큐에 남는다**(바로 아래)
  - ~~초대 보상(친구 초대 시 카드 +1)~~ — 사람 수를 늘리는 정직한 방법이지만, 대학 이메일 인증과 중복 계정 방지 설계가 선행되어야 한다. 이번 결정 범위 밖, 보류

**`pending-decision-queue` (신규, 2026-09-08).** 구매한 추가 카드가 만료되지 않으므로 "아직 수락·거절하지 않은 카드"가 쌓일 수 있다. 별도 화면을 만들지 않고 **오늘의 카드(화면 10)를 큐로 확장**한다 — 진입하면 결정 대기 카드를 먼저 순서대로 보여주고, 다 처리하면 이번 주기의 카드로 넘어간다.

- 메인 `hero-today` 우상단에 `count-badge` 로 결정 대기 장수를 표시한다. 0이면 배지를 그리지 않는다(§8.8 빈 요소 금지 원칙)
- 큐가 비면 기존 화면 11(카드 소진 · 대기)로 그대로 이어진다
- **무상 카드는 이 큐에 들어오지 않는다.** 만료 규칙이 서로 다른 두 종류를 한 목록에 섞으면 "왜 어떤 카드는 남고 어떤 카드는 사라지나"를 설명할 수 없게 된다

**`my-record`** — "내가 받은 수락 3회 · 대화 3개". 개인 기록은 서비스가 작아도 항상 의미가 있다. 지표가 비어 있는 초기에는 이 블록이 `stat-panel` 을 대신한다

**지표에 관한 규칙 — 이것이 메인 설계의 핵심이다.**

1. **어떤 숫자도 조작하지 않는다.** 부풀린 접속자 수는 표시광고법상 거짓·과장 표시이고, 스토어 심사 대상이며, 들키면 신뢰가 한 번에 무너진다
2. **동시접속자를 쓰지 않는다.** 초기에 "지금 접속 3명"이 뜨면 서비스가 죽어 보인다. 가장 크게 보이고 싶은 자리에 가장 약한 숫자를 놓는 셈이다
3. **매칭률처럼 정의가 모호한 지표를 쓰지 않는다.** 무엇을 무엇으로 나눈 값인지 한 줄로 설명할 수 없으면 넣지 않는다
4. **데이터가 없으면 숫자를 지어내지 않고 자리를 바꾼다.** 임계값 미만인 칸은 숨기고, 세 칸이 모두 미달이면 `stat-panel` 전체를 **마스코트 72dp + "첫 기록이 쌓이는 중이에요" 한 줄**로 대체한다(`.pen` 스니펫 `Tklrw`, 남성 마스코트로 통일 — 기본 09b 보드가 아니라 대체 상태 스니펫). 숫자가 준비되면 같은 자리에 그대로 들어온다 (§13 미결 9)
5. 숫자는 **천 단위 구분 기호**를 넣고 tabular figures 로 렌더한다. 갱신될 때 자릿수가 흔들리지 않아야 한다

### 8.10 하트(재화) · 스토어

**하트는 이제 유일한 수익원이다(설계 문서 §2.4, 2026-09-08 등록비 폐지).** 그래도 여전히 **완전히 선택적인** 편의 재화라는 성격은 그대로다 — 매칭·카드 조회·채팅 등 핵심 기능 어디에도 하트를 요구하지 않는다. 하트로 살 수 있는 것은 **추가 카드(§8.9, 50하트)와 아바타 재생성(10하트, 최초 1회 무료) 둘뿐**이다. 어느 쪽도 매칭 품질에 영향을 주지 않는다 — 추가 카드도 동일한 벡터 매칭 큐를 그대로 쓴다(§13 미결19 원칙).

- **재화 아이콘은 `heart-flat-vector-v3` (소프트 3D 벡터, §5.4)로 통일한다** (2026-09-10 변경, `.pen` M3B/M7 — 종전 Lucide `heart` 채움에서 승격). 이모지를 재화 심볼로 쓰지 않는다는 §5.3 원칙은 그대로다. 재화 글리프는 인접 폰트보다 크게 렌더한다 — 잔액 44~48 / 번들 28~30 / 결제 시트 32 / 설정 28 / CTA·아바타 코스트 20 / 리워드 18. **여기서 제외되는(계속 Lucide `heart`) 자리**: 바텀 내비 오늘 탭, 10b 호감 하트, 16c 수락·매칭 기록, `heart-handshake`(지인 리뷰), 09b 108px 히어로 장식 하트, 10 "수락하기" 액션, `00`·`00b` 레퍼런스 보드
- `heart-balance-chip` — `heart-flat-vector-v3` + 숫자(`{type.label}`). 나의정보 탭 상단과 하트 스토어 상단에 노출. 탭하면 하트 스토어로 이동

**`heart-store`** (전체 화면, `app-bar` 뒤로가기 + "하트") — 위에서부터: `heart-value-scene` 히어로(장식, §5.4) → `heart-balance-chip`(크게, 화면 중앙 상단) → 구매 섹션 → 무료 획득 섹션. 두 섹션은 `section-header`로 구분한다. 히어로 씬은 장식일 뿐 잔액·가격 정보를 대신하지 않는다. 무료 획득 섹션은 **요약**(대표 Task 3개 + "전체 보기")이고, 전체 목록은 별도 화면 **18a `무료로 하트 모으기`**다 — 설정(16)의 "하트 무료로 모으기"와 이 요약 섹션 양쪽에서 18a로 들어가고, 18a의 각 Task가 18b(인증샷 제출)로 이어진다(2026-09-10).

- **구매 섹션 — `heart-bundle-card`** — 가로 폭 전체 리스트, `{radius.md}` 카드. 좌측 **하트 티어 이미지**(50→1개/100→2개/200→3개/400→7개 더미, §5.4)+수량(`{type.title}`), 우측 가격(`{type.label}`) + `button-secondary`. 구매 확인 시트(18d)도 선택 상품의 티어 이미지를 그대로 보여준다. **가격 확정(2026-09-08, 설계 문서 §2.4). 기준 단가는 하트 1개 = 40원**:

  | 100 하트 | 3,800원 | 38.0원 | 5% **(추천)** |
  | 200 하트 | 7,200원 | 36.0원 | 10% |

  - **"추천" `count-badge`는 100하트 한 장에만 얹는다**(색은 `{colors.primary}`). 가장 비싼 번들이 아니라 실제로 가장 합리적인 번들에 붙이는 것이 §8.8 정직함 원칙과 맞다
  - **최소 번들이 정확히 추가 카드 1장치다.** 경쟁사는 전부 최소 번들을 여러 번치로 묶어 잔액을 남기는데, 그걸 하지 않는 것 자체가 차별점이다
  - **할인을 얕게 건다(최대 15%).** 추가 카드는 지급 주기당 1장이라 소비량에 하드 상한이 있다. 대량 할인을 세게 걸면 다 못 쓰는 잔액이 쌓이고 환불 분쟁으로 돌아온다
  - **취소선 할인가·실시간 카운트다운 배너를 쓰지 않는다** — 등록비 결제 화면에 적용하던 원칙을 그대로 재화 판매에도 지킨다(최종보고서 §3-4, 썸타임의 상시 구매 압박 배너를 반면교사로 삼음)
  - **사용 제한을 결제 전에 알린다(2026-09-08 확정).** 번들 리스트 **위**에 `{colors.surface-soft}` 바탕 `{radius.sm}` 안내 박스를 고정한다 — "추가 카드는 다음 카드가 올 때까지 한 장만 열 수 있어요. 산 카드는 결정할 때까지 사라지지 않아요." 결제 확인 시트에도 같은 두 문장을 반복하고, 옆에 `help-circle` 로 FAQ(화면 21)를 연다. 쓸 수 있는 양에 상한이 있는 재화를 팔면서 그걸 결제 후에 알리는 건 환불 분쟁과 스토어 심사 양쪽에서 지는 방식이다
  - 결제는 인앱결제 + 서버(FastAPI) 영수증 검증을 그대로 따른다(설계 문서 §7.6과 동일 원칙 적용, 2026-09-12: 백엔드가 FastAPI+Supabase로 확정)

- **무료 획득 섹션 — `list-row`(Task 배리언트, ListRow 컴포넌트 확장)** — 아이콘(좌 20dp) + 제목 + 보상량(하트 아이콘+숫자) + 우측 상태 버튼/뱃지. 상태는 4가지:

### 8.11 커뮤니티

**목적은 하나 — 오늘 카드가 없는 날에도 열어볼 이유를 최소한으로 만드는 것**(최종보고서 §6-8 권고: "매칭 외 콘텐츠는 스코프를 강하게 제한"). 그래서 컴포넌트는 `poll-card` 하나로 제한한다 — 타로·미니게임·스토리형 콘텐츠 등 썸타임의 나머지 체류 장치는 가져오지 않는다.

**`poll-card`** — 리스트형 피드의 기본 단위. `{radius.md}` 카드, 내부 패딩 `{space.md}`

- 상단: `verified-chip` 스타일의 익명 표시("익명") + 작성 시각(상대 시간, `{type.caption}`)
- 중앙: 질문 텍스트(`{type.subtitle}`, 최대 2줄, 넘치면 말줄임)
- **투표 전**: 좌우 2개 버튼. 라벨이 기본값("찬성"/"반대")이면 텍스트 없이 **O·X 아이콘 버튼만**(좌 O = 찬성 파랑 `#2D96DE` 채움, 우 X = 반대 `{colors.primary}` 채움, 흰 아이콘, 2026-09-11 변경 — 종전 O=`{colors.primary}`·X=`{colors.surface-strong}`에서 사용자 요청으로 교체). 커스텀 라벨이면 라벨 텍스트를 담은 `button-secondary` 2개. 버튼 하나를 누르면 투표 확정 — **투표는 되돌릴 수 없다**(재투표로 결과를 조작하지 못하게)
- **투표 후 / 남의 투표 결과를 볼 때**: 버튼 자리가 **도넛 차트**(지름 96, 두께 12, 두 색은 `{colors.primary}` vs `{colors.surface-strong}`)로 바뀌고, 안쪽에 우세한 쪽의 퍼센트(`{type.title}`)를 표시. 도넛 아래 "찬성 62% · 반대 38%" 텍스트 한 줄과 "127명 참여" 캡션
- 하단: `chevron-right`로 상세(전체 댓글·참여자 수) 진입 — 상세 화면은 이번 스코프에서는 **투표 비율 상세 + 참여자 수만** 보여주고 댓글은 만들지 않는다(모더레이션 부담, §13 신규 미결)

**`poll-composer`** (질문 작성 화면) — `app-bar` "익명으로 질문하기" + 질문 입력 `text-field`(멀티라인, 최대 80자 카운터) + 옵션 A/B 라벨 입력(기본값 "찬성"/"반대", 자유 수정 가능) + `button-primary` "익명으로 올리기". 상단에 "작성자 정보는 절대 공개되지 않아요" 안내 1줄

- **모더레이션은 이번 스코프에 포함하지 않는다** — 신고 버튼(`flag`, 기존 신고 컴포넌트 재사용)만 카드마다 붙이고, 처리 정책은 조각6(safety)에서 별도 결정(§13 신규 미결)

**커뮤니티 탭 피드 구조** — `app-bar`(제목 "커뮤니티" + 우측 `+`아이콘 버튼 → `poll-composer`) + `poll-card` 세로 리스트(무한 스크롤) + 빈 상태는 기존 `empty-state` 패턴("아직 질문이 없어요" + "질문 올리기" `button-secondary`)

### 8.12 지인 차단

**목적** — 연락처에 저장된 특정 지인과 서로의 프로필이 매칭 후보에 뜨지 않게 한다.

**2026-09-08 수정 — 전화번호 수집과 "차단할 사람 고르기"를 분리했다.** 지인 차단은 상호 대조라서, 차단하는 쪽(B)이 차단당하는 쪽(A)을 걸러내려면 A의 번호가 시스템에 먼저 등록돼 있어야 한다 — A가 지인 차단에 관심이 없어도 마찬가지다. 그래서:

- **전화번호 등록은 회원가입 필수** — 04 온보딩 1(기본 정보) 화면에서 생년·키·성별과 함께 받는다(§9 화면 4 참조). 별도 소개·동의 화면 없음
- **차단할 사람을 고르는 것(8d, `contact_blocks`)만 선택 사항** — 원할 때 설정 탭에서 진행한다

> **마스코트를 쓰지 않는다.** §5.4의 "신고·차단 흐름에 마스코트 금지" 원칙을 그대로 적용한다 — 참고한 경쟁사 화면(썸타임)은 마스코트를 쓰지만, 이 흐름은 개인정보와 안전이 걸린 화면이라 CampusMate 자체 원칙이 우선한다. 아이콘은 `shield-check`.

**8d 차단할 연락처 선택** (설정 탭에서만 진입, 온보딩에는 없음)

- OS 연락처 권한 요청 다이얼로그(시스템 기본) 이후 진입
- 연락처 리스트, 각 행은 이름 + 마스킹된 번호(`010-****-1234`) + 우측 체크박스, 다중 선택
- 상단 검색창, 하단 고정 `button-primary` "선택 완료 (N명)" — N은 실시간 카운트, 0명이면 비활성
- 완료 시 16b 화면으로 돌아가 갱신된 차단 목록을 바로 보여준다

**설정 탭 진입점** — 기존 `16 설정` 화면의 "차단 목록"(매칭·채팅 상대 차단, 조각 6 기존 기능) 행과 **이름이 겹치므로 구분**: 새 행 "**연락처 차단**"을 별도로 추가한다. 설명 문구 "연락처 속 지인이 나를 발견하지 못하도록 차단해요" + `chevron-right`

### 8.13 자주 묻는 질문 `faq` (신규, 2026-09-08)

**왜 만드는가.** 이 앱에는 설명 없이는 오해를 사는 규칙이 여럿이다 — 카드가 매일 오지 않고, 산 카드를 바로 여러 장 열 수 없고, 실사진이 매칭 전엔 안 보이고, 받은 리뷰를 지울 수 없다. 규칙 하나하나를 그 자리에서 길게 설명하면 화면이 무거워지므로, **짧은 고지는 그 자리에 두고 자세한 설명은 여기로 모은다.**

**`faq-row`** — 질문 한 줄(`{type.label}`) + 우측 `chevron-down` 20dp. 탭하면 같은 카드 안에서 답변(`{type.body}`, `{colors.muted}`)이 펼쳐진다. 펼침·접힘은 `{motion.standard}`. 화면 이동이 아니라 아코디언인 이유는 **찾는 사람이 목록과 답을 번갈아 본다**는 것 하나다.

- 카테고리별 `section-header` 로 묶는다 — **카드·매칭 / 하트·결제 / 사진·프로필 / 지인 리뷰 / 안전·신고 / 계정**
- 상단에 `text-field` 검색 1개. 질문·답변 본문을 모두 대상으로 하는 단순 부분일치면 충분하다
- 한 번에 하나만 펼친다(아코디언). 여러 개가 동시에 열리면 스크롤 위치를 잃는다
- **빈 상태 없음.** 문구를 서버에서 받아오는데 실패하면 마지막 캐시를 그린다. 캐시도 없으면 이 진입점 자체를 숨긴다

**진입점 두 곳.**

| 위치 | 형태 |
| --- | --- |
| 설정(16) | `list-row` "자주 묻는 질문" + `chevron-right` |
| 하트 스토어(18)·결제 확인 시트 | `app-bar` 우측 `help-circle` 20dp — 눌리면 **하트·결제 카테고리로 스크롤된 상태**로 연다 |

**문구는 Supabase `faq` 테이블에서 받는다(2026-09-08 확정).** 하드코딩하면 오타 하나 고치는 데도 스토어 심사가 필요하다. 초기 운영에서 문구가 가장 많이 바뀌는 영역이라 원격 수정이 가능해야 한다. 앱은 마지막 응답을 로컬에 캐시해 오프라인·실패 시에도 그대로 그린다.

## 10. Do / Don't

### Do

- Rausch 는 한 화면에 **한두 곳**만. 수락 버튼이 있으면 그 화면의 Rausch 는 거기서 끝이다
- 모든 탭 가능한 요소는 **48dp 이상**의 터치 영역을 갖는다
- 색으로 전달하는 모든 상태에 **아이콘이나 텍스트를 함께** 붙인다
- 에러는 **문제가 생긴 필드 바로 아래**에 놓는다
- 숫자에는 tabular figures 를 적용한다
- 사진은 로딩 전에 4:5 자리를 미리 잡아둔다
- 신고·차단은 채팅방과 프로필 양쪽에서 두 번의 탭 안에 도달한다
- 결제 금액과 성별 차등 조건은 결제 시트에 **그대로 적는다**
- 사용자를 가리키는 이름은 전 화면에서 닉네임이다. 실명(`real_name`)은 서버 응답에 아예 담지 않는다 (§8.7)

### Don't

- **좌우 스와이프 제스처를 만들지 않는다.** 이 앱은 덱이 아니다
- 카드 뒤에 다음 카드가 쌓인 듯한 시각 효과를 만들지 않는다
- 궁합 점수·일치율 같은 숫자를 노출하지 않는다
- 그라데이션 배경을 쓰지 않는다. 브랜드 그라데이션도 만들지 않는다
- 이모지를 아이콘으로 쓰지 않는다. 모든 아이콘은 벡터 한 가족(외곽선 1.5px)에서 가져온다
- 하트 아이콘을 남발하지 않는다. 수락은 하트가 아니라 체크로 표현한다
- 버튼·칩·앱바에 그림자를 넣지 않는다
- 플레이스홀더를 라벨 대신 쓰지 않는다
- 비활성 버튼에 연한 핑크(`#FFD1DA`)를 쓰지 않는다
- 오늘의 카드 화면에 배너·추천·프로모션을 추가하지 않는다
- 위젯 안에 `Color(0xFF...)` 리터럴이나 하드코딩된 수치를 쓰지 않는다
- 결제 유도에 카운트다운 타이머나 취소선 할인가를 쓰지 않는다
- 상대의 실명을 어디에도 노출하지 않는다 — 매칭 전후 모두, 푸시 알림 문구 포함. 항상 닉네임을 쓴다
- 카드 뒤집기를 스와이프 제스처에 걸지 않는다. 탭이다

- 가로 스크롤이 발생하면 버그다
- 가로 방향(landscape)에서도 카드 화면이 깨지지 않아야 한다. 카드를 스크롤 가능하게 만들고 액션 바를 고정한다

### 11.2 접근성

- 본문 대비 4.5:1, 컨트롤 경계 3:1 (§2.6 검증 완료)
- 터치 타깃 iOS 44pt / Android 48dp 이상, 인접 간격 8dp 이상
- 시스템 글꼴 확대(최대 배율 2.0)에서 레이아웃이 깨지지 않아야 한다. 고정 높이 컨테이너 안에 긴 한글을 넣지 않는다
- 모든 아이콘 버튼에 `Semantics(label:)` 를 준다. 장식용 아이콘은 `ExcludeSemantics` 로 접근성 트리에서 감춘다
- 스크린 리더 포커스 순서가 시각 순서와 일치해야 한다
- 축소 모션 설정을 존중한다 (§7)
- 인증코드 필드는 붙여넣기와 자동완성을 허용한다
